# 변경 설계

목표에 맞는 변경 방향을 함께 이해하고 선택한다. 기존 구조를 정답으로 삼거나 후보 목록만 사용자에게 넘기지 않는다. 설계자가 제안하고 별도 검토자가 비판하며, 메인은 근거를 확인해 권고한다. 제품 구현은 시작하지 않는다.

## 설계할 질문과 조건을 잡는다

[프로젝트 기준 관리](../../docs/project-guidance.md)에 따라 관련 기준을 읽고 설계자와 별도 검토자 모두에게 전달한다. 기존 기준도 변경 후보가 될 수 있음을 구분한다. 마무리에는 확정한 지속 약속의 갱신 여부를 확인해 남기고 계획과 현재 구현을 혼동하지 않는다.

제품 문서와 [작업과 기록의 기준](../../docs/work-records.md)에 따라 보드에서 찾은 현재 작업 파일·지정된 상세 문서·사용자 동작과 명세·기존 결정·관련 이해 기록을 읽는다. 구체적인 설계 질문에서 시작할 수 있으며 별도의 에픽을 만들지 않는다. 반드시 지킬 동작·데이터·외부 약속과 비교할 비용을 후보를 만들기 전에 드러낸다. 사용자의 목적이 불분명하면 중요한 부분부터 함께 정한다.

**후보를 만들기 전에 전제를 꺼낸다.** 작업 파일의 「후보 수단」처럼 아직 대안과 비교된 적 없는 수단과, 설계를 복잡하게 만들 것 같은 전제를 적는다. 각각 같은 높이의 대안(예: 에이전트가 읽는다 ↔ 고정 스크립트가 읽는다)을 적는다. 비교에 필요한 사실을 싸게 시험할 수 있으면 Understand의 실험으로 먼저 돌린다. 이미 같은 높이의 대안과 비교를 거친 결정은 다시 열지 않는다. 실패 예: 대화에서 나온 "에이전트가 수집한다"를 확정으로 넘겨 설계자도 검토자도 그 전제를 묻지 않았다.

현재 구조를 판단할 근거가 부족하면 [현재 구조 이해](../understand/SKILL.md)로 필요한 사실만 확인한다. 충분한 기존 기록이 있으면 같은 조사를 처음부터 반복하지 않는다. 이해와 설계 논의는 오갈 수 있으며 사실·추론·후보·선택을 구분한다.

원칙(들)은 [basics의 「pstack 원칙(들)」](../../basics.md#pstack-원칙들)에서 고르고, 설계 질문과 예시는 [설계 원칙 참고](../../docs/design-principles-reference.md)의 해당 절만 읽는다.

## 후보를 만들고 비교한다

[설계자 역할표](../../docs/agent-calls.md#설계-후보-생성)에 따라 같은 요청서로 두 독립 설계자에게 후보를 요청한다. 메인도 다른 보고를 읽기 전에 자신의 초안·이유·전제를 남긴다. 모델·강도·새 세션·보고 보존·실패 시 대체는 역할표를 원본으로 삼는다.

질문과 필수 조건을 [설계 요청서 틀](references/decision-request.md)에 담는다. 현재 작업·적용할 자료와 해당 부분·담당 범위·각자의 보고 경로를 전달한다. 새 질문과 전제가 바뀐 결정 모두에 쓸 수 있고 처음부터 완성된 명세를 요구하지 않는다.

후보는 요구를 만족하는 가장 단순한 구조부터 설명한다. 후보마다 핵심이 되는 자료구조·알고리즘·패턴을 이름으로 적고, 이 문제 모양에 맞는 이유와 버린 더 단순한 대안을 붙인다. 주요 책임·상태 소유와 수명·데이터 흐름·중요한 실패 처리, 기존 구조와의 연결과 변경 비용을 확인한다. 실제 선택이 갈리는 대안만 비교하며 후보 수를 채우지 않는다. 후보는 복잡함이 생기는 높이에서 가른다.

먼저 필수 조건을 만족하는지 보고, 만족하는 후보의 복잡함·책임·실패 처리·이전과 재변경 비용을 비교한다. 성능·보안 등은 이번 요구와 위험에 따라 깊게 본다. 메인의 안도 같은 기준으로 평가하고 부적합하면 제외한다. 서로 다른 안을 합치면 전체 책임과 상태·실패 처리의 일관성을 다시 확인한다. 공통 근거와 차이를 남기며 다수결로 선택하지 않는다.

## 별도 적대 검토와 확인을 거친다

중요한 설계 후보는 [적대 검토자 역할표](../../docs/agent-calls.md#중요한-설계-후보의-적대적-검토)에 따라 설계에 참여하지 않은 두 새 세션에 같은 요청서로 검토를 맡긴다. 요청서에는 같은 요구·확인 근거·설계 후보와 검토 질문을 담는다. 「확정 (다시 열지 않는다)」에는 사용자 목적·조건과 비교를 거친 결정만 넣고, 후보 수단은 검토 대상으로 넘긴다. 메인의 추천 하나만 넘기지 않고 후보와 제외 이유를 보존한다. 서로의 보고·메인의 전체 대화·작성자와 메인의 선호를 넘기지 않는다.

검토자는 요구 위반·책임과 상태 수명·동시 실행·실패와 재시도·데이터 보존·되돌리기 비용·불필요한 복잡함을 확인하고, 설계자가 고른 원칙(들)의 적용 조건과 빠진 원칙도 본다. 지적에는 근거·발생 조건·사용자가 겪는 결과·필요한 확인을 적게 한다. 지적 수를 채우거나 새 구조를 강제로 만들지 않게 한다. 두 세션이 같은 모델이면 약점을 공유할 수 있으므로 보고의 일치를 동작 증명으로 취급하지 않는다.

지적은 [설계 검토 처리 기준](../../how-we-work.md#설계-검토-지적을-처리하는-기준)으로 근거와 처리 결정을 나눈다. 메인이 타당성을 대조해 이유를 남기고, 실행이 필요한 중요한 전제는 작은 실험으로 확인한다. 현재 권한과 외부 호출·비용의 승인 범위를 따른다. 실행하지 않은 설계를 실행 검증한 것처럼 보고하지 않는다.

새 근거로 주요 전제·책임·동작이 바뀌면 바뀐 부분과 영향을 다시 확인한다. 관련 없는 제안까지 모두 수정하거나 끝없이 검토를 반복하지 않는다. 필요한 두 검토 보고를 확보하지 못하면 완료라고 표시하지 않는다.

## 함께 이해하고 선택한다

논의 중에도 메인이 [브라우저 설명 스킬](../browser-explain/SKILL.md)을 사용해 후보·책임·흐름을 보여 주고 그림을 짚으며 설명한다. 모든 보고가 끝난 뒤에만 사용자를 참여시키지 않는다. 설계안과 후보를 어떤 그림으로 보여 줄지는 [그림 선택 기준의 「설계안을 보여 줄 때」](../browser-explain/references/diagram-guide.md#설계안을-보여-줄-때)와 [설계 페이지 템플릿](../browser-explain/SKILL.md#설명을-읽는-화면으로-만든다)을 따른다. 설명에 필요한 사실이 부족하면 해당 부분의 이해로 돌아간다.

메인은 실제로 갈리는 후보들을 나란히 보여 주고, 후보마다 얻는 것·감수할 비용·맞는 조건과 메인의 추천 이유·권고가 바뀌는 조건·남은 미확인을 설명한다. 사용자가 후보를 고르거나 바꾼다. 추천 하나만 올려 확인받지 않는다. 고르는 방식과 범위는 basics의 「설계 판단은 선택지를 보고 사용자가 고른다」를 따른다. 보고서에 적힌 추천을 사용자가 선택한 방향으로 바꾸어 기록하지 않는다.

지금 정할 범위는 변경 방향, 주요 책임·상태 소유·연결과 여러 레이어가 함께 지킬 약속이다. 결정을 미루면 다시 해야 할 데이터 이전·외부 호출자 수정·쌓인 구현이 있는지 판단한다. 이후 레이어의 상세 파일·함수·인터페이스를 전부 미리 정하지 않는다. 구체적인 형식이 여러 부분의 약속이라면 그 부분은 먼저 정할 수 있다. (진화적 설계, evolutionary design: Kent Beck의 XP, Martin Fowler의 「Is Design Dead?」)

## 남기고 끝낸다

새 요청서·메인 초안·두 설계 보고·두 검토 보고·선택 근거와 설명 자료는 `tasks/<작업 이름>/`에 이름을 달리해 둔다. `설계-정리.md`에는 정한 방향과 이유·대안·수용한 비용·검토 지적의 처리·미확인·레이어에서 구체화할 질문을 남긴다. 반복 호출은 기존 성공 보고를 덮어쓰지 않는 다른 경로를 지정한다. 기존 `designs/<에픽 또는 주제>/` 등은 당시 근거로 연결하며 옮기지 않는다.

메인은 선택한 결과를 작업 파일의 현재 명세·채택 결정의 핵심·적용할 상세 문서에 맞춘다. 중요한 결정의 상세 근거는 설계 정리에 두며 기존 `decisions.md`는 필요할 때 연결한다. 아직 고르지 않은 것은 질문과 정해야 할 시점으로 적는다. 보고와 작업 파일이 충돌하면 메인이 해소하며 설계자·검토자는 자기 보고만 쓰고 작업 파일·개인 기준을 직접 고치지 않는다. 레이어를 나눌 때 이미 정한 결정을 다시 미정으로 취급하지 않도록 관련 기록을 넘긴다.

설계 방향을 사용자가 확인했고 중요한 미확인과 다음에 구체화할 범위가 드러나면 끝낸다. 레이어 분할·구현으로 자동 진행하지 않는다. 레이어 계획과 구현 요청 전체를 이 스킬의 결과물로 미리 만들지 않는다.
