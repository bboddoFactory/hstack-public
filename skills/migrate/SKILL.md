# 규칙 적용

hstack의 규칙이나 말이 바뀌면, 이미 쌓인 프로젝트 기록(제품 문서, 현황판, 레이어 표, 대화 로그)은 저절로 바뀌지 않는다. 이 스킬이 그것을 맞춘다. **기록은 PC마다 따로 있다**. 규칙을 바꾼 PC 말고 다른 PC에서도 hstack을 받은 뒤 한 번씩 돌린다.

**무엇이 바뀌었는지는 `docs/migrations.md`만 읽는다.** `git log`를 읽고 추측하지 않는다. 그 목록은 hstack을 고치는 사람이 버전을 올릴 때 쓴다.

## 흐름 한눈에

| 단계 | 하는 일 | 사용자 |
|---|---|---|
| 1 | 대상 프로젝트 범위를 정하고, 프로젝트마다 시작 버전 뒤의 항목을 모은다 | |
| 2 | 항목마다 적용이 필요한지 알아보고, 바꿀 것과 그대로 둘 것을 표로 만든다 | **멈춘다.** 확인받는다 |
| 3 | 고치고, 버전 파일과 로그를 갱신한다 | |
| 4 | 무엇을 했는지 알린다 | |

## 1. 시작 버전과 항목

기록은 `~/workspace/hstack/data/story-map/`에서 찾되 점검 대상은 다음과 같이 정한다.

- 사용자가 프로젝트 하나나 여러 개를 지정하면 그 범위만 대상으로 한다. 전체 프로젝트를 요청하면 현재 PC의 전체 프로젝트 기록을 대상으로 한다.
- 지정이 없으면 현재 대화에서 다루는 프로젝트를 제품 문서·기록과 연결해 확인한다. 코드 작업 폴더 이름만으로 대상을 정하지 않는다.
- 현재 프로젝트를 식별할 수 없으면 대상만 짧게 확인한다. 불분명하다는 이유로 전체 프로젝트로 확대하지 않는다.

선택한 대상 범위를 짧게 알리고 그 안에서 아래 절차를 진행한다.

[프로젝트 기준 관리](../../docs/project-guidance.md)에 따라 대상 프로젝트의 관련 기준을 읽고, 승인한 마이그레이션 항목에 따른 갱신 필요를 마무리에 확인해 남긴다. 이 참조만으로 새 안내를 일괄 생성하거나 마이그레이션 목록 밖의 규칙을 도입하지 않는다.

[작업과 기록의 기준](../../docs/work-records.md)에 따른 새 `tasks/<작업 이름>/` 기록과 기존 `rows/verbs/cells`·에픽·단계별 폴더 기록이 실제로 어느 형식인지 구분한다. 새 작업은 보드에서 찾은 작업 파일·현재 적용할 상세 문서를 읽고, 기존 기록은 당시 경로와 뜻으로 읽는다. 원본에 새 기준이 생긴 사실과 해당 프로젝트에 적용한 버전은 다르다. 사용자가 버전·전역·설치본 갱신이나 기록 이전을 보류했다면 그 범위를 지킨다. 이 스킬의 원본을 고쳤다는 이유만으로 실제 이전을 실행하지 않는다. 기존 기록의 전환은 출시한 버전의 적용 항목과 사용자 확인 범위 안에서만 한다.

- 시작 버전은 프로젝트 폴더의 **`hstack-version`**(한 줄, 예: `0.6.0`)이다. **파일이 없으면 "0.5.0 이전"**으로 보고 `docs/migrations.md`의 모든 항목을 읽는다.
- 읽을 항목은 `docs/migrations.md`에서 시작 버전보다 **높은 버전**의 것이다. 낮은 버전부터 순서대로 처리하고 현재 출시 버전(`.claude-plugin/plugin.json`)을 상한으로 삼는다. 아직 목록에 정리하지 않은 미출시 변경을 커밋이나 대화에서 추측해 적용하지 않는다.

## 2. 적용이 필요한지 알아본다

항목마다 **"알아보는 법"**을 이 프로젝트의 기록에 대어 본다. 이미 적용된 것은 "적용됨"으로, 해당 없는 것은 "해당 없음"으로 표시하고 건드리지 않는다. 그래서 시작 버전을 몰라도(파일이 없어도) 안전하다.

표에는 선택한 프로젝트마다 항목별로 **적용됨 / 해당 없음 / 바꿀 것(무엇을)**과 이유를 넣는다. 바꿀 것이 없는 프로젝트도 "없음"으로 넣는다. 표를 보이고 **멈춘다.**

**어떤 항목에서도 고치지 않는 것**:

- **대화 로그의 옛 줄.** 덧붙이기만 하는 파일이다. 옛 줄을 고치지 않고 새 줄로 남긴다.
- **옛 이름의 폴더와 파일, 현황판의 에픽 이름.** 핸드오프 문서와 설계 폴더가 현황판의 이름으로 이어져 있어 바꾸면 연결이 끊긴다.
- **옛 방식으로 이미 정한 것.** 새 규칙이 정하는 자리를 옮겼어도 이미 정한 결정을 새 방식으로 다시 하지 않는다. 새 규칙만으로 기존 에픽·레이어를 자동 재분할하거나 옛 결정을 다시 승인받지 않는다.

**범위를 바꾸는 항목**(예: `sample-shop-web` → `sample-shop`)은 사용자에게 제품 이름을 먼저 확인한다. 폴더 이름을 바꾸고, 같은 제품의 다른 폴더가 이미 있으면 합칠지 묻는다.

## 3. 적용하고 남긴다

- 확인받은 것을 고친다.
- 프로젝트마다 **`hstack-version`을 반영한 마지막 항목의 버전으로 고친다**(없으면 만든다). 이 파일이 다음 적용의 시작점이다.
- 프로젝트의 `log.md`에 적용한 버전·바뀐 규칙·이 프로젝트에서 확인하고 바꾼 결과와 한계를 요약한다. 상세한 판단·진행 경과는 해당 작업 로그에 두고 연결한다. 시각과 형식은 공통 작업 기록 기준을 따르며 옛 로그 항목은 바꾸지 않는다.
- 다른 작업이나 세션의 변경을 보존하고 확인받은 부분만 고친다.

## 4. 알린다

- 선택한 대상 범위와 프로젝트마다 한 일 한 줄
- 그대로 둔 것과 이유
- 다른 PC에서도 돌려야 한다는 것(그 PC의 기록은 그 PC에만 있다)

**여기서 스킬이 끝난다.**

## 판단이 모호할 때

`docs/migrations.md` 항목의 "알아보는 법"이 모호하면 적용하지 말고 사용자에게 확인한다.
