# 질문에 맞는 그림과 의미 점검

## 무엇을 보여 주려는가

| 사용자가 확인하려는 것 | 먼저 고려할 표현 | 확인할 핵심 |
|---|---|---|
| 어떤 조건에서 어느 길로 진행하는가 | 흐름도 | 조건별 분기·합류·반복·종료가 실제 선으로 연결되는가 |
| 누가 누구에게 언제 요청하고 응답하는가 | 시퀀스 다이어그램 | 참여자와 시간 순서, 호출 상대와 응답 상대, 조건이 다른 경로 |
| 어느 상태에서 어떤 사건으로 바뀌는가 | 상태 전이도 | 상태와 동작을 구분하고 사건·전환 조건을 적었는가 |
| 누가 어느 책임을 맡고 서로 의존하는가 | 구성도·책임 경계도. 위치가 중요하면 코드 지도를 함께 쓴다 | 실제 대상과 책임, 경계와 연결의 뜻이 분명하며 시간 순서처럼 보이지 않는가 |
| 어떤 데이터가 어디에서 와서 어디에 남는가 | 데이터 흐름도·테이블 관계도 | 데이터의 출처·변환·저장·관계가 호출 순서와 구분되는가 |
| 설계안이 무엇을 어떻게 바꾸는가, 후보가 어떻게 다른가 | 아래 「설계안을 보여 줄 때」 | 바뀌는 가장 높은 수준에서 시작하고, 후보의 차이를 그 차이가 드러나는 그림 위에 얹었는가 |
| 코드를 고치면 처리 흐름이 어떻게 달라지는가 | 고치기 전·후의 짧은 의사 코드나 흐름도를 나란히 | 실제 이름과 책임을 표시하고 같은 조건에서 바뀌는 연결을 비교하는가 |

위 표는 선택 기준의 시작점이다. 사용자가 익숙한 그림 이름을 말했을 때도 실제 질문을 해석해 고른 이유를 먼저 설명한다. 특정 형식을 명확히 요구한 경우에는 그 제약을 존중한다.

## 설계안을 보여 줄 때

- **C4 순서로, 바뀌는 가장 높은 수준에서 시작한다.** System Context(만드는 것의 경계와 바깥) → Container(따로 실행되는 것과 저장소, 추가·변경·삭제 표시) → 바뀌는 곳의 Component → Sequence. 바뀌는 곳까지만 확대한다. 작은 변경은 Component부터 시작할 수 있다. container 사이를 오가는 데이터는 모양과 읽는 쪽을 함께 적는다. (흔한 관행: [C4 model](https://c4model.com), Simon Brown)
- **정상 흐름을 먼저, 후보는 갈리는 곳에서만** 보여 준다.
- **후보의 차이는 그 차이가 드러나는 그림 위에 얹는다.** 표는 보조로만 쓴다.
  - 실행 중 동작이 다르면 sequence 안의 "후보" 상자로 묶는다. UML의 `alt`를 빌리되 이름은 "후보"로 해 실행 중 분기와 구분한다. 공통 메시지는 한 번만 그리고, 갈리는 메시지만 상자의 칸마다 후보 하나로 둔다.
  - 바꿀 때 비용이 다르면 구조도(ERD 등) 위에 흔히 생길 같은 변경 하나를 후보마다 얹고, 같이 고칠 곳(migration, SQL이 있는 코드 등)을 선으로 잇는다. 데이터가 쌓인 뒤 되돌리기 비싼 변경을 우선 고르고, 그 기능을 미리 만들지는 않는다.
- **구조 그림에는 구조와 동작만** 그린다. 작업 단계(레이어)나 이력("L2 구현")을 상자로 그리지 않는다. 레이어가 구조 어디에 해당하는지는 해당 책임 옆 주석으로 단다. 실패 경로는 실패가 생기는 호출에서 갈라 그린다.
- 페이지는 [설계 페이지 템플릿](../SKILL.md#설명을-읽는-화면으로-만든다)에서 시작한다.

## 흐름도

- “쿠폰이 유효한가?”와 같이 답에 따라 다음 행동이 달라지는 곳을 분기로 표시한다. 각 선에 조건을 붙인다.
- 다음 쿠폰을 확인하는 반복선과 확인을 끝내는 경로를 모두 표시한다. 단계 번호를 참조하는 문장으로 선을 대신하지 않는다.
- 쿠폰이 유효하지 않은 경우와 쿠폰 서비스에 접근하지 못한 경우처럼 결과가 달라지는 조건은 다른 경로로 드러낸다. 처리 정책을 아직 정하지 않았다면 그 지점만 미정으로 표시한다.
- 각 노드는 알아볼 수 있는 행동 또는 판단 하나를 뜻한다. 긴 명세 문단을 상자로 감싸고 아래 화살표를 붙인 것은 관계를 그린 것과 다르다.
- 실행 중 조건에 따라 갈라지는 경로와 설계에서 고를 두 후보를 구별한다. 설계 후보를 앱이 매번 묻는 실행 단계로 그리지 않는다.

## 시퀀스 다이어그램

- 시간은 위에서 아래로 흐른다. 참여자는 질문에 필요한 책임을 가진 주체이며, 메시지는 그 주체 사이를 오간다.
- DB를 조회한 서버가 화면에 결과를 전달한다면, 질문의 수준에서 서버를 표시해 놓고 DB가 화면에 직접 응답하는 것처럼 생략하지 않는다. 데이터가 화면에 보인다는 개념만 설명할 때는 데이터 흐름도로 구분한다.
- 요청·응답, 비동기 이벤트, 자기 안의 처리를 필요에 맞게 구분한다. 시간 초과는 응답이 없어서 호출자가 판단하는 경우가 있으므로, 응답을 받았다는 화살표로 무조건 그리지 않는다.
- 선택 실행은 `opt`, 조건에 따른 대안은 `alt/else`, 반복은 `loop` 같은 의미로 표현할 수 있다. 그 도구를 사용하지 않더라도 경로가 서로 대안인지 연속 과정인지 알아볼 수 있어야 한다.
- 색이나 작은 번호로 빈틈을 표시할 수 있다. 해당 사건·조건의 짧은 이름도 그림에서 읽혀야 하며, 상세 평가와 권고는 대화에 둔다.

## 상태 전이도

- 무엇의 상태인지 주체를 이름 붙인다. 주문 상태와 배송 상태처럼 독립적으로 움직이는 대상은 구분한다.
- 상자에는 상태를, 화살표에는 상태가 바뀌는 사건과 조건을 적는다. 단순한 작업 순서와 상태 변화를 섞지 않는다.
- 실패와 취소가 어느 상태에서 가능한지, 그 뒤 상태와 데이터가 어떻게 되는지 중 현재 질문에 필요한 범위를 보여 준다. 미정인 재시도·보관 정책을 임의로 더하지 않는다.

## 정보량과 표현 수준

“첫 화면에 핵심을, 필요할 때 세부를” 보여 주는 점진적 공개는 활용할 수 있는 설계 기법이다. 그러나 핵심 관계를 클릭 뒤에 숨기거나 불필요한 단계를 먼저 만드는 이유가 되지는 않는다. 한 장 전체를 비교해야 하는 질문이면 함께 보여 준다. 사용자의 장면이 다른 경우에는 탭이나 여러 그림이 도움이 될 수 있다.

그림만 단독으로 보아도 누가 무엇을 주고받는지, 중요한 조건이 무엇인지 읽을 수 있어야 한다. 실제 SDK·기억 저장 위치의 차이가 판단 대상이면 그 이름과 짧은 뜻을 남긴다.

## 참고 출처와 적용 범위

- [Mermaid 시퀀스 문서](https://mermaid.js.org/syntax/sequenceDiagram.html): 참여자·메시지·조건·반복의 표현과 문법. Mermaid가 아니어도 같은 관계의 의미를 보존하는 데 참고한다.
- [Mermaid 흐름도 문서](https://mermaid.js.org/syntax/flowchart.html): 노드·연결선·방향·분기 표현. Mermaid 사용 자체를 강제하는 근거가 아니다.
- [NN/g, Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/): 핵심과 부차 정보를 구분하는 흔한 설계 기법. 이 지침에서 페이지·채팅·기록을 나누는 것은 실제 협업 사례에 맞춰 정한 적용안이며, 외부 문서가 이 역할 분담을 그대로 규정한 것은 아니다.

참고 문서는 필요할 때 해당 표현의 정확한 문법과 개념을 확인하는 데 사용한다. 이 스킬을 쓸 때마다 세 문서를 모두 읽거나 이론 설명을 사용자에게 반복하지 않는다.
