# 설명 페이지 제작 요청서 틀

메인이 설명 페이지를 다른 에이전트에게 맡길 때 쓴다. 요청서의 말투와 제목은 페이지 구성을 그대로 끌고 간다. 그래서 요청서에는 사실과 결론만 쓰고, 어떻게 보여 줄지는 스킬과 만드는 쪽에 맡긴다.

## 쓰는 법

- **결론은 메인이 정리해서 준다.** 질문에 대한 답을 세 줄 이하로 쓰고, 그것을 받치는 사실은 "근거"로 따로 적는다. 결론 줄을 늘어놓으면 그대로 긴 요약이 된다. 자료만 넘기면 결론 없는 나열이 나온다.
- **맥락 설명에는 "너에게 주는 맥락, 페이지에 옮기지 않는다"를 붙인다.** 붙이지 않으면 배경 문단이 페이지 머리에 옮겨 적힌다.
- **구성을 이끄는 말을 쓰지 않는다.** 요청서의 제목을 "정할 것", "위험과 대안"처럼 페이지 절 이름으로 쓰지 않는다. "독자는 무엇을 정해야 하는지 알고 싶다" 같은 문장은 실제로 사용자가 정할 것이 있을 때만 쓴다. 표, 막대, 흐름도 같은 표현을 지정하지 않는다.
- **원칙을 지정하지 않는다.** 어떤 원칙을 쓸지는 만드는 쪽이 스킬의 원칙 표에서 고른다.
- **긴 원자료는 경로로 준다.** "행의 사실만 쓰고 그 파일의 문장 표현과 구성은 따르지 않는다"를 함께 적는다. 원자료 안의 내부 참조(번호, 결정 이름)는 무엇을 뜻하는지 요청서에서 풀어 준다.
- **한 낱말은 한 뜻으로만 쓴다.** 비슷한 것이 둘이면 이름을 따로 붙인다(예: "미정 결정"과 "판정이 다른 항목"). 요청서의 말은 그대로 페이지로 옮겨 간다.
- **모르는 것은 무엇이 결론을 바꿀 수 있는지만 적는다.** "모르는 것은 페이지에 적으라"고 시키지 않는다. 면책 문단이 생긴다.

## 틀

```markdown
# 설명 페이지 요청: <주제>

너는 설명 페이지를 만드는 에이전트다. `<hstack>/skills/browser-explain/SKILL.md`와 그 파일이 가리키는 references, assets를 읽고 그대로 따라 페이지 하나를 만든다.

## 맥락 (너에게 주는 맥락, 페이지에 옮기지 않는다)
<누가 읽는지, 그 사람이 이 페이지로 알고 싶은 것 한 문장>

## 사실
<참여자, 순서, 숫자, 조건. 확인한 것과 가정한 것을 구분한다>

## 결론
<질문에 대한 답 세 줄 이하. 남은 선택이 있으면 선택지와 메인의 권고>

## 근거
<결론을 받치는 사실. 페이지에서는 요약이 아니라 그림 옆으로 간다>

## 결론을 바꿀 수 있는 미확인
<없으면 없음>

## 원자료 (있으면)
<경로>. 사실만 쓰고 표현과 구성은 따르지 않는다. <원자료 속 내부 참조의 뜻>

## 지킬 것
- 파일은 아래 폴더 안에만 쓴다. 다른 파일은 읽기만 한다.
- 다른 에이전트에게 다시 맡기지 않는다.
- 이 요청서에 없는 사실을 지어내지 않는다.

## 파일과 확인
- 작업 폴더와 자료 이름: <작업 폴더>, <이름>. `new page <작업 폴더> <이름>`(비교판이면 `new board <작업 폴더> <이름>`)으로 자리를 만들고 `<작업 폴더>/자료/<이름>/` 안에서만 쓴다.
- 스킬 CLI의 `build <자료 폴더>`가 검사를 통과해 판을 놓게 한다. 스크린샷을 찍어 읽지 않는다.

## 보고
같은 자료 폴더의 `보고.md`에 고른 원칙과 이유, `build` 결과, 요청서에서 모호했던 점, 엔진으로 그리지 못해 직접 그린 그림과 엔진 입력으로 옮기지 못한 뜻을 쓴다. 마지막 답은 보고서 경로 한 줄이다.
```
