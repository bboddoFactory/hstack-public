# 브라우저로 설명하기

설명 페이지는 사람이 보는 보고서다. **설명은 그림으로 하고, 글은 그림을 읽게 돕는 만큼만 쓴다.** 줄글이 길수록 이해가 떨어진다. 글로만 전할 것이면 페이지를 만들지 않고 대화에서 한다. 페이지는 채팅에 기대지 않는다. 다만 이것은 배경을 늘어놓으라는 뜻이 아니다. 낯선 말은 그 말이 처음 나오는 자리에서 짧게 푼다.

이해만 필요한 질문이면 그 이해를 도우면 충분하다. 빈틈과 선택지를 억지로 만들지 않는다.

## 질문에서 시작한다

사용자가 알고 싶은 관계, 흐름, 차이를 한 문장의 질문으로 잡는다. 이 질문은 페이지를 짜는 기준이고 페이지에 "질문:"으로 적는 문장이 아니다. 이미 알 수 있는 목적을 다시 묻지 않는다. 사용자는 그림 이름을 몰라도 요청할 수 있어야 한다. 특정 형식을 명확히 요구했으면 그 제약을 따른다.

"발표하듯", "PPT처럼", "한눈에"를 슬라이드 넘김 요청으로 자동 해석하지 않는다. 사용자가 무엇을 어떻게 이해하려는지에서 확인한다.

## 보고서 모양으로 둔다

위에서부터 이 순서다. 해당 없는 자리는 뺀다. 각 자리의 마크업은 [페이지 뼈대](references/page-skeleton.md)에 있다.

1. **제목.** 무엇에 대한 페이지인지. 제목 아래에 배경, 경위, 페이지 소개 문단을 두지 않는다.
2. **요약.** 결론을 세 항목 이하의 목록으로. 항목 하나는 굵은 핵심 구절과 짧은 이유 한 마디(예: "**알림은 주문 저장 뒤에 보낸다.** 저장이 실패하면 알림도 가지 않는다")이고, 폰에서 두 줄을 넘지 않는다. 결론을 받치는 나머지 사실은 그것을 보여 주는 그림 옆으로 보낸다. "질문/답" 같은 라벨이나 강조 상자를 쓰지 않는다. 훑어 읽는 사람이 굵은 구절만 이어 읽어도 결론이 잡히게 한다.
3. **정할 것.** 읽는 사용자가 이 페이지를 보고 정해야 할 것이 있으면 요약 바로 아래에, 선택지를 나란히 놓은 짧은 비교(얻는 것, 잃는 것)와 권고로. 맨 아래에 묻지 않는다. 다른 방법(평가, 시험)으로 정하기로 한 것은 "정할 것"으로 쓰지 않는다.
4. **본문.** 그림마다 제목, 부제, 그림. 그림 제목은 그 그림에서 읽어야 할 주장 한 문장이다(예: "주문이 저장되면 알림 서버가 한 번만 보낸다"). 부제는 그림 이름과 짧은 뜻, 이 질문에 그 그림을 고른 이유 한 문장이다. 사용자가 그림 이름과 고르는 기준을 익히게 하려는 자리다.
5. **확인하지 못한 것.** 결론이나 결정을 바꿀 수 있는 것만 한두 줄. 작성자가 자기 그림을 확신하지 못한다는 류의 문장, 절마다 붙는 면책 문구는 쓰지 않는다.

"읽는 법" 같은 별도 절을 두지 않는다. 그림 속 참여자나 상자의 뜻은 그림 안에 짧게 붙인다(예: 상자 이름 아래 작은 부제).

장면이 여러 개면 각각이 다른 질문이나 조건에 답하는지 본다. 한 장면의 연속 흐름을 읽으려고 다음 버튼을 반복해서 누르게 만들지 않는다.

## 쓰기 전에 원칙을 고른다

표현과 구성은 [설명 글의 원칙](references/writing-principles.md)에서 이 페이지에 맞는 것을 골라 정한다. 표를 열어 "꺼낼 상황"이 지금 페이지에 해당하는 원칙을 고르고, 그 원칙의 "이 스킬에서는"과 예를 읽는다. 고른 원칙은 작업 기록이나 위임 보고에 한 줄로 남기고 페이지에는 쓰지 않는다.

어느 페이지에나 지키는 것:

- **표현은 내용의 모양으로 고른다.** 흐름과 순서는 그림, 여러 항목의 비교는 표, 값의 크기 비교는 막대처럼. 고른 것 하나를 강조할 때는 강조색 하나만 쓰고 나머지는 중립색으로 둔다.
- **같은 속성을 반복하는 카드 더미를 만들지 않는다.** 항목마다 "지금, 바꿀 안, 위험"처럼 같은 칸을 문단으로 채운 카드가 이어지면, 내용의 모양(무엇이 어디로 옮겨 가나, 무엇으로 이루어졌나, 무엇이 무엇보다 큰가)에 맞는 그림이나 표로 바꾼다.
- **긴 목록은 개요를 먼저, 상세는 접어 둔다.** 항목이 많으면 전체를 한눈에 보는 그림(예: 묶음마다 가로 막대 하나를 목적지별 색으로 나눔)을 먼저 두고, 항목별 상세는 기본으로 접힌 목록으로 둔다.
- **그림을 글로 다시 풀지 않는다.** 그림이 보여 주는 순서나 관계를 문단으로 반복하지 않는다. 그림이 없는 절이 줄글로 길어지면 표, 목록, 그림으로 바꾸거나 뺀다.
- **페이지의 질문에 답하지 않는 절은 넣지 않는다.** 받은 사실을 모두 옮겨 담지 않는다.
- **짧아도 뜻이 완결된 구절로 쓴다.** 명사를 가운뎃점(·)이나 화살표로 이어 문장을 대신하지 않는다.
- **페이지 밖에 기대는 참조를 쓰지 않는다.** 대화나 작업 기록에만 있는 번호와 이름("결정 2", "S2"), 원본 없이 뜻이 없는 줄 번호, 정의 없는 내부 줄임말을 쓰지 않는다. 페이지 안에서도 앞의 항목은 번호보다 이름으로 가리킨다.
- **페이지가 만든 표시는 그 자리 가까이에서 뜻을 준다.** 같은 표시에 두 가지 뜻을 맡기지 않는다.
- **개념은 전문 용어에 짧은 뜻을 붙여 쓴다.** 비유나 새로 지은 말로 바꾸지 않는다.
- **맡겨서 만들 때 받은 요청서의 배경 설명은 에이전트가 읽으라고 쓴 것이다.** 페이지에 옮기지 않고, 요청서나 요청한 쪽을 페이지에서 언급하지 않는다.

## 맡겨서 만든다

페이지는 메인이 [요청서 틀](references/page-request.md)로 요청서를 써서 [역할표](../../docs/agent-calls.md#구현자-레이어-구현-버리는-시제품)의 설명 페이지 제작에 맡기는 것이 기본이다. 결론을 정리하는 일은 메인이 하고, 표현을 고르고 그리고 화면을 다듬는 반복은 맡긴 쪽이 한다. 받은 페이지는 메인이 build(check) 통과와 내용이 질문에 맞는지를 확인한다. 화면을 눈으로 보는 판단은 사용자가 허브에서 한다. 그림 하나에 몇 줄처럼 다듬을 것이 적고 메인의 대화가 짧을 때는 메인이 직접 만들어도 된다.

## 관계를 실제로 그린다

그림 종류, 주체, 화살표, 분기 표현을 고를 때 [그림 선택과 의미 점검](references/diagram-guide.md)의 해당 부분을 읽는다. hstack-diagram 엔진을 쓸 수 있으면 엔진이 그리는 종류(시퀀스, 흐름도, 상태 전이도, ERD, C4 컨텍스트와 컨테이너, 데이터 흐름 등)는 엔진으로 그린다. 엔진은 [스킬 CLI](scripts/explain.mjs)로 부른다(`node ~/workspace/hstack/skills/browser-explain/scripts/explain.mjs <명령>`, 경로나 환경 변수를 맞추지 않는다). `describe <종류>`로 그 종류의 입력과 예시를 보고(입력과 제약의 원본이다), 입력 JSON을 쓴 뒤 `draw <입력.json>`으로 옆에 같은 이름의 SVG를 만든다. 그림을 페이지에 넣는 법은 [페이지 뼈대](references/page-skeleton.md)의 「엔진이 그린 그림 넣기」를 따른다. 아직 정하지 않은 것은 `undecided`(이유 한 줄), 상자의 짧은 설명은 `description`, 새로 생기거나 바뀌거나 없어지는 것은 `change`로 엔진에 옮긴다. 엔진이 그 종류를 그리지 못하거나 그림의 뜻을 엔진 입력으로 옮길 수 없으면 그 그림만 직접 그리고 무엇을 옮기지 못했는지 보고에 남긴다(엔진에 더할 거리다). 직접 그릴 때는 그 그림의 공식 표기법(UML 시퀀스와 상태 기계, 흐름도 기호, crow's foot ERD, C4 같은 것)을 지킨다. 종류를 채우려고 여러 그림을 만들지 않는다.

- 주체, 화살표, 조건을 먼저 정하고 꾸민다. 확인한 동작, 적용할 제안, 모르는 부분을 섞어 하나의 확정된 흐름으로 그리지 않는다. 제안이면 제안 표시를 붙인다.
- 미정인 정책을 완성된 흐름으로 메우지 않는다. 정하지 않은 지점만 미정으로 표시한다.
- 흐름도의 분기, 합류, 반복은 선으로 연결한다. "3번으로 돌아감" 같은 문장으로 연결을 대신하지 않는다.
- 주석을 잇는 선과 다음 실행으로 넘어가는 화살표를 구분한다.
- 시퀀스의 화살표는 실제로 메시지를 주고받는 주체에 잇는다. 중간 주체를 생략하면 그 추상화가 무엇인지 알아볼 수 있게 한다.
- 질문에 중요한 실패, 재시도, 늦은 응답은 그 조건을 보여 준다. 가능한 모든 예외를 처음부터 붙이지 않는다.
- 화살표, 선 모양, 색의 뜻을 그림 안에서 일관되게 쓴다. 요청과 응답, 확정과 제안처럼 서로 다른 구분을 한 기호에 동시에 맡기지 않는다.
- 그림의 의미를 바꾸는 조건은 남긴다. "실패 표시 뒤에도 저장한 결제는 남는다" 같은 결과, 실제 동작과 제안의 구분, 단위는 부연이라는 이유로 지우지 않는다.

## 화면으로 만든다

`new page <작업 폴더> <이름>`(이해하는 설명 페이지)이나 `new board <작업 폴더> <이름>`(사용자가 후보를 골라야 할 때의 비교판)이 만든 `<작업 폴더>/자료/<이름>/원본.html`에 쓴다(빈 뼈대는 [page-blank.html](assets/page-blank.html)과 [board-blank.html](assets/board-blank.html), 부품을 다 보인 예시는 [page.html](assets/page.html)). 자리와 부품은 [페이지 뼈대](references/page-skeleton.md)의 요소와 class를 쓴다. 모양은 [공통 CSS](assets/explain.css) 한 벌이 정한다.

그림에 닿기 전에 큰 표어, 배지 줄, 기호 사전을 지나게 하지 않는다. 장식보다 관계와 읽는 순서에 강조를 쓴다. 상자 안에 상자를 겹쳐 넣지 않는다. 글자를 줄여 한 화면에 억지로 넣지 않는다. 의미가 다른 장면으로 나누거나 세부를 별도 그림으로 확대한다.

버튼, 탭, 접기를 넣을 때는 사용자가 무엇을 비교하거나 확인하려고 누르는지 정한다. 핵심 경로를 숨기지 않는다. 검색, 필터, 재생, 테마 설정 같은 컴포넌트를 기본으로 넣지 않는다. 임시 설명 자료의 모양을 제품 앱의 디자인 규칙으로 등록하지 않는다.

## 의미와 화면을 확인한다

저장 위치, HTTP 제공, 서버 유지와 주소 전달은 [브라우저 설명 자료 절차](../../how-we-work.md#브라우저로-이해설계-자료를-보여-주는-방법)를 따른다.

- **페이지만 읽은 사람이 되어 본다.** 대화를 모르는 사람이 이 페이지만 보고 "무엇을 설명하나, 결론은 무엇인가, 뜻을 모르는 표시가 있나"에 답할 수 있는지 본다. 막히면 그 자리를 페이지 안에서 고친다.
- 질문을 놓고 그림을 처음부터 끝까지 따라간다. 주체 이름, 요청과 응답의 상대, 조건별 경로와 끝이 맞는지 본다. 글과 그림이 같은 것을 다르게 말하지 않는지 본다(예: 본문은 "3번까지 다시 시도", 그림은 "3번째 실패에서 멈춤").
- 스킬 CLI의 `build <자료 폴더>`가 check를 돌리고 통과해야만 판(올린 시각 이름의 HTML)을 놓는다. 따로 볼 때는 `check <페이지>`다. 넓은 화면과 폰 폭(390px)에서 틀 덮어쓰기, 고정 자리 순서, 작은 글자, 명암비, 폰 넘침, 채우지 않은 그림 자리, 상자 안 글자 잘림, 단어 중간 줄바꿈을 센다. 엔진 그림 안의 겹침과 잘림은 엔진이 그릴 때 검사한다.
- 스크린샷을 찍어 읽지 않는다. 셀 수 있는 화면 문제는 `check`가 잡고, 눈으로 보는 판단은 사용자가 페이지를 열어 한다.

## 채팅에서는 짚고 판단한다

채팅에는 페이지마다 허브 주소 한 줄(`<허브 주소>/#<프로젝트>/<작업>/<자료 이름>`)과 한두 줄 요지를 준다. 판 파일 주소를 주거나 브라우저를 열어 주지 않는다. 페이지의 내용을 채팅에 다시 늘어놓지 않고, 페이지에 없는 설명을 채팅에만 두지도 않는다.

그다음 채팅에서는 그림의 특정 주체, 단계, 조건을 짚으며 사용자의 질문에 답하고 함께 판단한다. 지금 알아야 할 빈틈과 결정할 지점부터 이야기하고 모든 미정을 한꺼번에 묻지 않는다. 사용자가 결정하면 페이지와 작업 명세를 맞춰 고친다. 대화에서 나온 설명이 다음에 다시 열어도 필요하면 페이지에 옮긴다. 그림이 생겼다는 이유로 설계가 확정됐거나 구현이 승인됐다고 해석하지 않는다. 조사 경과와 검증 내역은 작업 기록에 남긴다.
