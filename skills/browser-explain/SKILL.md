# 브라우저로 설명하기

사용자가 그림을 보며 동작과 구조를 이해하고, 빠진 조건과 결정할 지점을 발견해서 판단할 수 있게 돕는다. 브라우저에는 그림과 핵심 해설을 놓고, 그 대상을 짚으며 하는 상세 설명은 대화에서 한다. 이해만 필요한 질문에서는 그 이해를 도우면 충분하며 빈틈과 선택지를 억지로 만들지 않는다.

이 역할 분담은 현재 대화에서 함께 보며 이해·설계를 논의하는 자료에 적용한다. 사용자가 혼자 읽을 보고서나 강의 자료를 요청했다면 해설도 그 자료 안에서 완결돼야 한다. 모든 글을 채팅으로 빼는 규칙으로 확대하지 않는다.

## 질문에서 시작한다

현재 대화에서 사용자가 알고 싶은 관계·흐름·차이를 한 문장으로 잡는다. 이미 알 수 있는 목적을 다시 묻지 않는다. 사용자는 그림 이름을 몰라도 요청할 수 있어야 한다. 익숙한 그림 이름을 말했더라도 현재 목적을 함께 해석하고 다른 표현이 더 맞으면 이유를 짧게 설명한다. 특정 형식을 명확히 요구한 경우에는 그 제약을 존중한다. 단순한 사실 답변을 위해 별도 페이지를 만들지는 않는다.

그림 이름·그 그림이 보여 주는 관계의 짧은 뜻·이번 질문에 그 그림을 고른 이유를 **페이지 제목 바로 아래**에 한두 문장으로 쓴다(템플릿의 `context` 문단). 선택 이유는 채팅에서 반복하지 않는다. 그림을 보면서 바로 읽을 수 있게 하려는 것이다. 사용자가 이름과 선택 기준을 반복해서 익힐 수 있도록 실제 관계와 연결해 쓴다. 예: “상태 전이도: 무엇이 어떤 상태에서 어떤 상태로 바뀌는지 보여 주는 그림. 주문 상태를 보면 결제 후 배송으로 어떻게 넘어가는지 확인하기 좋아서 골랐다.” 그림 선택을 사용자에게 넘기는 질문이나 별도 승인 단계로 만들지 않는다. 같은 그림의 작은 수정마다 고치지 않으며, 질문이나 표현 방식이 바뀌면 선택 이유를 다시 쓴다.

“발표하듯”, “PPT처럼”, “한눈에”라는 표현을 슬라이드 넘김 요청으로 자동 해석하지 않는다. 사용자가 원하는 것은 무엇을 어떻게 이해하게 되는지에서 확인한다.

첫 그림에는 현재 질문의 관계가 보여야 한다. 장면이 여러 개라면 각각이 다른 질문이나 조건에 답하는지 본다. 한 장면의 연속 흐름을 읽기 위해 다음 버튼을 반복해서 누르게 만들지 않는다. 여러 장면을 한 페이지에 두거나 탭으로 나누는 것은 비교·집중에 실제로 도움이 될 때 고른다.

## 내용을 둘 곳을 가른다

| 위치 | 남길 내용 |
|---|---|
| 브라우저 | 지금 보는 대상과 관계를 드러내는 그림·표·실제 예시와 짧은 핵심 해설. 읽는 데 필요한 제목·주체 이름·화살표 뜻·분기 조건·단위·범례와 주석 |
| 대화 | 그림의 어느 부분을 보면 되는지, 상세 해석과 판단의 근거·대안·권고, 사용자와 논의할 선택 |
| 작업 기록 | 조사 경과, 파일·명령·포트, 검증 내역, 전체 미정 목록, 상세 근거와 변경 이력 |

브라우저에 문장을 더하기 전에 **이 문장이 없으면 그림을 잘못 읽거나 지금의 판단을 못 하는지** 본다. 아니면 대화나 기록으로 옮긴다. 화살표를 같은 뜻의 문단으로 다시 풀어 쓰지 않는다. 그림 바깥에 요약·상태 배지·주의·확인 목록·기록 링크를 관성적으로 덧붙이지 않는다.

기본 구성은 제목 → 핵심 질문 → 그림 → 짧은 핵심 해설이다. 핵심 해설은 그림에서 무엇을 봐야 하는지와 그 의미를 한두 문장으로 짚는다. 그림만 보고 요점을 전부 찾아내게 하지 않는다. 중요한 조건을 문장 수에 맞추려고 지우지 않는다.

그림의 의미를 바꾸는 조건은 남긴다. 예를 들어 “실패 표시 뒤에도 저장한 결제는 남는다”는 결과, 실제 동작과 제안의 구분, 반환값의 단위는 부연이라는 이유로 지우지 않는다. 중요한 미확인·생략을 채팅에만 숨겨 그림이 확정 사실처럼 보이게 하지 않는다. 해당 위치의 짧은 표시로 구분한다.

사용자가 후보를 비교하거나 남은 논의를 고르려는 경우, 비교 기준·차이·비용·핵심 질문 자체가 보는 대상이다. 이 내용을 단순 부연으로 지우지 않는다. 이를 해석하는 메인의 권고와 이유를 대화에서 설명한다.

무엇을 보여 줄지는 질문에 맞춘다. 사용자 조작만 묻는 그림에 내부 파일·API·모델 제품명을 늘어놓지 않되, 보여 주는 것은 실제 이름으로 부른다.

## 관계를 실제로 그린다

그림 종류·주체·화살표·분기 표현을 고를 때 [그림 선택과 의미 점검](references/diagram-guide.md)의 해당 부분을 읽는다. 종류를 채우려고 여러 그림을 만들지 않는다.

- 주체·화살표·조건을 먼저 정하고 꾸민다. 현재 확인한 동작, 적용할 제안, 모르는 부분을 섞어 하나의 확정된 흐름으로 그리지 않는다.
- 미정인 정책을 완성된 흐름으로 메우지 않는다. “쿠폰이 유효하지 않은 경우와 서비스 접근 실패는 구분한다”만 정했다면, “접근 실패를 기록하고 즉시 종료한다”까지 확정된 동작으로 그릴 수는 없다. 제안이라면 해당 처리에 제안 표시를 붙인다.
- 흐름도의 분기·합류·반복은 선으로 연결한다. “3번으로 돌아감”이라는 설명 문장만 두고 연결을 독자에게 복원시키지 않는다.
- 주석을 잇는 선과 다음 실행으로 넘어가는 화살표를 구분한다. 설명 상자로 향하는 화살표 때문에 새 처리 단계나 실패 경로가 생긴 것처럼 보이지 않게 한다.
- 시퀀스의 화살표는 실제로 메시지를 주고받는 주체에 연결한다. 중간 주체를 생략하면 그 추상화가 무엇인지 알아볼 수 있게 하고, 요청·응답 그림과 데이터 이동 그림을 설명 없이 섞지 않는다.
- 질문에 중요한 실패·재시도·늦은 응답은 해당 조건을 보여 준다. 가능한 모든 예외를 처음부터 붙이지 않는다. 조건이 다른 경로를 모두 연속 실행되는 순서처럼 그리지 않는다.
- 화살표·선 모양·색의 뜻을 그림 안에서 일관되게 사용한다. 요청/응답과 확정/제안처럼 서로 다른 구분을 같은 기호에 동시에 맡기지 않는다.

## 설명을 읽는 화면으로 만든다

처음 만드는 자료는 [흐름도](assets/flow.html)·[시퀀스](assets/sequence.html)·[상태 전이도](assets/state.html) 중 질문에 맞는 템플릿과 [공통 스타일](assets/shared.css)을 필요한 만큼 프로젝트의 작업 폴더로 복사해 시작한다. 제목·주체·단계·관계·핵심 해설은 현재 질문에 맞춰 바꾸고, 배치는 대상 수와 관계에 맞춰 조정한다. 공통 템플릿을 개별 작업 결과로 덮어쓰지 않는다. 템플릿 안의 내용(sample-shop)은 편집 예시이며 다른 프로젝트의 사실이나 확정 설계가 아니다. 템플릿 형식에 질문을 억지로 맞추지 않는다.

설계안과 후보를 보여 줄 때는 아래 템플릿에서 시작한다. 그림 선택 기준은 [「설계안을 보여 줄 때」](references/diagram-guide.md#설계안을-보여-줄-때)다. 모든 `data-slot` 자리를 현재 질문의 내용으로 바꾸고, 필요 없는 자리는 지운다.

| 질문 | 템플릿 | 자리(`data-slot`) |
|---|---|---|
| 무엇이 어떻게 바뀌나 | [설계안](assets/design.html) | `type`, `title`, `context`, `legend`, `system-context`, `container`, `component`, `sequence`, `sequence-detail` |
| 후보마다 실행이 어떻게 갈리나 | [후보: 동작 차이](assets/candidate-sequence.html) | `type`, `title`, `context`, `legend`, `diagram`(후보 상자가 있는 sequence), `insight` |
| 나중에 바꿀 때 무엇을 같이 고치나 | [후보: 변경 비용](assets/candidate-change-cost.html) | `type`, `title`, `context`, `legend`, `diagram`(같은 변경을 얹은 ERD), `insight` |

기존 설명 자료의 표현을 재사용할 수 있으면 재사용한다. 표준 다이어그램을 안정적으로 그리는 도구가 있으면 활용하고, SVG 등을 직접 그리더라도 주체와 연결의 의미는 유지한다. 도구 선택이 새로운 제품 구조나 개발 작업이 되게 하지 않는다.

짧은 제목과 큰 그림을 중심에 둔다. 그림에 도달하기 전에 큰 표어·배지·서론을 지나게 만들지 않는다. 제목·단계 이름·글자 크기를 일관되게 두고 장식보다 관계와 읽는 순서에 강조를 쓴다. 임시 설명 자료의 모양을 제품 앱의 장기 디자인 규칙으로 자동 등록하지 않는다.

글자를 줄여서 한 화면에 억지로 넣지 않는다. 의미가 다른 장면으로 나누거나 세부 관계를 별도 그림으로 확대한다. 비교에 필요한 전체 관계는 계속 찾을 수 있어야 한다. 좁은 화면에서 넓은 그림을 가로로 이동하게 할 수 있지만, 페이지 전체가 의도치 않게 넘치거나 관계의 한쪽이 잘려서는 안 된다.

버튼·탭·접기를 넣을 때는 사용자가 무엇을 비교하거나 확인하기 위해 누르는지 정한다. 핵심 경로를 숨기거나 같은 상세 화면으로 가는 조작을 중복해서 만들지 않는다. 검색·필터·재생·테마 설정 같은 컴포넌트를 기본 꾸러미로 넣지 않는다.

## 그림의 의미와 화면을 확인한다

저장 위치·HTTP 제공·서버 유지와 주소 전달은 [브라우저 설명 자료 절차](../../how-we-work.md#브라우저로-이해설계-자료를-보여-주는-방법)를 따른다. 프로젝트의 기존 접속 기준과 서버·공유 주소를 재사용한다.

사용자의 질문을 놓고 처음부터 끝까지 그림을 따라가 본다. 주체 이름이 맞는지, 요청과 응답의 상대가 맞는지, 조건에 따른 경로와 끝이 맞는지 확인한다. 원래 데이터와 반대 의미의 그림이나 생략 때문에 오해할 그림을 예쁘다는 이유로 통과시키지 않는다.

실제 URL을 브라우저로 열어 그림의 렌더링, 읽을 수 있는 글자 크기, 선·글자 겹침과 잘림을 직접 확인한다. 넣은 조작은 눌러 본다. 사용 기기에 맞는 폭에서 확인하고, 색상 모드에 따라 값이 바뀌면 그 모드도 본다. HTTP 200이나 구문 통과는 화면 확인의 대체가 아니다.

브라우저 연결 도구가 막히면 사용 가능한 다른 브라우저·앱 조작 도구로 실제 화면을 확인한다. 가능한 경로가 없으면 확인하지 못한 층을 밝히고, 보았다고 보고하지 않는다. 이 때문에 관계없는 설정을 바꾸거나 새 도구 체계를 만들지는 않는다.

사용자가 보려는 그림을 열어 두고 정확한 주소를 전달한다. 채팅에는 필요할 때 읽는 순서와 이번 판단만 덧붙이고, 페이지의 내용을 다시 전부 나열하지 않는다. 선택과 검증의 자세한 근거는 해당 작업 기록에 남긴다.

## 그림을 보며 함께 판단한다

브라우저 자료를 만든 뒤 채팅에서 그림의 특정 주체·단계·조건을 짚으며 의미와 근거를 설명한다. 사용자가 현재 알아야 할 빈틈과 결정할 지점부터 논의하고 모든 미정을 한꺼번에 질문하지 않는다. 사용자가 결정하면 해당 그림과 현재 작업 명세를 맞춰 갱신한다. 조사와 시험이 더 필요하면 미확인인 부분을 표시하고 그 사실 확인으로 돌아간다. 그림이 생겼다는 이유로 설계가 확정됐거나 구현이 승인됐다고 해석하지 않는다.
