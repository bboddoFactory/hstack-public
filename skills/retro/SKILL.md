# 돌아보기

필요할 때 **현재 세션에서 사용자와 에이전트가 실제로 협업한 과정**을 돌아본다. 작업이나 세션이 끝날 때마다 실행하지 않아도 된다. 사용자 요청·응답·후속 반응과 실행 근거를 살펴보고 Hstack의 지침·단계·역할·설명·위임·검증·기록 방식을 어떻게 개선할지 제안한다.

Hstack 로그는 대화의 맥락과 관련 자료를 찾는 보조 근거다. 요약 로그나 현재 규칙 파일만으로 실제 대화와 행동을 판단하지 않는다. 다른 세션의 원문을 자동으로 모으거나 로그와 세션을 연결하는 체계는 이 스킬에서 만들지 않는다.

**승인받은 것만 고친다.** 공통 스킬과 지침은 여러 작업의 진행 방식에 영향을 주므로 메인이 혼자 고치지 않는다.

pstack의 `/reflect`에서 배운, 실제 경험에서 개선할 점을 찾고 승인한 변경을 반영하는 뼈대를 따른다.

## 흐름 한눈에

| 단계 | 하는 일 | 사용자 |
|---|---|---|
| 1 | 현재 세션에서 확인할 수 있는 대화와 실행 근거의 범위를 밝힌다 | |
| 2 | 실제 협업의 사례와 원인을 Hstack 지침에 비춰 살핀다 | |
| 3 | 근거·고칠 곳·변경 전후 문구와 이유를 보여 준다 | **멈춘다.** 사용자가 판단한다 |
| 4 | 승인받은 변경만 반영한다 | |
| 5 | 확인 범위·반영한 것·미룬 것과 다음에 확인할 효과를 남긴다 | |

## 1. 이번 세션의 근거를 읽는다

[프로젝트 기준 관리](../../docs/project-guidance.md)에 따라 관련 기준도 확인하고, 마무리에 그 문서의 Retro·Migrate 행을 확인한다.

[작업과 기록의 기준](../../docs/work-records.md)에 따라 현재 작업·관련 Hstack 로그와 자료의 위치를 확인한다. 제품 문서·보드는 작업의 목적과 범위를 이해하는 데 필요한 만큼 읽는다. 사용자 요청, 에이전트의 해석·응답, 후속 정정이나 동의, 실제 실행·검증·보고가 어떻게 이어졌는지 살핀다. 사용자가 이번 세션의 일부를 지정하면 그 범위를 따른다.

현재 접근할 수 있는 대화와 이미 확인한 실행 기록만 근거로 쓴다. 압축 전 대화의 요약과 실제 원문을 구분하고, 원문을 확인하지 못한 구간은 그대로 밝힌다. 보지 못한 대화를 복원해 인용하거나 요약만 읽고 전체 세션을 확인했다고 보고하지 않는다. 근거가 부족한 판단은 미확인으로 남긴다.

사례와 관련된 Hstack 지침을 읽되 현재 원본이 이 세션에서도 전달·적용됐다고 가정하지 않는다. 당시 적용한 지침을 확인할 수 있으면 구분한다. 같은 세션에서 이미 돌아본 범위와 남긴 제안이 있으면 재사용하고, 새로 드러난 사례·근거·미룬 내용에 집중한다. 다른 세션의 개선 제안을 현재 세션에서 재현한 사실로 세지 않는다.

## 2. 고른다

실제 협업에서 일하는 방식과 관련된 사례를 고른다.

| 고르는 것 | 예 |
|---|---|
| 사용자가 방식이나 답을 지적한 것 | 설명이 너무 길거나 확인 전에 진행한 경우 |
| 이해·설계·승인·위임의 흐름이 어긋난 것 | 방향에 동의한 것을 구현 승인으로 해석한 경우 |
| 검증·보고·기록이 실제 결과와 달랐던 것 | 실행하지 않은 확인을 완료라고 보고한 경우 |
| 지침이나 단계가 불필요한 부담을 만든 것 | 짧은 사실 확인에도 과한 위임 절차를 적용한 경우 |
| 실제로 도움이 된 방식 | 변경 후보를 비교해 사용자가 선택 이유를 이해한 경우 |

사례마다 사용자가 기대한 것과 실제 응답·행동·결과를 근거로 비교한다. 원인이 지침의 부족인지, 있는 지침을 따르지 않은 것인지, 도구·환경의 제약이나 정상적인 요구 변경 등 다른 원인인지 가른다. 원인을 모르면 모른다고 하며 모든 문제를 Hstack 규칙 추가로 해결하지 않는다. 제품의 버그 수정·코드 리뷰로 회고 범위를 넓히지 않는다.

발생 횟수·영향·재발 가능성과 근거를 함께 본다. 한 번 발생했다는 이유만으로 제외하지 않고, 작은 불편마다 공통 규칙을 늘리지 않는다. 반복 횟수를 확인하지 못했으면 숫자를 만들지 않는다. 도움이 된 방식도 모든 작업에 적용할 새 의무로 바로 바꾸지 않는다.

개선이 필요한 것만 **어디를 어떻게 고칠지**로 바꾼다. 어디에 적는지는 `/hstack:hstack-guide`를 따른다(어느 일에서나 지킬 것은 `basics.md`, 한 단계의 일은 그 스킬). 불필요한 단계·중복 지침을 줄이거나 없애는 것도 검토한다.

- 반복해서 규칙을 적어도 해결되지 않은 원인이 있으면 요청서·검사 도구 등 필요한 보완을 비교한다. 회고할 때마다 새 도구나 강제 단계를 추가하지 않는다.
- 이미 반영한 내용은 새 수정안으로 반복하지 않는다. 특정 프로젝트에서만 통하는 기준은 해당 프로젝트의 기록에서 다루고 공통 Hstack 규칙으로 확대하지 않는다.
- 고칠 것이 없으면 없다고 한다. 채우려고 지어내지 않는다.

## 3. 근거와 수정안을 보여 준다

중요한 개선안부터 사용자가 판단할 수 있게 설명한다.

- 실제로 어떤 요청·응답·행동이 있었으며 어떤 결과를 겪었는가.
- 확인한 근거와 원인, 아직 모르는 부분은 무엇인가.
- 어느 문서나 스킬을 어떻게 고칠 것인가. 변경 전후 문구를 그대로 보여 준다.
- 왜 그 수정이 필요한가. 다른 방법과 비교한 이유·부담·적용 범위는 무엇인가.

판단할 것이 많으면 한 번에 하나씩 설명한다. 제안을 승인된 결정으로 쓰거나 사용자가 설명을 이해했다는 답을 실행 승인으로 넓히지 않는다.

## 4. 승인한 변경을 반영한다

`/hstack:hstack-guide`의 "고칠 때 순서"에 따라 승인한 변경만 반영한다. 사용자가 버전·전역·설치본 갱신을 보류했다면 그 범위를 유지하고 적용 상태를 구분해 보고한다. 회고 제안만 요청받았으면 제안에서 끝낸다.

## 5. 확인 범위와 결과를 남긴다

- 이번 세션에서 확인한 대화·실행 근거의 범위와 접근하지 못한 부분, 제안·선택·반영한 변경·미룬 내용을 해당 Hstack 작업 폴더에 남기고 관련 자료를 연결한다. 대화나 세션을 식별할 근거가 없으면 식별자를 만들어 쓰지 않는다.
- 메인이 작업 파일의 현재 결과·미확인·남은 일을 맞추고 작업 로그에 회고 결과를 덧붙인다. 검토한 것과 실제 반영한 것을 구분한다. 기록의 위치·프로젝트 요약은 공통 작업 기록 기준을 따른다. 기존 보고와 로그 원문을 덮어쓰지 않는다.
- 회고를 했다는 이유로 원래 제품 작업의 상태를 완료로 바꾸지 않는다. 다른 세션의 미검토 기록까지 처리한 것으로 표시하지 않는다.
- `data/story-map/hstack/journal.md`에 겪은 일과 고친 이유.
- 다음 실사용에서 개선을 볼 장면을 짧게 남긴다. 실제 사례의 응답·산출물·행동으로 효과를 확인하며, 문구 반영이나 동기화 성공을 행동 개선의 증거로 삼지 않는다. 매번 자동 테스트·긴 강의·사용자 시험을 추가하지 않는다.

**여기서 스킬이 끝난다.**

## 원문에 접근할 수 없을 때

현재 대화 원문이나 압축 전 기록에 접근할 수 없는 범위는 그렇다고 밝힌다. 요약으로 대신 검증했다고 쓰지 않는다.
