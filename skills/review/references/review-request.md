# 통합 리뷰 요청서

[작업과 기록의 기준](../../../docs/work-records.md)에 따라 `tasks/<작업 이름>/리뷰-<호출 이름>-요청서.md`에 같은 요청서를 저장해 두 새 세션에 준다. 모델·강도·대체는 [최종 리뷰 역할표](../../../docs/agent-calls.md#작업-최종-리뷰)를 따른다. 보고는 같은 폴더의 `리뷰-<호출 이름>-1.md`, `리뷰-<호출 이름>-2.md`처럼 자리로 구분하고 메인의 정리도 같은 작업 폴더에 둔다. 실제 모델은 실행 정보와 보고에 남긴다. 실패·재시도 결과는 기존 성공 보고를 덮어쓰지 않는다.

```markdown
# 작업 최종 리뷰: <작업>

목적은 <사용자 목적과 이번 지원 범위>다. 동작·구조·설계·테스트와 실제 검증 근거의 맹점을 독립적으로 찾는다. 다른 검토자의 보고·메인의 선호 답을 보지 않고 추가 에이전트를 부르지 않는다. 검토와 재현을 하며 구현을 자동으로 고치지 않는다.

## 먼저 읽을 것
1. 제품 문서: <전체 경로>
2. 현재 작업과 최신 사용자 확인 완료 정의·변경 근거: <tasks/<작업 이름>/작업.md의 전체 경로와 해당 부분>
3. 현재 적용할 상세 문서·레이어 표·관련 설계·결정·구현 보고·기존 실행 근거: <작업 파일이 지정한 실제 경로와 해당 부분. 옛 핸드오프 문서는 당시 근거로 구분>
4. 원본 코드와 검토할 변경 범위·버전: <전체 경로와 기준 커밋·검토 커밋·허용한 미커밋 변경>
5. 팀 지침과 실행·테스트 방법: <실제 경로>. 화면이 바뀐 작업이면 시각 규칙(<DESIGN.md 전체 경로>)과 [기본 점검표](../../ui-design/references/floor-checklist.md)의 전체 경로도 주고, 점검표 항목과 "DESIGN.md에 없는 값이 끼지 않았나"를 실제 화면으로 본다
6. 개인 작업 기준: <Hstack의 project-guide.md 전체 경로와 관련 항목·조건. 없으면 부재와 대신 읽을 근거>

개인 기준과 작업 파일은 읽고 적용하며 낡음·충돌·미확인·갱신 제안은 자기 보고서에 남긴다. 작업 파일·기준 파일을 고치거나 프로젝트 지시 파일에 개인 규칙을 추가하지 않는다. 현재 합의와 상세 근거의 충돌은 임의로 선택하지 않고 메인에게 알린다. 과거 결정과 테스트를 정답으로 가정하지 않는다.

**원칙(들):** `/Users/<사용자>/workspace/hstack/basics.md`의 「pstack 원칙(들)」 표를 읽는다(실제 절대 경로로 적는다). 메인이 보기에 해당하는 원칙: <이름과 이번 일에서의 뜻>. 이것은 출발점이며 빠진 원칙을 더하거나 맞지 않는 것을 뺄 수 있다. 보고서에 적용한 원칙(들)과 그것이 바꾼 결정을 쓴다.

## 각자 작업 위치와 실행 권한
- 검토자 1: <분리된 작업 사본·시험 DB·결과 폴더·포트·보고 경로>
- 검토자 2: <분리된 작업 사본·시험 DB·결과 폴더·포트·보고 경로>
- 각자는 호출 때 지정한 자기 자리만 사용한다. 대상 버전과 사본의 일치 근거: <메인이 확인한 것>
- 허용한 시험 명령·도구·입력·계정·외부 호출과 총한도: <실제 승인 범위. 없으면 시험 데이터와 로컬 환경만>
- 실행 전 필요한 기존 준비와 재사용할 서버: <명령·실제 위치·건드리지 않을 서버와 포트>
- 쓰기 허용: <자기 재현 파일·임시 시험 데이터·실행 근거의 경로>. 보고 경로 밖에 근거를 만들면 메인이 지정 위치로 보존할 수 있게 위치를 적는다.
- 원본 구현·메인의 테스트·운영 데이터·다른 검토자의 공간을 바꾸지 않는다. 테스트를 약화하거나 문제를 자동 수정하지 않는다. 배포·커밋·결제 설정 변경은 하지 않는다.
- 설치·외부 전송·비용이 드는 호출은 위에 명시한 기존 승인 범위와 총한도 안에서만 한다. 명시되지 않은 활동은 실행하지 않고 필요한 이유와 확인할 범위를 보고한다.
- 안전하게 분리되지 않은 실행은 <메인이 지정한 순서·담당>만 한다. 재현할 수 없으면 접근·환경·권한 제약과 영향을 보고하며 성공·문제 없음으로 바꾸지 않는다.

## 검토 순서
1. 사용자 목적과 전체 흐름을 자기 말로 이해하고, 정상·실패·지연·재시도에서 약속을 깨는 상황을 찾는다. 이번 작업에서 실제로 겪은 일: <관련 장면>. 새 요구 제안과 약속 위반을 구분한다.
2. 그 가설을 코드·설계·테스트와 대조한다. 기존 테스트가 있다는 이유로 장면을 제외하지 않는다. 틀린 결과·누락·중복 효과를 검사하는지, 내부 구조만 바뀌어도 깨지는 검사는 아닌지 본다.
3. 레이어와 기존 코드의 연결, 책임·상태 소유·수명·데이터·실패 전달의 일관성을 본다. 따라갈 연결·숨은 상태·중복 판단과 현재 변경이 만든 불필요한 복잡함을 구체적으로 설명한다.
4. 이번 변경에 해당하는 보안·자료 보존·동시성·중단과 재시작·기존 호출자 호환·성능과 비용을 살핀다. 미래의 가상 요구와 취향으로 범위를 키우지 않는다. 수치를 주장하면 측정 대상·조건·반복과 편차·누락·캐시 등의 근거를 확인한다.
5. 허용한 환경에서 필요한 가설을 직접 재현한다. 명령·입력·환경과 버전·기대한 결과·실제 결과를 남긴다. 실행하지 못한 위험과 코드로 확인한 구체적인 모순을 구분한다. 재현하지 않았다는 이유로 중요한 구조 위험을 모두 버리지 않는다.

## 보고
<자기 보고 경로>에 쉬운 한국어로 쓴다. 발견이 없으면 없다고 하되 확인하지 못한 범위는 별도로 적는다. 개수를 채우거나 중요한 발견을 고정 개수 때문에 버리지 않는다.

각 발견에 다음을 적는다.
- 발생 조건과 사용자·호출자·운영자가 겪는 결과, 어긴 약속 또는 현재 구조의 구체적인 부담
- 근거 종류: 실행 확인 / 코드·설계의 구체적인 모순 / 미확인 위험 / 유효한 대안의 선택
- 실제 근거 위치, 실행했다면 정확한 명령·입력·예상과 실제 결과·산출물 위치
- 영향·확실성·미확인과 가장 작은 수정 방향. 같은 원인이라고 판단한 근거도 적는다.
- 지금 수정·추가 확인·후속 후보 중 권고와 이유. 중요한 방향을 사용자 대신 확정하지 않는다.

마지막에 실제 모델과 지정한 추론 강도, 검토한 코드 버전·범위·실행한 것과 안 한 것, 적용한 프로젝트 기준·충돌·갱신 제안(없으면 없음)을 남긴다. 실제 모델은 메인이 실행 메타데이터로 대조하며 자기 진술만으로 확인했다고 쓰지 않는다. 자신이 시작한 자원을 정리한 결과와 남길 근거를 적는다.
지정된 자기 보고와 허용한 근거만 직접 쓴다. 마지막 답은 보고 위치 한 줄이다.
```

메인은 두 보고의 근거·이견·미확인을 대조하고 필요한 명령과 실제 결과를 재확인한다. 보고의 일치를 동작 증명으로 대신하지 않는다. 모델을 부르는 실행 조건과 Fable 과금 조건은 위 역할표를 따른다.
