# 질문을 좁힌 추가 검토 요청서

기본 통합 리뷰 뒤 중요한 미확인·이견이 남거나 처음부터 범위가 너무 커 특정 질문을 따로 봐야 할 때만 쓴다. 기본 리뷰와 별개로 항상 두 명을 더 부르는 틀이 아니다.

[통합 요청서](review-request.md)의 현재 작업·적용할 상세 문서·담당 범위·각자 보고 경로와 분리된 실행 위치·권한·보고 항목을 그대로 재사용하고 아래 질문만 구체화한다. 새 요청·보고는 같은 `tasks/<작업 이름>/`에 호출별 다른 이름으로 두며 성공한 보고를 덮어쓰지 않는다. 모델·강도·실패 시 대체는 [최종 리뷰 역할표](../../../docs/agent-calls.md#작업-최종-리뷰)를 따른다.

```markdown
# 추가 독립 검토: <질문>

먼저 읽을 제품 문서: <전체 경로>
현재 작업과 적용할 상세 문서: <작업.md 전체 경로와 지정된 문서·해당 부분>
같은 질문의 두 새 세션에 동일하게 주는 기존 통합 요청서: <전체 경로>
이번 질문에 필요한 기존 요구·설계·테스트·실행 근거: <실제 경로와 해당 부분>

- 지금 답할 질문과 중요한 이유: <한정된 질문>
- 실제로 확인한 사실과 아직 모르는 것: <구분>
- 현재 지원 범위와 지킬 약속: <해당 부분>
- 이번에 더 읽거나 실행할 범위·허용 명령·데이터·한도: <기존 권한에서 필요한 부분만>
- 각자의 분리된 작업·재현 근거·보고 위치: <자리별 경로와 환경>

원본 코드·운영 데이터·기존 테스트·작업 파일·개인 기준을 고치거나 새 기능을 구현하지 않는다. 현재 합의와 상세 근거의 충돌은 메인에게 알린다. 다른 검토자의 보고를 보지 않고 독립적으로 판단한다. 허용 범위에서 직접 재현할 수 있으며 불가능하면 이유와 필요한 확인을 남긴다. 실행한 실패·정적 모순·미확인 위험을 구분하고 기존 보고의 결론을 사실로 반복하지 않는다.

**원칙(들):** `/Users/<사용자>/workspace/hstack/basics.md`의 「pstack 원칙(들)」 표를 읽는다(실제 절대 경로로 적는다). 메인이 보기에 해당하는 원칙: <이름과 이번 일에서의 뜻>. 이것은 출발점이며 빠진 원칙을 더하거나 맞지 않는 것을 뺄 수 있다. 보고서에 적용한 원칙(들)과 그것이 바꾼 결정을 쓴다.

질문의 답·핵심 근거·가장 작은 수정 방향·남은 조건과 적용 기준·갱신 제안(없으면 없음)을 기존 통합 요청서의 보고 형식에 맞춰 남긴다. 사용자 판단이나 구현을 대신하지 않는다.
```

추가 검토 결과도 메인이 대조한 뒤 기존 리뷰 결과와 수정 레이어에 연결한다. 기존 검증을 이유 없이 전부 반복하지 않는다.
