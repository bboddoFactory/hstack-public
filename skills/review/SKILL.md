# 작업 통합 리뷰

리뷰는 작업의 목적과 현재 지원 범위에 비춰 완성된 결과물·연결된 코드·설계·시나리오·테스트와 검증 근거를 새 관점에서 살피고, 고칠 문제와 남은 질문을 판단하는 과정이다. 레이어에서 확인한 것을 재사용하되 원래 설계와 검사가 옳다고 가정하지 않는다. 새 요구 제안과 기존 약속 위반은 구분한다.

| 살필 대상 | 묻는 것 |
|---|---|
| 사용자 동작 | 정상·실패·지연·재시도와 전체 흐름에서 약속을 지키는가? |
| 구조와 연결 | 책임·상태 소유·수명·데이터·외부 약속이 일관적인가? 변경과 이해의 부담이 불필요하게 커졌는가? |
| 설계·시나리오·테스트 | 처음 정한 기준에 잘못된 전제와 빠진 조건은 없는가? 테스트가 실제 약속을 확인하는가? |
| 검증 근거 | 어떤 환경과 버전에서 무엇을 실제로 확인했고 무엇이 미확인인가? |

같은 통합 요청서를 두 새 세션에 준다. 각자 사용자 흐름과 코드·구조·테스트를 모두 살피며 다른 보고를 보지 않는다. 모델·강도·실패 시 대체는 [최종 리뷰 역할표](../../docs/agent-calls.md#작업-최종-리뷰) 한 곳에서 정한다. 메인 자신의 의견은 독립 검토로 세지 않는다.

구현 작업의 마지막 통합 검토·수정 레이어·완료 확인을 맡는다. 원인 조사로 끝나는 작업에 구현과 이 통합 리뷰 전체를 형식적으로 강제하지 않는다. [공통 작은 수정 기준과 절차](../../how-we-work.md#일을-시작할-때-묻는-것)를 끝까지 만족해 그 절차로 마무리하는 작업에도 이 통합 리뷰를 필수로 덧붙이지 않는다. 이 스킬로 통합 리뷰를 진행하는 경우의 두 독립 검토 기준은 유지한다.

답의 내용·그림체 등 별도 품질 평가의 기준·도구를 이 절차에서 자동으로 새로 만들지는 않는다. 완료 정의에 포함된 품질 약속은 무시하지 않고 기존 확인 근거와 평가의 한계를 밝힌다. 미정인 평가 방법은 필요한 질문으로 남긴다.

## 들어오는 것

- 제품 문서와 [작업과 기록의 기준](../../docs/work-records.md)에 따라 보드에서 찾은 `tasks/<작업 이름>/작업.md`의 현재 완료 기준·채택 결정·남은 일·지정된 상세 문서.
- 같은 작업 폴더의 레이어 표·관련 설계·결정·구현 보고·실제 검증 근거. 기존 핸드오프 문서와 단계별 폴더의 자료는 당시 근거로 실제 경로를 연결하며 옮기지 않는다.
- 대상 코드와 이번 변경 범위·기준 버전. 기존 코드와 연결된 부분도 필요한 만큼 본다.
- [프로젝트 기준 관리](../../docs/project-guidance.md)에 따른 개인 기준·기존 팀 지침과 적용 항목. 기준 자체의 낡음·충돌도 검토한다.

## 흐름 한눈에

| 단계 | 누가 | 하는 일 | 사용자 |
|---|---|---|---|
| 1 | 메인·두 독립 검토자 | 범위와 실행 조건을 정하고 같은 요청서로 각각 검토·재현 | 그동안 직접 써 볼 수 있다 |
| 2 | 메인 | 근거·이견·미확인을 대조하고 필요한 결과를 직접 재확인 | |
| 3 | 메인 | 지금 고칠 것·추가 확인·후속 후보와 이유를 설명 | 중요한 범위와 방향을 정한다 |
| 4 | 메인·구현자 | 리뷰 레이어로 나눠 Layer 절차로 수정·검증 | 레이어 표와 결과를 확인한다 |
| 5 | 메인 | 최신 완료 정의와 지적 해결·연관 동작을 확인 | 미룬 확인을 다시 정한다 |
| 6 | 메인 | 정한 방식으로 배포하고 기록을 닫는다 | 배포한 곳에서 확인한다 |

## 1. 같은 범위로 독립 검토한다

메인이 [통합 리뷰 요청서](references/review-request.md)를 같은 작업 폴더에 쓴다. 요청서·두 보고·메인의 정리는 서로 이름을 달리하며 반복 호출에서도 성공한 보고를 덮어쓰지 않는다. 현재 작업·적용 자료와 해당 부분·담당 범위·각자 보고 경로, 목적·지원 범위·최신 완료 기준·확정 결정과 변경 가능한 전제·실제 검증 범위·개인 기준을 두 검토자에게 동일하게 전달한다. 과거 보고의 결론을 정답으로 주입하지 않는다. 이번 작업에서 겪은 실패나 지연은 의심할 실제 장면으로 연결한다.

검토할 코드 버전과 승인한 미커밋 변경을 명시한다. 원래 작업 폴더와 사용자 변경을 보존하고, 재현에 필요한 변경 사본은 각자의 작업 공간에 준비한다. 기존 정상 동작과 이번 변경의 문제를 구분한다.

### 검토자의 직접 실행 범위

검토자는 코드·운영 기록을 읽고, 요청서에 정한 개발·시험 환경에서 테스트·실행·재현 코드 작성을 할 수 있다. 메인은 허용한 실행 명령·데이터·계정·포트·도구와 결과 위치를 먼저 적는다. 필요한 기존 도구와 실행 방법을 재사용하며 실행할 수 없는 부분은 미확인으로 남긴다.

- 각 검토자가 쓰는 작업 폴더·시험 DB·결과 파일·필요한 포트를 분리한다. 안전하게 분리할 수 없는 실행은 메인이 한 번에 하나씩 배정한다. 동시 실행 때문에 생긴 실패를 제품 결함으로 오인하지 않는다.
- 재현 파일과 실행 결과는 지정 범위에만 쓴다. 원본 구현·메인의 테스트·작업 파일·개인 기준은 바꾸지 않고 자동 수정·커밋·배포하지 않는다. 현재 합의와 상세 근거가 충돌하면 임의로 선택하지 않고 메인에게 알린다.
- 실제 데이터 변경·외부 전송·설치·비용을 발생시키는 호출은 기존 승인 범위 안에서만 한다. 허용하지 않은 부작용이 필요한 재현은 실행하지 말고 이유와 필요한 확인을 보고한다.
- 허용한 서버만 시작·종료하고 기존 서버는 건드리지 않는다. 끝나면 자신이 시작한 자원만 정리하고 보존할 근거를 보고한다.

재현 명령·입력·기대한 결과·실제 결과·환경과 버전을 남긴다. 실행했다고만 적거나 오래된 화면·대체 환경의 결과를 실제 사용 검증으로 바꾸어 쓰지 않는다.

### 관점과 원칙을 연결한다

사용자 목적에서 실패 가설을 세우고 코드·설계·테스트로 대조한 뒤 구조의 부담을 살핀다. 원칙(들)은 [basics의 「pstack 원칙(들)」](../../basics.md#pstack-원칙들) 표에서 이번 변경에 맞는 것을 고르고, 리뷰어에게도 요청서로 같은 표를 읽게 한다.

보안·데이터 보존·동시성·실패와 재시작·기존 호출자 호환은 이번 변경과 약속에 따라 깊게 본다. 취향이나 미래의 가상 요구로 범위를 키우지 않는다. 현재 구조에서 구체적으로 줄일 부담과 수정 방향을 제안하며, 이름·줄 수·클래스 수만으로 구조를 평가하지 않는다.

## 2. 메인이 근거를 대조한다

두 보고가 같아도 같은 전제를 잘못 믿었을 수 있다. 중요한 코드 연결을 직접 읽고 실행 명령과 증거를 필요한 만큼 재확인한다. 같은 원인의 지적은 근거를 확인해 묶고 서로 다른 전제는 남긴다.

근거는 [공통 근거 구분표](../../how-we-work.md#설계-검토-지적을-처리하는-기준)를 참조해 실행으로 확인한 실패·구체적인 모순·미확인 위험·유효한 대안의 선택으로 구분한다. 실행하지 못한 위험을 확인된 결함으로 쓰지 않고, 정적 모순과 중요한 구조·보안 위험을 실행하지 못했다는 이유만으로 모두 버리지도 않는다. 실패한 호출이나 미완성 보고는 두 완료 보고에 넣지 않는다.

범위가 너무 넓거나 중요한 미확인이 남으면 질문을 좁혀 [추가 검토 요청서](references/attack-request.md)를 필요한 경우에만 쓴다. 기존 근거를 재사용하고 해당 질문에도 독립 비교를 유지한다. 모든 수정 뒤에 전체 리뷰를 반복하지 않는다.

## 3. 고칠 대상과 방향을 함께 정한다

동작·구조·테스트·보안·성능·운영 등의 해당 항목에서 다음을 구분해 보여 준다.

- **지금 고칠 것:** 현재 약속 위반·자료 보존과 보안 문제·확인한다고 한 것을 확인하지 못하는 검사·현재 변경이 만든 불필요한 복잡함. 발생 조건과 영향·근거·가장 작은 수정 방향을 설명한다.
- **추가 확인:** 결함인지 판단할 중요한 근거가 부족한 것. 무엇을 확인하면 판단이 달라지는지 적는다.
- **후속 후보:** 현재 약속을 깨지 않는 후속 개선. 실제로 꺼낼 조건과 관련 후보에 연결한다. 미래 기능의 틀을 미리 만들지 않는다.

사용자는 중요한 수정 범위·방향과 감수할 비용을 정한다. 사용자에게 보이지 않는 작은 내부 정리는 공통 지침대로 메인이 거르고 설명한다. 보고 수·지적 수를 채우거나 검토자가 자동으로 수정하지 않는다. 구조와 변경 흐름을 함께 이해할 때는 [브라우저 설명 스킬](../browser-explain/SKILL.md)을 사용해 기존 설명 자료를 활용한다.

## 4. 리뷰 레이어로 수정한다

[공통 분할 기준](../../how-we-work.md#레이어를-나누는-공통-기준)과 [표 틀](../prepare/references/layer-table.md)을 재사용해 기존 레이어 표에 `리뷰-1`, `리뷰-2`로 잇는다. 같은 원인의 수정은 묶고 한 번에 이해·확인하기 어려우면 나눈다. Prepare 전체를 다시 실행하지 않는다.

확정 결정의 전제가 유지되면 재사용한다. 중요한 책임·상태·외부 약속 변경은 필요한 Understand·Design으로 판단하고, 세부 방법은 해당 레이어에서 구체화한다. 사용자와 표를 확인한 뒤 [Layer](../layer/SKILL.md)로 명세·구성·검증 계획 확인 → 메인 테스트 → 구현 위임 → 동작·구성 대조 → 올리기·사용자 확인을 진행한다.

리팩토링은 유지할 동작을 먼저 고정하고 내부를 바꿔도 같은 결과인지 확인한다. 실제 버그를 고칠 때는 바뀌어야 할 동작을 명시한다. 기존 행동 검증을 줄이지 않고 필요한 테스트 변경은 메인이 판단한다. 동작 수정과 구조 수정은 구분해 커밋한다.

수정 뒤에는 해당 지적이 해결됐는지와 연관 동작·검증 근거가 여전히 유효한지 확인한다. 수정으로 새 중요한 위험이 생기거나 근거가 무효해지면 그 범위만 추가 검토한다.

## 5. 최신 완료 정의를 확인한다

작업 파일의 최신 사용자 확인 완료 정의마다 누가 어떤 환경과 버전에서 무엇으로 확인했는지 적는다. 레이어에서 미룬 확인도 다시 꺼낸다. 돌려 보지 않은 것을 통과로 쓰지 않는다. 완료 기준이 남았으면 완료로 쓰지 않는다. 사용자가 미확인을 남겨 둔 채 종료하기로 하면 이유·남은 조건·미해결 결과와 영향을 보존하고 성공 완료와 구분한다.

닫기 전에 [프로젝트 기준 관리](../../docs/project-guidance.md)의 Review 행을 확인한다.

## 6. 배포하고 닫는다

프로젝트에서 정한 방식과 승인 범위에 따라 작업의 묶음을 배포한다. 레이어마다 운영에 배포하지 않았으므로 배포한 곳에서 사용자와 결과를 확인한다.

메인은 결과·미확인·근거·수용한 비용·후속 후보를 작업 파일에 먼저 남기고 보드 카드 하나의 상태를 맞춘다. 완료 기준을 충족하면 `done`(완료), 더 하지 않기로 정했으면 이유·미해결 결과를 보존하고 `cancelled`(취소)로 표시한다. 확인이 남아 계속할 작업은 `doing`(진행 중)으로 둔다. 상태의 원본은 보드이며 작업 파일·레이어 표에 별도의 작업 상태를 만들지 않는다. 레이어별 진행·수정 커밋·배포 표시를 맞추고 상세 경과는 작업 로그에 남긴다.

작업을 마무리하면 공통 작업 기록 기준에 따라 프로젝트 로그에 결과·확인 범위·제한과 작업 파일·작업 로그 연결을 목록 항목 하나로 남긴다. 제품 문서·가이드는 확정한 공통 사실과 기준의 해당 부분만 갱신한다. 다른 작업과 세션의 변경은 보존한다. 시험 폴더와 서버를 지울지는 기존 권한과 사용자 확인을 따른다.
