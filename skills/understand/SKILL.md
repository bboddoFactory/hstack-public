# 현재 구조 이해

이번 질문에 필요한 현재 구조와 확인 가능한 배경을 조사하고 사용자와 함께 이해한다. 기존 코드가 있다는 이유로 그 구조가 새 요구에도 적합하다고 가정하지 않는다. 제품 코드는 바꾸지 않는다.

## 질문과 조사 범위를 잡는다

[프로젝트 기준 관리](../../docs/project-guidance.md)에 따라 관련 기준을 읽고 조사 요청서에도 전달하며, 마무리에 그 문서의 Understand 행을 확인한다.

공통 프로젝트 시작 절차와 [작업과 기록의 기준](../../docs/work-records.md)에 따라 제품 문서·프로젝트 요약·보드에서 찾은 현재 작업 파일·작업 로그와 지정된 상세 문서를 읽는다. 궁금한 동작과 왜 지금 알아야 하는지에서 질문을 정한다. 대상 위치를 모르면 사용자 동작·화면·요청·명령의 입구에서 관련 부분을 찾는다. 전체 저장소를 기본 범위로 삼지 않는다. 단순 질문마다 작업 기록을 강제하지 않는다.

기존 이해 기록이 있으면 질문·대상 코드·관련 변경이 지금도 맞는지 확인해 재사용한다. 달라진 부분과 부족한 근거만 갱신한다. 탐색 전 브리핑은 `basics.md`를 따른다.

## 현재 동작과 필요한 이유를 확인한다

관련 코드·문서·타입·테스트와 필요한 실행 결과를 확인한다. 질문에 맞는 조사 관점은 [상황별 관찰 질문](references/observation-questions.md)의 해당 부분만 읽는다. 원칙의 이름·짧은 뜻과 이번에 확인할 행동을 연결한다. 단순 사실 확인에 불필요한 절차나 원칙을 붙이지 않는다.

직접 조사와 위임, 조사 등급·모델·두 독립 보고의 확보는 [역할표](../../docs/agent-calls.md)를 따른다. 넓은 조사를 위임해도 메인이 핵심 근거를 확인하고 설명할 책임은 남는다. 보고의 일치는 실제 동작 검증이 아니다.

사실 조사를 위임할 때는 [탐색 요청서](references/explore-request.md)를 질문에 맞춰 쓴다. 사실 조사마다 설계 권고를 함께 요청하지 않는다.

왜 그렇게 만들었는지가 중요하면 관련 문서·주석·변경 이력에서 시작해 필요한 자료로 넓힌다. 확인한 당시 이유와 현재 코드에서 추론한 가능성, 아직 모르는 이유를 구분한다. 매번 전체 이력을 훑거나 이유를 지어내지 않는다.

돌려 봐야 알 수 있는 질문은 [실험 요청서](references/experiment-request.md)로 작게 확인한다. 기존 권한·외부 호출·비용의 승인 범위를 따르며 실행한 범위와 남은 조건을 적는다. 실험 실행 담당과 독립적으로 조사·해석하는 역할을 구분하고 위임 조사는 공통 역할표를 따른다. 두 조사자가 있다는 이유로 외부 호출을 자동으로 두 번 실행하거나 승인된 총횟수를 늘리지 않는다. 결과만 검토했다면 직접 실행한 것으로 쓰지 않는다. 테스트가 있는 것, 읽은 것, 실제 실행한 것을 구분한다.

## 설명하며 설계 질문을 연결한다

질문의 답을 실제 코드의 이름과 업계 용어로 설명하고 처음 나오는 용어에는 짧은 뜻을 붙인다. 그다음 필요한 책임·흐름·근거를 보여 준다. 파일과 함수 목록을 답으로 대신하지 않는다. 코드에 이미 쓰인 패턴이 있으면 이름과 그 패턴이 푸는 문제, 코드가 그 패턴에서 벗어난 곳을 함께 말한다. 관계와 흐름을 함께 살펴볼 때는 메인이 [브라우저 설명 스킬](../browser-explain/SKILL.md)을 사용해 자료를 만들고 그림을 짚으며 설명한다.

이해 중에 ‘그러면 이렇게 바꿔야 하지 않나’라는 설계 질문이나 후보가 나오면 자연스럽게 논의한다. 현재 사실·추론·후보·선택은 구분한다. 변경 방향을 비교·권고·선택할 필요가 생기면 [변경 설계](../design/SKILL.md)의 해당 과정을 활용하고, 추가 사실이 필요하면 다시 이 과정으로 돌아온다. 형식적인 단계 전환이나 새 승인 자리를 늘리지 않는다.

아이디어가 나왔다는 이유로 새 구조를 채택하거나 구현을 시작하지 않는다. 사용자에게 다시 설명해 보라고 시험하지 않는다.

## 남기고 끝낸다

새 요청서·독립 보고·실험 근거와 `탐색-정리.md`·설명 자료는 `tasks/<작업 이름>/`에 이름을 달리해 둔다. `탐색-정리.md`에는 질문·범위·확인 날짜와 코드 상태·핵심 설명·근거·미확인·이어갈 질문을 남긴다. HTML의 내용은 브라우저 설명 스킬을 따른다. 반복 호출은 성공한 보고를 덮어쓰지 않도록 다른 이름을 지정한다. 기존 `understandings/<에픽 또는 주제>/` 자료는 당시 근거로 연결하고 옮기거나 덮어쓰지 않는다.

메인은 확인 결과가 현재 합의를 바꾸면 작업 파일의 명세·채택 결정·현재 적용할 상세 문서와 남은 일을 맞추고 보드 상태를 갱신한다. 보고와 작업 파일이 충돌하면 메인이 해소하며 하위 에이전트는 자기 보고만 쓴다. 위임에는 현재 작업·적용 자료·담당 범위·자기 보고 경로를 전달한다. 상세한 원본 분담은 공통 기록 기준을 따른다.

현재 질문에 답했고 남은 미확인과 다음 판단의 질문이 드러났으면 끝낸다. 배경 조사·실험·위임 비교는 필요할 때 수행하며 모든 질문에 같은 규모로 강제하지 않는다. 레이어 분할이나 구현으로 자동 진행하지 않는다.
