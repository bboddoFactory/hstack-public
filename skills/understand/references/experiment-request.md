# 실험 요청서 틀

읽어서는 알 수 없고 돌려 봐야 아는 것을 알아낼 때 쓴다. 실행할 질문·대상·총 외부 호출 횟수·비용·허용 범위를 먼저 정한다. 기존 승인 범위 밖이면 시작 전에 확인한다. 실행 담당과 독립 조사·해석은 구분하고 [공통 역할표](../../../docs/agent-calls.md)를 따른다. 두 조사자에게 같은 요청서를 주더라도 외부 실행은 사전에 정한 담당과 총한도 안에서만 한다. 같은 실행 근거를 읽어 검토했다면 독립 재실행이나 별도 실험 증거가 생긴 것으로 세지 않는다. 독립 판단에 추가 실행이 필요하면 그 필요와 한도를 먼저 확인한다.

요청·보고·실행 근거는 [작업과 기록의 기준](../../../docs/work-records.md)에 따라 `tasks/<작업 이름>/`에 실험·호출마다 다른 이름으로 둔다. 기존 자료는 실제 경로로 연결한다.

```markdown
너는 아래에 지정한 역할로 기술 질문을 확인한다. 실행 담당은 허용한 작은 실험을 직접 돌리고, 독립 검토자는 그 실행 근거를 읽어 판단한다. 기억이나 설명서만으로 실행 결과를 지어내지 않는다. 직접 실행한 것과 다른 담당의 실행을 검토한 것을 구분한다.

## 맥락 (먼저 읽는다)

- 제품 문서: <전체 경로>
- 현재 작업·질문: <tasks/<작업 이름>/작업.md의 전체 경로>
- 현재 적용할 상세 문서와 해당 부분·관련 근거: <작업 파일이 지정한 실제 경로>
- 대상과 이번 담당 범위: <프로젝트 경로>
- 지금 상태: <탐색에서 확인된 것 중 이 실험에 필요한 것 몇 줄>
- 개인 작업 기준: <Hstack의 project-guide.md 전체 경로와 관련 항목·적용 범위. 없으면 부재와 대신 읽을 근거>. 관련 팀 지침: <실제 경로>

기준과 작업 파일은 읽기만 하고 적용한 항목·충돌·미확인·갱신 제안(없으면 없음)을 자기 보고서에 남긴다. 접근 불가도 보고하며 개인 안내나 프로젝트 지침은 고치지 않는다. 현재 합의와 상세 근거가 충돌하면 임의로 선택하지 않고 메인에게 알린다.

**원칙(들):** `/Users/<사용자>/workspace/hstack/basics.md`의 「pstack 원칙(들)」 표를 읽는다(실제 절대 경로로 적는다). 메인이 보기에 해당하는 원칙: <이름과 이번 일에서의 뜻>. 이것은 출발점이며 빠진 원칙을 더하거나 맞지 않는 것을 뺄 수 있다. 보고서에 적용한 원칙(들)과 그것이 바꾼 결정을 쓴다.

## 알아낼 것 (돌려서)

1. <질문. 무엇을 바꿔 가며 불러 볼지까지>
2. …

수치를 비교·선택의 근거로 쓰는 실험이면 실행 전에 어떤 결과가 결정을 바꿀지와 비교 조건을 정한다. 실행과 보고에서는 다음을 확인한다.

- 같은 입력·조건에서 실제로 어떤 일을 수행했는지와 실패·누락·캐시로 생긴 차이를 구분한다.
- 반복 횟수와 측정마다 결과가 얼마나 달랐는지 남긴다. 차이가 반복 측정의 흔들림보다 작으면 개선으로 단정하지 않는다.
- 성능 개선을 주장하면 무엇이 속도를 제한했는지 실행 중 계측·프로파일 등의 근거로 설명한다. 확인하지 못하면 미확인으로 표시하고 결론의 범위를 제한한다.
- 기존 외부 호출·비용·시간 한도 안에서 확인한다. 근거가 부족해도 자동으로 한도를 늘리거나 추가 실행하지 않는다. 수치 판단을 하지 않는 기술 확인에 이 측정 절차를 강제하지 않는다.

## 돌리는 법

- 실행 담당만 새 폴더 `<프로젝트 안의 따로 둔 폴더. 프로젝트의 의존성을 써야 할 때만 안에, 아니면 밖에>`에 만든다. 버릴 것이다. 커밋하지 않고 git에 추가하지 않는다. 기존 파일을 고치지 않는다. 보고서와 실행 근거는 아래 사전 지정 위치에만 남긴다. 의존성을 설치하거나 더하지 않는다. 설치 없이는 안 되면 멈추고 그렇다고 보고한다.
- 돌릴 때마다 받은 것 전체를 `<같은 작업 폴더의 지정 파일 경로>`에 남긴다. 설정과 호출이 이름에 드러나게 한다. 실행마다의 설정과 결과를 모은 요약 파일도 같은 작업 폴더에 둔다. 처음부터 단계별 하위 폴더를 만들지 않는다.
- 진짜 바깥 호출은 <횟수> 안쪽으로 한다. 호출마다 제한 시간을 둔다.
- 이번 세션의 역할: <실행 담당 / 기존 실행 근거의 독립 검토>. 실행 담당만 위 한도 안에서 외부를 호출한다. 검토 담당은 실제 실행 근거를 읽고 실행하지 않은 범위를 분명히 적는다.
- 바깥 계정에 닿는 도구는 읽기만 하는 것 하나로만 시험한다. 보내기, 만들기, 지우기, 고치기는 어떤 것도 부르지 않는다. 읽기만으로 시험할 수 없으면 시험하지 않고 그렇다고 적는다.
- <건드리면 안 되는 포트, 서버, 설정>

## 보고 (한국어)

지정된 `<tasks/<작업 이름>/실험-<무엇>-<호출 이름>-보고-<번호>.md의 전체 경로>`에 보고를 직접 쓴다. 실행 담당은 설정·결과 요약과 날것의 기록도 같은 작업 폴더의 사전에 지정한 서로 다른 파일에 남긴다. 독립 검토자는 그 근거를 수정하지 않는다. 실행 여부·담당·실제 모델·실행 범위와 남은 조건을 구분한다. 기존 성공 보고를 덮어쓰지 않는다.

짧게 쓴다. 질문마다 세 줄 안쪽의 답과, 근거가 되는 결과 파일의 경로. 그다음:
- 모든 실행의 표: 설정 → 일어난 일 → 결과.
- 수치로 비교·판단했다면 위 조건을 확인한 근거와 남은 미확인.
- "예상과 달랐던 것"
- "확인하지 못한 것"
- 만든 폴더의 경로.

사실만 적는다. 앱을 어떻게 설계할지는 권하지 않는다.
```

## 받은 뒤

메인은 보고 파일을 읽되 그대로 옮기지 않는다. 남은 요약 파일과 결과 파일에서 핵심 몇 가지를 직접 세어 보고와 맞는지 본다. 앱의 기존 파일이 안 바뀌었는지도 `git status`로 본다.
