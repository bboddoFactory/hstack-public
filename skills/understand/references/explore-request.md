# 현재 상태 탐색 요청서 틀

질문에 필요한 사실 조사를 위임할 때 쓴다. [작업과 기록의 기준](../../../docs/work-records.md)에 따라 `tasks/<작업 이름>/탐색-<호출 이름>-요청서.md`에 저장하고 [공통 호출](../../../docs/agent-calls.md)에 따라 같은 요청서를 최소 두 새 세션에 준다. 조사자는 지정 보고서에 직접 쓴다. 새 보고서는 `탐색-<호출 이름>-보고-1.md`, `탐색-<호출 이름>-보고-2.md`로 두며 실제 모델·강도·호출 결과를 함께 남긴다. 기존 성공 보고는 덮어쓰거나 이름을 바꾸지 않는다.

```markdown
너는 아래 질문에 필요한 현재 동작과 확인 가능한 배경을 조사한다. 제품 코드·운영 기록을 수정하지 않고 설치·커밋·서버 시작과 종료를 하지 않는다. 지정 보고서 파일 하나만 직접 쓴다. 다른 조사자나 보고서는 보지 않는다.

## 먼저 읽을 것
1. 제품 문서: <전체 경로>
2. 현재 작업: <tasks/<작업 이름>/작업.md의 전체 경로와 현재 질문·필요 배경>
3. 현재 적용할 상세 문서와 해당 부분·관련 근거: <작업 파일이 지정한 실제 경로. 기존 핸드오프 문서 등은 당시 근거로 구분>
4. 개인 작업 기준: <Hstack의 project-guide.md 전체 경로와 관련 항목·적용 범위. 없으면 부재와 대신 읽을 근거>. 관련 팀 지침: <실제 경로>

기준과 작업 파일은 읽기만 한다. 적용한 항목·충돌·미확인·갱신 제안(없으면 없음)을 자기 보고서에 남기며 접근 불가도 보고한다. 현재 합의와 상세 근거가 충돌하면 임의로 선택하지 않고 메인에게 알린다. 관찰한 관행을 확정 규칙으로 바꾸거나 프로젝트 안에 개인 지침을 추가하지 않는다.

**원칙(들):** `/Users/<사용자>/workspace/hstack/basics.md`의 「pstack 원칙(들)」 표를 읽는다(실제 절대 경로로 적는다). 메인이 보기에 해당하는 원칙: <이름과 이번 일에서의 뜻>. 이것은 출발점이며 빠진 원칙을 더하거나 맞지 않는 것을 뺄 수 있다. 보고서에 적용한 원칙(들)과 그것이 바꾼 결정을 쓴다.

## 대상과 질문
대상과 이번 담당 범위: <프로젝트와 관련 범위의 전체 경로>
확인할 질문: <질문 목록. 모든 코드의 조사를 기본값으로 삼지 않는다>

해당하는 관점만 다룬다.
- 기존 코드: 지금 무엇이 어디에 있고 어떻게 돌아가며 무엇이 기대는가?
- 외부 경계: 무엇을 받고 무엇을 돌려주는가? 실제 형식과 조건은 무엇인가?
- 선택 배경: 확인한 문서·변경 이력의 당시 이유는 무엇인가? 현재 추론과 구분한다.
- 실행이 필요한 질문: 읽기로 답할 수 없으면 필요한 실험과 미확인을 적는다. 허용하지 않은 실행을 시작하지 않는다.

현재 사실의 답에 새 설계 권고를 섞지 않는다. 구조 변경을 판단해야 하는 질문은 별도로 식별하고 그 판단에 필요한 근거를 남긴다.

## 보고
한국어로 질문의 답을 먼저 설명하고 확인할 수 있는 파일·줄·함수·문서·실행 근거를 연결한다. 코드 읽기와 실제 실행 결과를 구분한다. 시간 순서가 중요하면 순서 그림을 붙인다. 끝에 미확인·이견 가능성·다음 질문을 적는다. 짐작을 확인 사실로 쓰지 않는다.

보고서 위치: <두 보고서의 전체 경로. 각자 자기 파일만 다룬다>
```

메인은 두 보고의 근거·이견·미확인을 대조해 기존 탐색 정리에 연결한다. 변경 방향을 고를 필요가 생기면 [Design](../../design/SKILL.md)의 해당 과정을 활용한다. 사실 보고를 설계 후보·적대 검토의 완료 근거로 세지 않는다.
