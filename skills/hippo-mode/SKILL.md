# 히포 모드

요청의 목적과 사용자가 확인할 결과를 기준으로 작업을 정리하는 Hstack의 입구다. 기존 작업의 연속이면 같은 작업에서 이어 가고, 새로운 독립 결과이면 작업을 나눌지 판단한다. 조사만 합의한 요청을 구현까지 자동 진행하지 않으며 짧은 일반 질문마다 기록을 만들지 않는다.

스토리맵은 사용자 행동별로 작업을 보는 보드의 이름이다. 카드 하나가 작업 하나이며 가로는 사용자가 하는 행동, 세로는 후보·진행 중·완료·취소다. 후보를 고르면 같은 작업을 구체화하고 별도 에픽을 만들지 않는다. 이 스킬은 목적·범위·현재 기록과 보드를 관리하며 이해·설계·구현·검증은 필요한 스킬로 연결한다. 이미 작업과 목적이 분명하면 해당 스킬에서 바로 이어 갈 수 있다.

## 시작할 때

[작업 기록 기준](../../docs/work-records.md)과 [프로젝트 기준 관리](../../docs/project-guidance.md)를 따른다. 제품 문서·프로젝트 요약·보드와 현재 작업 파일·작업 로그 끝부분을 읽고 목적과 실제 기록 경로를 확인한다. 기록이 없으면 아래 기준으로 시작한다. 짧은 일반 질문마다 새 보드나 빈 기록을 만들지 않는다.

- **프로젝트는 제품이나 저장소 하나다.** 모노레포처럼 여러 부분(예: core, ide, cli, desktop)이 한 제품이면 프로젝트는 그 제품 하나다. 지금 손대는 부분을 프로젝트 이름으로 삼지 않고, 작업 이름 앞에 영역으로 붙인다(예: `web-장바구니-쿠폰적용`). 제품 문서에는 제품 전체가 아니라 이 저장소에서 맡는 범위만 적어도 된다. 말의 뜻은 [용어집](../../docs/terms.md)에 있다.
- **프로젝트 기록을 처음 만들 때는 그때의 hstack 버전을 프로젝트 폴더의 `hstack-version`(한 줄, 예: `0.6.0`)에 적는다.** 값은 `.claude-plugin/plugin.json`의 `version`이다. 규칙이 바뀐 뒤 `/hstack:migrate`가 이 파일로 시작 버전을 안다. 이미 있는 프로젝트에 파일이 없으면 `/hstack:migrate`가 만든다.
- **프로젝트 자체가 아직 없으면:** 현재 폴더를 새 프로젝트라고 가정하지 않는다. 사용자와 무엇을 하려는지, 왜 필요한지, 처음 어디까지 해볼지를 하나씩 이야기한다. 기록에 쓸 프로젝트 이름도 확인한다. 확인된 목적과 아직 정하지 않은 점을 최소 제품 문서(`product.md`)로 남긴다. 불분명한 것은 질문·가설로 표시하고 확정된 계획으로 쓰지 않는다. 코드 폴더 생성은 별도 작업이 필요할 때 한다. 첫 작업은 목표 장면 하나를 처음부터 끝까지 가장 얇게 잇는 것(walking skeleton: 실제로 끝까지 도는 가장 작은 구현)으로 잡고, 상태·schema·설계를 미리 다 정하지 않는다.
- **프로젝트는 있지만 hstack 기록이 없으면:** 기존 README·지침·문서와 현재 동작을 먼저 조사한다. 관련 코드는 basics의 역할 구분에 따라 직접 확인하거나 조사를 위임한다. 파악한 목적과 상태를 짧게 보여주고, 지금 사용자의 의도와 맞는지 중요한 부분부터 확인한다. 확인한 사실·사용자가 정한 방향·남은 질문을 최소 제품 문서로 남긴다. 과거 문서의 계획이나 추측을 현재 결정으로 승격하지 않는다. 기존 문서는 임의로 이동·삭제하지 않고 출처를 연결한다.

**처음부터 모든 문서를 만들지 않는다.** 기록 폴더와 최소 제품 문서부터 시작하고, 설계·결정·현황판은 해당 작업이 생길 때 만든다. 확인 질문을 한꺼번에 쏟지 않는다. 조사로 알 수 있는 것은 먼저 확인하고, 목적과 범위를 바꾸는 중요한 부분만 사용자와 하나씩 정한다. 현재 작업과 목적이 분명하면 필요한 단계에서 바로 이어 가며 짧은 일반 질문에 기록과 전체 흐름을 강제하지 않는다.

프로젝트 이름은 [프로젝트 이름 확인 도구](../story-map/scripts/project-id.sh)로 확인할 수 있다. 현재 폴더를 곧 새 제품으로 가정하지 않으며 제품이나 저장소 단위로 기록한다. 기록은 `~/workspace/hstack/data/story-map/<프로젝트>/`다. 기존 팀 문서나 옛 프로젝트 기록을 옮기거나 삭제하지 않는다.

새 기능·변경·원인 조사·버그·성능·보안·작은 UX 수정도 먼저 기대하는 결과와 현재 확인된 사실을 가른다. 관련 위치·재현 여부·원인이 불분명하면 [Understand](../understand/SKILL.md), 구조 선택이 필요하면 [Design](../design/SKILL.md), 구현 순서를 준비하려면 [Prepare](../prepare/SKILL.md)로 이어 간다. 작은 수정은 공통 기준을 적용한다. 아직 실제로 쓰지 않은 작업 유형의 상세 절차를 미리 만들거나 모든 요청에 전체 흐름을 강제하지 않는다.

## 제품과 사용자 행동을 확인한다

`product.md`의 목표·원칙·현재 지원 범위와 중요한 제한을 읽는다. 없으면 [제품 문서 틀](../story-map/references/product-template.md)로 확인된 내용부터 정리한다. 코드로 알 수 없는 제품의 목적·누가 어떤 장면에서 쓰는지는 사용자와 확인한다. 과거 계획이나 코드의 현재 모양을 제품의 최종 목표로 가정하지 않는다.

가로 열은 기능·기술 이름이나 구현 단계가 아니라 사용자가 하는 일을 쓴다. 실제 작업을 찾는 데 필요한 행동부터 시작하고 빈 열을 채우려고 늘리지 않는다. 여러 행동에 걸친 작업도 주된 행동 한 곳에 놓고 나머지는 작업 범위에 적는다. 들어갈 행동을 정하기 어려운 조사·내부 변경은 공통 열에서 찾는다.

사용자 행동의 추가·합치기·이름 변경이 제품을 보는 관점을 바꾸면 먼저 설명하고 사용자와 정한다. 이미 합의한 이름과 배치를 적는 일은 추가 승인 없이 반영한다.

## 후보를 같은 작업으로 남긴다

들어온 요청이 현재 작업의 연속인지, 독립적으로 확인할 다른 결과인지 먼저 본다. 기존 작업의 구체화이면 같은 파일을 갱신하고 독립적인 결과가 추가되면 나누는 기준으로 본다. 요청 글·화면·함수·행동 열 하나를 무조건 작업 하나로 세지 않는다.

후보 단계에는 `tasks/<작업 이름>/작업.md`에 제목·기대하는 결과나 질문·나온 이유 정도만 쓴다. [작업 파일 안내](../story-map/references/work-template.md)를 참고하되 상세 명세·보고서·빈 목차를 미리 모두 만들지 않는다. [보드 형식](../story-map/references/board-format.md)에 같은 파일 경로를 가리키는 카드 하나를 등록한다. 보드에는 상태·주된 행동·짧은 표시 이름·파일 연결만 두고 명세나 완료 기준을 다시 쓰지 않는다.

파일 경로는 같은 작업을 이어 가는 기준이다. 설명 제목이 바뀌거나 후보를 시작한다고 경로를 자동 변경하거나 복제하지 않는다. 에픽 승격·별도 핸드오프 문서를 새로 만들지 않는다.

## 기능 명세를 잡는다

해야 할 일이면 종류와 상관없이(기능, 버그, 조사 등은 예일 뿐이다) 명세를 사용자와 함께 잡는다. 어느 작업을 진행할지는 사용자와 정한다. 제품의 목표와 이미 되는 흐름을 바탕으로 목적·현재 범위·사용자 동작과 조건·완료 기준을 함께 구체화한다. 일부를 빼도 같은 결과를 확인할 수 있으면 더 작은 범위를 비교한다. 서로 독립적으로 평가할 결과가 여럿이면 작업을 나눌 가능성을 설명한다.

- 무엇을 하면 사용자가 어떤 결과를 얻는가.
- 이번에는 원인 확인까지인가, 실제 변경·검증까지인가.
- 어떤 조건에서 무엇을 확인하면 현재 합의를 충족하는가.
- 바뀌면 안 되는 동작·저장 데이터·실패 처리 중 이번에 관련된 것은 무엇인가.

**빈칸은 그림으로 찾는다.** 사용자 동작이 있는 일이면 [브라우저 설명 스킬](../browser-explain/SKILL.md)로 사용자 시나리오를 흐름으로 펼치고, 정상 흐름 밖의 갈림길(실패, 비어 있음, 두 번 실행, 중간에 멈춤, 권한 없음 등 이 일에 해당하는 것)에 아직 정하지 않은 곳을 표시해 함께 메운다. 해당하지 않는 갈림길을 채우려고 늘리지 않는다.

**명세는 사용자가 확인해야 끝난다.** 목적·사용자 시나리오·바뀌면 안 되는 것·완료 기준을 사용자가 확인하면 작업 파일에 `명세 확인: <날짜>, <확인한 범위>`를 남긴다. 남은 미확인은 그 옆에 적는다. 이 줄이 없는 작업을 설계·구현으로 넘기려 하면 먼저 그 상태를 말한다.

명세를 잡을 때 메인은 `basics.md`의 「기준선은 메인 에이전트가 먼저 꺼낸다」대로 사용자가 묻지 않았지만 알아야 할 것(unknown unknowns)을 먼저 꺼낸다. 기준선에서 빠진 중요한 조건이 있으면 그 설명과 독립 검토 원칙을 따른다. Understand로 알아볼 질문과 현재 범위부터 정할 수 있다.

**명세에서 확정하는 것은 결과와 조건이다. 수단은 후보로 따로 적는다.** 목적·사용자 동작·지킬 조건·완료 기준만 확정으로 적는다. 대화나 실험에서 나온 "어떻게"(에이전트로, 특정 SDK로, MCP로)는 「후보 수단」으로 따로 적는다. 후보 수단은 Design에서 같은 높이의 대안과 비교된 뒤에야 확정이다. 사용자가 수단 자체를 원했을 때만(예: "Claude로 해야 한다") 조건으로 올린다. 사용자 동작 문장에 수단을 섞지 않는다. 나쁜 예: "코드가 특정 할인 엔진을 호출해 쿠폰을 적용한다". 좋은 예: "사용자가 유효한 쿠폰을 적용하면 주문 금액에 할인이 반영된다. 후보 수단: 할인 엔진".

작업을 시작하기로 합의하면 해당 카드의 상태를 `doing`으로 맞추고 필요한 Understand·Design·Prepare·Layer 등을 연결한다. 이 스킬에서 상세 구현 방법을 전부 정하거나 자동으로 끝까지 달리지 않는다. 현재 실행의 기준은 작업 파일과 그 파일이 지정한 상세 부분이다.

## 필요한 화면을 같은 작업 안에서 정한다

사용자가 보는 화면이 바뀌는 작업이면 [디자인 설명서](../ui-design/SKILL.md)를 읽고, 프로젝트의 `DESIGN.md`(hstack 기록 폴더, 팀 저장소면 팀 문서)를 먼저 읽는다. 완료 기준에 "이 화면의 핵심"을 한 줄로 사용자와 맞춘다. 색·글자·컴포넌트의 값은 디자인 설명서의 비교판으로 정한다. 새 화면·배치의 구조 선택이 필요하면 시안이 필요한지 사용자와 확인하고 [시안 요청서](../story-map/references/brief-template.md)로 서로 구조가 다른 세 장을 만든다. 이미 화면 방향과 기준이 정해졌다면 같은 선택을 반복하지 않는다.

요청서·현재 화면·시안은 같은 작업 폴더에 이름을 달리해 둔다. 시안 세 장의 차이·약점과 추천을 설명하고 사용자와 고른다. 시안의 본문 글은 이미지 모델이 지어낸 것일 수 있음을 구분한다. 선택과 사용자가 말한 이유·변경한 부분은 작업 파일에 반영하고 시안은 근거로 연결한다. 고르지 않은 시안도 임의로 지우지 않는다. 화면마다 별도 디자인 작업을 만들지 않고 같은 작업 안에서 정한다.

## 진행·마무리와 다시 이어 가기

메인은 상세 보고를 대조해 작업 파일의 현재 명세·선택과 짧은 이유·적용 자료·결과를 갱신한다. 결정 변경의 이유·상세 경과·미결 논의는 같은 작업의 `log.md`에 덧붙인다. 중요한 합의 변경은 다음 위임·실행 전에 반영하고 수행 중인 관련 에이전트에게도 전달한다. 보드의 상태 원본과 작업 파일의 현재 기준을 서로 복제하지 않는다.

- **조사로 끝난 작업:** 합의한 질문·근거·미확인을 확인하고 실제 조사 결과로 완료를 판단한다. 코드가 개선됐다고 표시하지 않는다.
- **구현 작업:** 필요한 레이어와 마지막 [Review](../review/SKILL.md)를 거쳐 현재 완료 기준을 확인한다. 다만 [공통 작은 수정 기준과 절차](../../how-we-work.md#일을-시작할-때-묻는-것)를 끝까지 만족한 작업은 그 절차의 실제 결과 확인과 기록으로 마무리할 수 있다. 직접 수정 여부는 별도 기준으로 판단하며, 구현을 위임했다는 이유만으로 이 예외를 배제하지 않는다. 결과·근거·남은 조건을 작업 파일에 먼저 남긴 뒤 보드에 완료를 반영한다. 구현이 끝났다는 보고만으로 필요한 통합 검토와 완료 확인을 생략하지 않는다.
- **기다리거나 실패한 시도:** 계속할 일이면 진행 중이며 이유·재개 조건을 현재 작업 파일에 남긴다.
- **더 하지 않기로 한 작업:** 사용자와 취소를 확인하고 이유·미해결 결과·필요한 데이터와 코드 영향을 보존한 뒤 취소로 표시한다. 후보나 성공 완료로 바꾸지 않는다.

완료 행은 작업의 결과 이력이다. 현재 제품의 모든 지원 기능을 자동으로 뜻하지 않는다. 기능 추가·제거·중요한 지원 조건과 제한이 바뀌면 제품 문서의 해당 설명도 맞춘다. 새 기능 원본이나 모든 작업의 재요약 목록은 만들지 않는다.

완료 또는 취소로 마무리할 때는 프로젝트의 `log.md`에 결과·확인 범위·제한과 작업 파일·작업 로그 연결을 목록 항목 하나로 남긴다. 작업 중 상세 경과를 공통 로그에 매번 반복하지 않는다. 프로젝트 전체의 중요한 결정은 작업 종료 전에도 요약할 수 있다. 기존 프로젝트 로그와 작업 파일의 누적 이력은 옮기거나 삭제하지 않는다.

## 보드를 확인하고 기록한다

새 형식과 구형 형식의 구분은 [보드 형식](../story-map/references/board-format.md)을 따른다. 옛 `rows/verbs/cells`는 당시 에픽과 칸의 의미로 읽고, 새 작업으로 일괄 치환하지 않는다. 기존 자료 전환은 `/hstack:migrate`의 별도 확인 범위다.

보드 표시나 연결을 바꿨거나 확인이 필요하면 `skills/story-map/scripts/serve.sh`가 제공하는 `skills/story-map/board/?p=<프로젝트>`에서 본다. 기존 서버가 있으면 재사용한다. 프로젝트의 접속 기준에 따라 정확한 주소의 HTTP 응답과 실제 화면을 확인하고 넓은 화면과 좁은 화면에서 행동·상태·작업 문서 연결이 읽히는지 본다. 파일만 만들고 화면이 됐다고 보고하지 않는다. 보드·도구·기존 틀은 주소와 링크를 보존하기 위해 `skills/story-map/`에 유지하며 그 폴더에는 별도의 스킬 입구를 두지 않는다.

관련 프로젝트 기준의 갱신 필요를 확인하고, 해당 작업에 필요한 기록만 갱신한다. 다른 작업과 세션의 변경은 보존한다. 버전·전역·설치본 갱신을 사용자가 보류한 세션에서는 그 지시를 유지한다.
