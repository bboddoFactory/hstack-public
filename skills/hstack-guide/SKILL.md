# hstack 길잡이

hstack(`~/workspace/hstack`)을 고치거나 거기에 무언가를 적을 때 따르는 안내다. 어디에 무엇이 있고, 새로 나온 것을 어디에 적고, 고친 뒤 무엇을 해야 하는지 담는다.

**Hstack을 바꿀 때마다 이 가이드의 갱신 필요를 확인한다.** 공통 지침·스킬·저장소 구조를 고치면 메인이 가이드의 위치·역할·절차·기록 안내를 실제 변경과 대조한다. 문서나 스킬의 추가·이동·이름 변경뿐 아니라 기존 스킬의 책임과 동작이 바뀐 경우도 포함한다. 안내를 고칠 필요가 있으면 같은 커밋에서 반영하고, 없으면 기존 작업 기록에 "가이드 검토: 갱신할 내용 없음"으로 남긴다. 확인할 때마다 가이드 문구를 억지로 바꾸지는 않는다.

고친 뒤 `skills/hstack-guide/scripts/check.sh`도 실행한다. 이 스크립트는 파일 목록·버전 등 일부만 검사한다. 역할·절차의 뜻과 README의 안내가 맞는지는 메인이 직접 대조하며, 스크립트 결과만으로 가이드 전체가 맞다고 보고하지 않는다.

## 어디에 무엇이 있나

| 경로 | 두는 것 |
|---|---|
| `basics.md` | 항상 깔리는 것. 사용자와 이야기하는 법, pstack 원칙(들) 표(원칙의 뜻·꺼낼 상황·hstack 조정의 원본), 만들 때의 기본, 기반 영역 표. 전역 `~/.claude/CLAUDE.md`가 불러와 모든 세션에 깔린다 |
| `how-we-work.md` | 일하는 순서의 지도. 작업의 범위 확인 → 필요한 Understand·Design·Prepare·Layer·Review 및 다른 일의 순서. 공통 레이어 분할 기준, 브라우저 자료의 저장·HTTP 제공·서버 유지, 설계 검토 지적 처리도 여기서 관리한다. 그림 선택과 설명 방식은 browser-explain으로 연결한다 |
| `skills/hippo-mode/` | 공통 작업 입구. 요청의 목적·범위·현재 기록을 정리하고 필요한 이해·설계·구현·검토로 연결한다. 작업을 스토리맵 보드에서 찾는다 |
| `skills/story-map/` | 스토리맵 보드와 공용 자료. `references/`에 작업·보드·제품·시안 틀, `board/`에 두 형식을 읽는 화면, `scripts/`에 실행 도구. 별도 스킬 입구는 없으며 기존 주소와 자료 링크를 보존한다 |
| `skills/prototype/` | 시제품 스킬. 방향을 모를 때 버리는 시제품을 만져 보고 정한다. 본문, `references/`(시제품 지시서) |

| `skills/prepare/` | 구현 준비 스킬. 필요한 Understand↔Design과 기존 근거 재사용을 연결하고 확정 결정·남은 질문·최신 완료 기준을 얇은 레이어 표로 정리한다. `references/`에 표 틀을 두고 분할 기준은 how-we-work를 참조한다 |
| `skills/layer/` | 레이어 스킬. 명세·이번 구성·검증 계획을 함께 확인하고 메인의 행동 테스트·구현 위임·동작과 구성의 대조를 거쳐 올린다. `references/`의 구현 요청서에 책임·상태·실패 흐름·검증 증거와 범위를 전달한다 |
| `skills/review/` | 리뷰 스킬. 같은 요청서의 두 독립 통합 검토·시험 환경 재현·메인의 근거 대조와 사용자 선택을 거쳐 리뷰 레이어로 고치고 닫는다. `references/`에 통합 요청서와 질문을 좁힌 추가 검토 틀을 둔다 |
| `skills/ui-design/` | 화면 디자인 설명서. 메인이 디자이너 역할로 화면의 값을 정할 때 무엇을 묻고 무엇을 원칙으로 정하나, 모르는 것을 먼저 꺼내는 법. `references/`에 기본 점검표·이론 모음·비교판·anti-pattern 모음·외부 스킬 참고·DESIGN.md 틀 |
| `skills/browser-explain/` | 질문에 맞는 그림 선택·작성 전 브리핑·브라우저 핵심 해설과 채팅 설명·의미와 화면 점검. `references/`에 그림 선택 기준, `assets/`에 공통 CSS와 흐름도·시퀀스·상태 전이도·설계안·후보 비교 템플릿. 제품 UI 구현은 ui-design이 맡는다 |
| `skills/codex-automation/` | Codex 자동화 스킬. 자동화를 toml 파일로 만들고 고치고 지우는 법, cron과 heartbeat, 예약 흔들림, 조용히 무시되는 실수, 확인하는 법. |
| `skills/brief/` | 브리핑 스킬. 돌아왔을 때 프로젝트 요약·현황판·현재 작업 파일과 작업 로그를 읽고 지금 어디인지 알려 준다 |
| `skills/herdr/` | 허더 스킬. 음성 입력의 표기 차이를 문맥으로 이해하고 위치로 패널을 찾는다. 실제 CLI 사용법은 설치된 공식 지침을 따른다 |

| `scripts/` | `sync-codex-basics.py`: 공통 본문을 전역 지침에 반영하고 Codex 훅을 등록·검사한다. `mirror-public.sh`: 원본 저장소에서 `data/`를 뺀 사본을 공개 저장소로 올리는 pre-push hook. 원격과 작업 위치는 환경 변수로 정한다 |

## 새로 나온 것을 어디에 적나

| 나온 것 | 적는 곳 |
|---|---|
| 어느 일에서나 지킬 규칙 | `basics.md` |
| pstack 원칙의 뜻·꺼낼 상황·hstack 조정 | `basics.md`의 「pstack 원칙(들)」 표 한곳. 다른 문서는 원칙 이름과 표 연결만 두고 자기 단계의 절차를 둔다 |
| 사용자 메시지마다 덧붙일 상기 문구 | `hooks/reminder.md`. 짧게 유지하고, 매 턴 필요한 것인지 먼저 따진다 |
| 일하는 순서, 단계에서 할 일 | `how-we-work.md`. 그 단계가 스킬이 됐으면 그 스킬 |
| 겪은 일, 규칙을 왜 고쳤나 | `data/story-map/hstack/journal.md` |
| 작업의 결정과 이유·진행·사용자 지적·미결 논의·다음에 할 일, 검증 결과와 미확인 | 해당 작업 폴더의 `log.md`에 덧붙인다. 스킬·규칙 문서와 README에는 쓸 때마다 알아야 할 결정과 지금도 행동을 바꾸는 미확인만 날짜와 경위 없이 둔다. 출시 메모는 출시 작업의 로그에, 프로젝트 기록에 영향을 주는 버전별 변경은 `docs/migrations.md`에 둔다. 현재 합의·결과는 `작업.md`를 갱신한다(공통 규칙은 `basics.md`와 `docs/work-records.md`) |
| 작업을 마친 결과·확인 범위·제한과 상세 연결, 프로젝트 전체의 중요한 결정 | 프로젝트의 `log.md`에 목록 항목으로 요약한다. 상세 경과를 반복하지 않는다 |
| 화면을 정하는 법(새 상황, 점검 항목, 이론, anti-pattern) | `skills/ui-design/`. 본문은 상황과 판단, 자료는 `references/` |
| 한 프로젝트의 시각 규칙 | `data/story-map/<프로젝트>/DESIGN.md`. 팀 저장소에 디자인 문서가 있으면 그것 |
| 한 프로젝트에서 정한 것 | `data/story-map/<프로젝트>/`. 현재 작업의 명세·결정·결과와 근거 연결은 `tasks/<작업 이름>/작업.md`, 새 상세 보고와 레이어 표도 같은 폴더다. 보드는 상태·위치·작업 연결을 관리한다. 기존 단계별 경로는 옮기지 않고 연결한다 |
| 개편 기준으로 관리하는 작업의 현재 내용과 보고서 | `data/story-map/<프로젝트>/tasks/<작업 이름>/`. `작업.md`에는 현재 합의·짧은 선택 이유·확인 결과·남은 일과 근거를 두고 누적 경과는 작업 로그에 둔다. 메인이 현재 내용을 관리하고 하위 에이전트는 지정된 자기 보고서만 작성한다. 과거 단계별 폴더의 보고서는 옮기거나 복사하지 않는다 |
| 다음 작업에도 지킬 프로젝트별 개인 기준 | `data/story-map/<프로젝트>/project-guide.md`. 확인된 기준부터 만들고 조건·근거·관련 기록을 연결한다. 프로젝트 내부의 지시 파일이나 링크는 만들지 않는다. 관리 절차는 `docs/project-guidance.md` |
| 이해·설계의 브라우저 설명 자료 | `tasks/<작업 이름>/설명.html`, `설계.html`. 그림 선택·내용 배치·설명·의미와 화면 점검은 browser-explain, 저장·HTTP 제공은 how-we-work.md를 참조한다. 기존 자료는 실제 경로로 연결한다 |
| 버전을 올릴 때 프로젝트 기록에 영향이 있는 변경 | `docs/migrations.md`에 항목 |
| hstack이 쓰는 말(작업, 레이어 등)의 뜻이나 새 말 | `docs/terms.md`. 들이기 전에 겹치는 말이 있는지 본다 |
| 개인적인 글 쓰는 습관(쓰는 말, 기호) | Claude 메모리. 두 도구가 함께 지킬 대화 행동 원칙은 `basics.md`, 그 근거와 예시는 `docs/response-style.md` |
| 조사자·독립 검토자·구현자의 모델, effort, 도구별 호출, 막혔을 때의 대체 | `docs/agent-calls.md`의 역할표. 에이전트 정의는 `agents/`. 설치와 인증 준비는 README |
| 코드가 알아야 할 이유 | 그 프로젝트의 주석과 커밋 메시지. hstack 경로에 기대지 않는다 |

문서를 새로 만들기 전에 위 표에 들어갈 자리가 있는지 먼저 본다. 자리가 없을 때만 만들고, 만들면 두 표에 줄을 더한다.

## 스킬과 규칙 문서에 쓰는 것

`basics.md`, `how-we-work.md`, `README.md`, `docs/`, `skills/`, `hooks/`, `agents/`의 문서에 적용한다.

- 규칙 문서는 누구나 받아 쓰는 공용 문서다. 특정 사람·프로젝트의 실제 내용(프로젝트 이름, 실제 값, 사용자 발언, 특정 PC의 경로, 직장 이야기)은 `data/`에 두고 여기에는 쓰지 않는다. 예시가 필요하면 가상의 이름을 쓴다.
- 읽는 에이전트(또는 사람)가 **할 일**만 쓴다.
- 상태(확인했다·못 했다·아직 써 보지 않았다), 경위(언제 왜 바꿨다), 옛것(예전에는, 옛 X는 이제)은 쓰지 않는다. 작업 로그나 `data/story-map/hstack/journal.md`에 쓴다.
- 실패 예는 로그가 아니라 규칙에 붙은 예시다. 날짜와 경위 없이, 그 규칙이 막으려는 상황을 알아보게 하는 한 문장으로 둘 수 있다.
- 조심할 것은 상태가 아니라 지시로 쓴다. "강도가 적용되는지 확인하지 않았다"가 아니라 "처음 쓸 때 `/tasks`로 강도를 확인한다".
- 규칙은 원본 한 곳에 두고 다른 곳에서는 원본의 세부를 다시 쓰지 않는다. 그 단계에서 할 일을 떠올리게 하는 짧은 문장(예: "마무리에 작업 기록 기준대로 로그를 남긴다")은 사본이 아니라 상기이므로 둔다.
- 더하기 전에 같은 뜻이 이미 있는지 찾고, 대신 뺄 것을 먼저 본다.

출시 전에 두 검토자가 이 기준으로 검토한다(아래 「고칠 때 순서」 3단계).

## 고칠 때 순서

1. **원본을 고친다.** `~/workspace/hstack/` 아래의 파일이다. 설치된 사본(`~/.claude/plugins/cache/`, `~/.codex/plugins/cache/`)은 고치지 않는다.
2. **가이드 갱신 필요를 검토한다.** 위 기준으로 위치 표와 역할·절차 설명을 확인하고 `README.md`의 스킬 목록과도 대조한다. 필요한 안내 변경은 같은 커밋에 포함하고, 검토 결과는 기존 작업 기록에 짧게 남긴다.
3. **공통 지침이나 스킬의 동작을 바꿨으면 hstack 버전을 올린다.** **올리기 전에 출시 전 문서 기준 검토를 한다.** [요청서 틀](references/release-review-request.md)로 두 독립 검토자(Sol xhigh, Opus xhigh)에게 같은 요청서를 주고, 메인이 근거를 대조한 뒤 고칠 것을 사용자와 정해 반영한다. `basics.md`, `how-we-work.md`의 행동 지침, `docs/agent-calls.md`의 실행 절차 또는 `skills/`의 절차·판단 기준·스크립트·문서 틀이 바뀌면 대상이다. `.claude-plugin/plugin.json`과 `marketplace.json`의 `version`을 같은 값으로 올린다. 어느 숫자를 올릴지는 아래 "버전과 적용 상태 확인"의 규칙을 따른다. 단순 오탈자와 설명 보완, 프로젝트별 작업 기록만 바뀌면 올리지 않는다. 도구별로 별도 버전을 만들지 않는다. **프로젝트 기록에 영향을 주는 변경이면 같은 버전의 항목을 `docs/migrations.md`에 쓴다**(영향이 없으면 `기록에 영향 없음` 한 줄). 항목마다 적용이 필요한지 알아보는 법, 할 일, 그대로 둘 것을 적는다. `/hstack:migrate`가 이것만 읽고 프로젝트에 적용한다.
4. **`skills/hstack-guide/scripts/check.sh`를 돌린다.** 표에 없는 문서나 스킬, 서로 다른 버전, 커밋에 안 들어간 새 파일을 알려 준다.
5. **공통 본문 또는 hstack 버전이 바뀌었으면 Codex 전역 반영과 검사를 한다.** 저장소 루트에서 `python3 scripts/sync-codex-basics.py` 다음 `python3 scripts/sync-codex-basics.py --check`를 실행한다. 어느 도구에서 수정했든 같다. 현재 PC에 Codex를 설치하지 않았으면 미적용으로 보고한다. 이 스크립트를 바꿨을 때도 임시 파일 검증 후 반영한다.
6. **커밋한다.** 새로 만든 파일은 `git add`로 넣는다. 해당 작업의 data 밖 문서·스킬과 필요한 공통 파일의 변경 부분만 골라 올리고 `git diff --cached`로 확인한다. 같은 프로젝트 안에서도 다른 작업·세션의 변경은 섞지 않는다. 부분만 올린 공유 파일은 경로를 지정한 `git commit -- <경로>`로 커밋하지 않는다. 부분 선택이 무시되고 작업 폴더의 다른 변경까지 들어갈 수 있다. 메시지는 사람이 읽을 수 있게 쓴다.
7. **`skills/` 아래를 고쳤거나 버전이 바뀌었으면 설치된 도구별로 설치본을 갱신한다.** 새 세션부터 적용된다. Claude Code:

   ```bash
   claude plugin marketplace update hstack
   ```

   ```bash
   claude plugin update hstack@hstack
   ```

   Codex는 README의 로컬 마켓 설치를 마친 PC에서 다음을 실행한다.

   ```bash
   codex plugin add hstack@hstack --json
   codex plugin list --json
   ```

   로컬 마켓은 원본 저장소를 직접 참조한다. 설치 버전이 원본과 같은지 확인한다. 다른 도구의 설치본은 실제 갱신하지 않았다면 최신이라고 보고하지 않는다.

프로젝트 첫 적용의 절차는 `skills/hippo-mode/SKILL.md`의 「시작할 때」를 따른다. Codex 공통 본문은 반영 스크립트로 전역 지침에 넣는다.

8. **공통 지침이나 스킬의 동작을 바꿨으면 각 PC에서 `/hstack:migrate`를 돌린다.** 진행 중인 프로젝트의 기록(말, 범위, 현황판, 진행 중인 작업과 기존 에픽)은 저절로 바뀌지 않고, 기록은 PC마다 따로 있다. 바꾼 PC는 그 자리에서, 다른 PC는 hstack을 받은 뒤에.

`basics.md`는 Claude Code에서 전역 `CLAUDE.md`가 원본을 직접 읽는다. 공통 지침의 동작이 바뀌면 스킬 변경이 없어도 버전을 올린다. 설치본 갱신만으로 원본 직접 참조나 Codex 전역 파일 반영이 모두 완료됐다고 보고하지 않는다.

### 버전과 적용 상태 확인

- hstack 릴리스 번호는 두 도구가 공유한다. 기존 설치본과 원본의 버전은 별도로 확인한다.
- 올릴 숫자는 **이미 쓰던 사람이 다음에 쓸 때 겪는 것**으로 정한다.
  - **패치**: 같은 절차를 더 정확히 써서 행동이 조금 달라진 것. 오탈자나 뜻이 바뀌지 않는 다듬기는 버전을 올리지 않는다. 쓰던 사람의 일하는 순서는 그대로다.
  - **마이너**: 새 스킬·새 단계·새 규칙을 더하거나, **누가 무엇을 하는지(역할·순서)가 바뀐** 것. 쓰던 사람이 다음에 쓸 때 다르게 해야 한다.
  - **메이저**: 이전에 만든 기록(레이어 표, 요청서, 로그)을 새 규칙으로 읽을 수 없게 되는 것.
  - 1.0이 되기 전에는 메이저를 쓰지 않고, 메이저에 해당하는 변경도 가운데 숫자를 올린다.
  - 한 작업의 변경은 한 번에 올린다. 원격에 올리기 전의 같은 작업은 숫자를 다시 올리지 않는다.
- Codex는 기존 Claude 호환 플러그인 정의를 로컬 마켓으로 설치한다. 설치·갱신 후에는 설치 버전을 조회하고 원본 릴리스와 맞는지 확인한다. 각 스킬의 전체 실행과 데스크톱 메뉴 표시는 별도 확인 대상이다.
- `scripts/sync-codex-basics.py`는 이 PC의 경로로 바꾼 공통 본문을 Codex 전역 파일의 지정 구간에 넣는다. 원본·적용본의 식별값과 버전을 남기며, `--check`로 예상 변환 결과와 일치하는지 검사한다. 구간 밖 기존 지침은 보존한다. 설치 경로가 달라지면 다시 반영한다.
- 플러그인 설치본의 버전과 공통 본문 적용 상태는 따로 확인한다. 한쪽만 갱신하고 전체 적용 완료라고 하지 않는다.
- 새 세션에서 적용 내용을 확인한다. 이미 열린 세션이나 설치 캐시가 자동으로 최신화됐다고 가정하지 않는다. 등록·설치, 전역 본문 일치, 실행 시 지침 전달, 실제 행동 준수는 서로 다른 검증이다. 앞 단계가 됐다는 이유로 뒤 단계까지 잘된다고 보고하지 않는다.

## 스킬로 만드는 기준

- 실제로 써 본 단계만 스킬로 만든다. 써 보기 전에 설계한 스킬은 만들지 않는다.
- 본문(`SKILL.md`)에는 흐름과 판단 기준만 둔다. 형식과 틀은 `references/`로 빼고 경로로 가리킨다.
- `basics.md`의 내용은 본문에 다시 적지 않는다. 이미 모든 세션에 깔려 있다.
- 요청받은 것만 담는다. 사용자의 성향이나 정해진 답변 형식을 넣지 않는다.
- 스킬은 쓰면서 고친다. 안 맞는 자리가 나오면 사용자와 이야기해서 고친다.

## 새 PC에 셋업하기

순서는 `README.md`의 "새 PC에 설치하기"에 있다(스킬이 설치되기 전에 읽어야 해서 거기 둔다). 끝난 뒤 확인하는 법:

- 설치본 갱신 후 새 세션에서 `/hstack:hippo-mode`가 보인다. 원본 변경·설치본 갱신·새 세션 인식은 구분한다.
- 새 세션에 "항상 깔리는 것이라는 문서가 보이나"를 물으면 `basics.md`의 규칙을 말한다.
