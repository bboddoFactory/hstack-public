# 화면 디자인

메인이 디자이너 역할을 맡을 때 읽는 설명서다. 따라 하는 절차가 아니라, 화면의 값을 정할 때 무엇을 묻고 무엇을 원칙으로 정하며 사용자가 모르는 것을 어떻게 먼저 꺼내는지를 담는다. 써 본 것만 적고, 쓰면서 고친다.

## 한 문장

**AI 티는 아무도 고르지 않은 기본값이다.** 화면의 값마다 "어느 목적을 위해, 어느 원칙으로"를 붙일 수 있어야 한다. 붙일 수 없는 값은 사용자가 고르거나 원칙으로 정할 때까지 임시다.

## 누가 하나

- 디자이너 역할은 **메인이 맡는다.** 사용자와 비교판을 보고, 원칙을 설명하고, DESIGN.md를 쓴다. 따로 디자이너 에이전트를 두지 않는다. 디자인 판단은 사용자와의 대화 안에서 일어나기 때문이다.
- 위임하는 것은 둘이다. 비교판 HTML을 만드는 일(값과 이론은 메인이 정해 준다), 그리고 화면을 독립적으로 검토하는 일(기본 점검표를 준다). 화면 구현은 평소대로 구현 에이전트가 한다.

## 언제 쓰나

| 상황 | 사용자가 고르는 것 | 원칙으로 정하는 것 |
|---|---|---|
| 테마 정하기: 앱에 시각 기준이 없거나 아무도 고르지 않은 값뿐일 때. 추상적으로 정하지 않고 첫 화면 위에서 정한다 | 색의 양과 분위기, 강조색, 글자 크기 방식, 라이트·다크 | 다크 값, 대비, 고정폭 숫자, 기본 글꼴 |
| 페이지 핵심: 작업 중 사용자가 보는 화면이 바뀔 때 | 이 화면에서 가장 먼저 봐야 할 것 | 크기·위치·색의 위계, 밀도. DESIGN.md 값 안에서 푼다 |
| 새 컴포넌트(component): 버튼, 입력, 차트, 대화상자, 알림, 빈 화면·불러오는 중·실패 같은 것이 그 앱에 처음 생길 때 | 비교판 중 하나 | DESIGN.md에 이유와 함께 더하고, 두 번째부터는 묻지 않는다 |

**이 셋 밖이라도 사용자가 보는 것이 달라지면 이 설명서를 쓴다.** 새 상황을 만나면 그 작업 로그에 "디자인: 새 상황 — 무엇, 어떻게 했나"를 적고, 돌아보기(`/hstack:retro`)나 hstack 수정 때 이 표에 더한다. 써 보지 않은 상황의 절차를 미리 만들지 않는다.

컴포넌트는 미리 만들어 두지 않는다. 큰 회사의 디자인 시스템처럼 버튼·입력·카드를 먼저 정하면 쓰지 않을 컴포넌트까지 정하게 된다(basics의 KISS). 처음 필요한 작업에서 한 번 정하고 DESIGN.md에 적는다. 같은 것이 반복되면 그때 묶는다("세 번의 규칙", 흔한 관행. Martin Fowler 『Refactoring』이 Don Roberts의 말로 소개).

## 생각하는 순서: 목적 → 원칙 → 값

1. **이 화면의 목적.** 사용자가 이 화면을 왜 여는가, 가장 먼저 봐야 할 것은 무엇인가. 한 문장으로 사용자와 맞춘다.
2. **그 목적에 맞는 원칙.** 목적이 이론을 고른다. "많이 팔린 상품이 눈에 들어와야 한다"면 시각적 위계와 색을 아끼는 원칙이, "주문 금액을 줄지어 비교한다"면 고정폭 숫자가 붙는다. 원칙 목록은 [이론 모음](references/theory.md).
3. **값.** 원칙 안에서 후보를 만들어 비교판으로 보거나, 원칙이 답을 정하면 바로 정한다.

페이지 핵심을 테마보다 먼저 정한다. 핵심이 있어야 어느 이론을 쓸지 고를 수 있다.

## 묻는 것과 정하는 것을 가른다

- **사용자에게 묻는 것:** 취향과 방향. 분위기, 강조색, 이 화면의 핵심, 컴포넌트의 모양. 말로 묻지 않고 [비교판](references/comparison-board.md)으로 보여 준다. 사용자는 "어떤 색이 좋으세요?"에는 답하기 어렵지만 나란히 놓인 화면에서는 바로 고른다.
- **원칙으로 정하고 한 줄로 알리는 것:** 정답이 있는 것. 대비, 다크 값, 숫자 폭, 누를 곳 크기 같은 것. 묻지 않는다. 이유는 알린다.
- 모델에게 고르게 하지 않는다. 모델은 같은 질문에 거의 같은 안을 고른다(Impeccable 자체 측정, 30번 중 27번). 고르는 사람은 사용자다.

## 모르는 것을 먼저 꺼낸다

사용자는 디자이너가 아니어서 무엇을 모르는지 모른다. basics의 "묻지 않았지만 알아야 할 것"을 화면 작업에도 그대로 적용한다.

- 화면 작업에 들어갈 때, 비교판을 낼 때, 화면을 확인할 때 [기본 점검표](references/floor-checklist.md)를 펴 본다.
- 이번 화면에 걸리는 것을 **최대 셋** 꺼낸다. 예: "폰 폭에서 이 금액은 이웃 칸과 붙습니다", "다크 모드를 정하지 않으면 기기 설정이 다크인 날 흰 화면이 뜹니다", "빨강을 지금 넓게 쓰면 나중의 경고가 묻힙니다". 없으면 없다고 한다.
- 점검표에 없는 것을 겪으면 점검표에 한 줄 더한다.
- 점검표를 통과했다고 좋은 화면은 아니다. 금지 규칙 위반이 0인데도 점수가 낮았다는 측정이 있다(taste-skill 제작자 자체 측정). 점검표는 최소 기준이고 고르는 것은 사용자다.

## 원칙을 설명한다

이론이나 원칙을 쓸 때마다 다음을 붙인다. 사용자가 다음 결정에 직접 참여하게 하려는 것이다.

- 이름과 짧은 뜻: "60-30-10 규칙: 화면의 60%는 바탕, 30%는 글자·면, 10%만 강조색"
- 출처와 basics의 구분(업계 표준 / 흔한 관행 / 내 의견)
- 이 화면에 왜 맞는지, 맞지 않는 조건은 무엇인지

비교판에도 후보마다 이론 이름을 붙인다. 이론끼리 무엇이 다른지 화면으로 보면, 사용자는 다음에 그 이론을 이름으로 부른다.

## 기술 스택과 토큰을 두는 곳

**무엇을 고르는지와 어디에 담는지를 나눈다.** 고르는 것(역할과 값)은 스택과 상관없이 같다. 값을 두는 곳(CSS 변수, Tailwind 설정 등)만 스택마다 다르다.

- 색 토큰은 두 종류다. primitive token(파랑 50~900 같은 단계 색)과 semantic token(바탕, 면, 글자, 강조처럼 역할로 부르는 색). 화면 코드는 semantic token만 부른다. Tailwind의 색 단계는 primitive token, shadcn의 `--primary`·`--muted`는 semantic token이다. 컴포넌트의 variant는 상태(state)가 아니라 같은 컴포넌트의 모양 변형이다.
- 프레임워크 없는 앱은 CSS 변수에 역할 이름으로 담는다.
- 이미 값을 두는 곳(CSS 변수 파일, Tailwind 설정 등)이 있으면 거기에 둔다. 그 방식을 바꾸려고 스택을 바꾸지 않는다.

## DESIGN.md

- **위치:** `~/workspace/hstack/data/story-map/<프로젝트>/DESIGN.md`. 저장소에 팀의 디자인 문서가 있으면 그것을 따르고 hstack 것은 만들거나 읽지 않는다. 코드가 직접 읽는 시각 규칙 파일은 저장소에 그대로 둔다.
- **쓰는 법:** [DESIGN.md 틀](references/design-md-template.md). 역할, 값, 쓰는 곳, 이유(원칙과 출처)를 적는다. 사용자가 고른 것과 임시로 둔 것을 구분한다. 여기 없는 값은 쓰지 않고, 새로 필요하면 이유와 함께 먼저 더한다.
- **코드 쪽:** 값은 한 곳(토큰을 두는 파일)에만 두고 흩어 쓰지 않는다. 가능하면 "고르지 않은 값이 없다"를 테스트로 검사한다.
- 구현 요청서의 "먼저 읽을 것"에 DESIGN.md의 hstack 경로를 적는다. 구현 에이전트는 이 설명서를 모른다고 가정한다.

## 확인

- 화면은 직접 열어 본다. 폰 폭(375px)과 넓은 화면, 라이트와 다크. 빌드 통과나 구현 보고로 대신하지 않는다.
- 실제 데이터로 본다. 긴 이름, 큰 금액, 0, 비어 있음.
- [anti-pattern 모음](references/failure-modes.md)에 이름이 있으면 그 이름으로 짚는다.
- 상태는 색이나 아이콘보다 말로 알리고, 실패하면 무엇이 안 됐고 어떻게 다시 하는지를 옆에 둔다.

## 이 설명서를 고칠 때

- 써 본 것만 넣는다.
- 새 상황, 새 점검 항목, 새로 이름 붙일 anti-pattern, 새 이론이 나오면 그 작업 로그에 먼저 적고, hstack을 고칠 때 이 본문이나 `references/`에 옮긴다(`/hstack:hstack-guide`의 순서).
- 외부 디자인 스킬을 들이기 전에 [외부 스킬 참고](references/external-skills.md)에서 이미 본 것인지 확인한다. 큰 묶음을 들이지 않고 필요한 생각만 가져온다(SkillsBench: 좁은 스킬이 큰 묶음보다 나았다).
