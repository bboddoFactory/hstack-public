# 요청서 틀: 레이어 구현

[작업과 기록의 기준](../../../docs/work-records.md)에 따라 `data/story-map/<프로젝트>/tasks/<작업 이름>/구현-<번호>-<이름>-요청서.md`로 저장하고 구현 에이전트 하나에게 준다. 보고는 같은 폴더의 `구현-<번호>-<이름>-보고.md`이며 재시도는 호출별 다른 이름으로 지정해 성공한 보고를 덮어쓰지 않는다.

```markdown
# 구현 요청: <작업> 레이어 <n> — <끝나면 보이는 모습 한 줄>

**너는 구현 에이전트다.** 공통 지침(`basics.md`)에 나오는 "메인"은 이 요청서를 쓴 쪽이고, 너는 구현 코드를 읽고 쓴다.

## 먼저 읽을 것
1. 제품 문서: <전체 경로>
2. 현재 작업과 최신 사용자 확인 완료 기준·변경 근거: <tasks/<작업 이름>/작업.md의 전체 경로와 해당 부분>
3. 레이어 표: <전체 경로>
4. 현재 적용할 상세 문서와 확정 결정: <작업 파일이 지정한 이번 레이어의 주요 책임·상태 소유·외부 약속의 실제 경로와 해당 부분>. 적용 전제: <현재도 맞는 전제>. 남은 질문: <이번 범위에서 구체화할 것과 정할 시점>. 기존 핸드오프 문서 등: <필요한 당시 근거의 실제 경로>
5. 앞 레이어의 보고: <전체 경로>. 마지막 보고에 지금 코드 지도가 있다
6. 프로젝트: <전체 경로>. 규칙 문서(<CLAUDE.md 등>), <살펴볼 폴더>. 화면이 바뀌면 시각 규칙: <hstack의 `data/story-map/<프로젝트>/DESIGN.md` 또는 팀 디자인 문서의 전체 경로>. 여기 없는 색·글자 크기는 쓰지 않는다
7. 개인 작업 기준: <Hstack의 project-guide.md 전체 경로와 이번에 읽을 항목·적용 범위. 없으면 부재와 대신 읽을 근거>

개인 기준과 작업 파일은 읽고 적용하되 파일을 고치지 않는다. 현재 합의와 상세 근거가 충돌하면 임의로 선택하지 않고 메인에게 알린다. 적용한 항목·기준과 실제 코드의 충돌·미확인·갱신 제안(없으면 없음)을 자기 보고서에 남긴다. 기준에 접근할 수 없으면 그 영향도 보고한다. 프로젝트 내부에 개인 지침이나 Hstack 링크를 추가하지 않는다.

**원칙(들):** `/Users/<사용자>/workspace/hstack/basics.md`의 「pstack 원칙(들)」 표를 읽는다(실제 절대 경로로 적는다). 메인이 보기에 해당하는 원칙: <이름과 이번 일에서의 뜻>. 이것은 출발점이며 빠진 원칙을 더하거나 맞지 않는 것을 뺄 수 있다. 보고서에 적용한 원칙(들)과 그것이 바꾼 결정을 쓴다.

## 이번 레이어
**이전 모습:** <앞 레이어까지 사용자에게 보이는 것>
**끝나면 모습:** <이번 레이어까지 하면 보이는 것. 이번만 임시로 그렇게 되는 것 포함>
**실패할 때 보이는 것:** <무엇이 보이고 무엇을 할 수 있나>

가장 단순한 모양 하나로 만든다. 무엇을 더하거나 나누려면 (1) 사용자가 할 일이 달라진다, (2) 나중에 나누면 비싸다, (3) 하나로 두면 조용히 틀린다 중 어느 것인지 보고서에 적는다. 이번 레이어에 쓰이지 않는 것(<다음 레이어들의 것>)은 넣지 않는다.

**사용자에게 보이는 동작을 이 요청서에 없는 방향으로 정해야 하면, 정하지 말고 보고서에 적고 멈춘다.** 보이지 않는 것은 가장 단순한 쪽으로 정하고 보고서에 한 줄 남긴다. 다만 요청 범위를 넘는 큰 자료 이전·외부 의존·실행 방식 변경을 발견하면 구현 전에 보고하고 멈춘다.

## 함께 확인한 구성과 구현 범위
<이번 레이어의 구성 설명·그림·확정 결정의 실제 경로와 해당 부분>
- 이번 담당 범위와 소유 파일: <구현자가 변경할 범위. 다른 에이전트도 작업 중이므로 다른 변경을 되돌리지 않음>
- 주요 책임과 기존 구조의 연결: <확정한 것>
- 데이터 단위·상태 소유·수명·동시 작업의 공유/분리: <해당하는 것>
- 정상·실패 흐름과 외부 검사·변환·오류 전달 책임: <해당하는 것>
- 보존할 동작·바꾸지 않을 범위·남은 질문과 정할 시점: <해당하는 것>
구체화한 책임과 약속 안에서 세부 파일·함수·연결을 정한다. 주요 책임·상태 소유·공개 형식을 바꾸거나 새 추상화나 계층을 넣어야 하면 임의로 하지 않고 메인에게 보고한다. 내부 선택만으로 매번 새 승인을 요구하지 않는다.

## 테스트 (메인이 이미 썼다)
테스트: <테스트 파일 전체 경로>. 실행: <명령>. 메인이 아래 시나리오대로 썼다. 새 동작 테스트: <현재 실패/기존 구현으로 충족, 실패 출력 일부>. 보존 회귀 테스트: <현재 통과 결과>. **이 테스트 파일은 바꾸지 않고** 통과시킨다. 보존 테스트까지 실패해야 하는 것은 아니다.

<시나리오 표 그대로. 범위·환경·자동/직접 수행·입력·기대 결과·증거·담당을 필요한 만큼 연결한다>
자동화할 수 없거나 이번 작업에서 자동 테스트가 적합하지 않은 확인은 <이유·담당·직접 실행 절차와 증거>. 실제 저장·외부 효과·실패 표시가 약속이면 관련 확인도 포함한다. 기존 도구·테스트·실행 절차는 <실제 경로와 명령>.

시나리오가 틀렸거나 불가능해 보이면 테스트를 고치지 말고 보고서에 적고 멈춘다. 안쪽을 확인하는 단위 테스트는 더 써도 되지만, 메인의 테스트나 지금 있는 테스트가 확인하는 것을 줄이지 않는다. **테스트는 프로젝트 밖 경로를 모른다.** 보고용 스크린샷이나 출력은 테스트 밖에서 만든다.

## 정리 (테스트가 통과한 뒤)
이번 범위의 불필요한 중복과 복잡함을 줄인다. 같은 모양만 보고 합치지 않고 대상·책임·규칙이 같은지 확인한다. 이번 일에 필요한 작은 정리만 하며 범위 밖 정리를 벌이지 않는다. 기존 테스트의 확인 내용은 바꾸지 않는다. 모았으면 보고서에 한 줄. (TDD의 red-green-refactor에서 세 번째 단계인 refactor. 출처: Kent Beck, Test-Driven Development: By Example)

## 실패·재시도 조건
실패는 재현하고 최초로 잘못된 상태·결정이 생긴 지점에서 원인을 확인한다. 같은 전제를 공유한 수정이 두 번 이상 같은 검사에서 실패하면 다음 수정 전에 그 전제를 적고 직접 확인한다. 필요한 실행·결과는 기존 보고서에 남긴다. 중요한 설계나 사용자 동작 변경은 메인에게 보고한다.
재시도·중단·재시작이 지원 범위이면 <두 번 실행·중단 뒤 재실행의 기대 결과와 확인 방법>. 해당 없으면 새 장애 실험을 추가하지 않는다.

## 지킬 것
- 프로젝트의 규칙 문서. 허락한 것(<설치해도 되는 패키지>) 말고는 설치하지 않는다. 비밀 값 파일은 열지 않는다. 운영, 올리기, 커밋은 하지 않는다. <건드리지 않을 폴더와 서비스>
- 띄운 것(서버, 백그라운드 프로세스, 열어 둔 포트)은 끝날 때 정리하고, **남지 않았는지 확인해** 보고서에 적는다. <건드리지 않을 포트>
- 주석은 지금 코드처럼, 왜 그런지가 드러날 때만 짧게.
- 끝나면 <타입 검사, 테스트, 빌드 명령>을 돌린다.

## 보고서
<보고서 전체 경로>에:
- 메인의 테스트를 바꾸지 않고 통과시킨 결과(더 쓴 안쪽 테스트가 있으면 그 경로)
- **코드 지도**: 이번 작업과 연결되는 코드 범위의 트리와 파일별 책임 한 줄. 새로 생기거나 바뀐 곳 표시. 나눈 것이 있으면 이유(세 이유 중 무엇)
- 시나리오별 실행 환경·결과·실제 증거와 미확인. 메인이 재확인할 명령·주소·데이터 위치
- 합의한 구성과 실제 구현의 차이·이유. 중요한 미합의 변경을 완료된 선택으로 쓰지 않는다
- 테스트 결과(통과 개수), <빌드 크기 등 잴 것>
- **정한 것**: 사용자에게 보이는 것을 따로 묶고, 그 밖은 한 줄씩
- 띄운 것을 정리하고 남지 않은 것을 확인한 결과
- 스크린샷이나 실행 결과: <무엇을, 어디에>

마지막 답은 "어디에 썼다" 한 줄.
```

## 실행

`docs/agent-calls.md`의 역할표에서 구현자를 부른다. 호출 전에 도구가 동작하는지 한 번 확인한다. 프롬프트는 "요청서를 읽고 그대로 수행해라: <경로>. 지킬 것을 반드시 지킨다. 마지막 답은 보고서 경로 한 줄." 끝나면 메인이 테스트를 직접 다시 돌리고(메인의 테스트 파일이 바뀌지 않았는지도 본다), 스크린샷을 보고, 남은 프로세스와 포트를 확인한다(`/hstack:layer` 4단계).
