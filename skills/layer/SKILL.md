# 레이어

**초기 레이어 계획은 [Prepare](../prepare/SKILL.md)가 연결하며 이 스킬은 나뉜 레이어를 하나씩 만든다.** 만들다 레이어 표 자체를 바꿔야 하면(더하기, 순서 바꾸기, 할 일 옮기기) [공통 분할 기준](../../how-we-work.md#레이어를-나누는-공통-기준)에 따라 사용자 확인을 받고 표를 고친다. 리뷰의 수정 레이어도 같은 기준을 쓴다.

레이어마다 같은 고리를 돈다.

```
명세·이번 구성·검증 계획 함께 확인 → 메인이 테스트·확인 준비 → 구현 → 메인이 동작·구성 확인 → 올린다 → 사용자가 확인
```

"확인 환경"(폰, 브라우저, 터미널 등)과 "검토 환경"은 레이어 표 머리에 있다. **운영에는 레이어마다 올리지 않고** 작업을 닫을 때 `/hstack:review`에서 한 번 배포한다.

이번 레이어의 주요 책임·데이터·상태·처리 흐름은 구현 전에 사용자와 함께 확인한다. 앞에서 확정한 설계는 재사용하고 이번에 바뀌는 부분을 구체화한다. 그 범위 안의 파일 배치·함수와 인터페이스의 세부 구현은 구현 에이전트가 정한다. 모든 파일과 함수를 미리 설계하지 않는다. 메인은 설계 판단에 필요한 관련 코드를 확인하고, 사용자가 판단에 참여할 수 있도록 구조와 선택 이유를 설명한다. 테스트가 부르는 **entry point 이름**(화면 요소, 요청 주소, 명령)은 메인이 시나리오에서 정해 요청서에 적는다.

레이어의 구조와 흐름을 함께 설명할 때도 [브라우저 설명 스킬](../browser-explain/SKILL.md)을 사용한다. 기존 작업의 이해·설계 자료를 연결하고 필요한 내용을 갱신한다.

화면이 바뀌는 레이어면 [디자인 설명서](../ui-design/SKILL.md)를 따른다. 버튼·입력·차트·대화상자·빈 화면 같은 컴포넌트가 그 앱에 처음 생기면 구현 요청 전에 사용자와 모양을 정해 DESIGN.md에 더한다.

**독립적인 작업 전체 리뷰는 작업 끝에 한다(`/hstack:review`).** 레이어마다 메인이 이번 코드 변경·동작·확정한 책임과 상태 관리의 일치를 확인하는 일은 생략하지 않는다. 별도 독립 리뷰를 매번 추가하지 않는다.

## 들어오는 것

[프로젝트 기준 관리](../../docs/project-guidance.md)에 따라 관련 기준을 읽고 구현 요청서에 전달하며, 결과 확인 뒤 그 문서의 Layer 행을 확인한다.

아래 경로는 `~/workspace/hstack/data/story-map/<프로젝트>/` 기준이다. [작업과 기록의 기준](../../docs/work-records.md)에 따라 보드에서 현재 작업을 찾고 작업 파일이 지정한 상세 문서를 읽는다.

- 현재 목적·범위·완료 기준·채택 결정·남은 일: `tasks/<작업 이름>/작업.md`와 지정된 상세 문서, `product.md`
- 레이어 표: `tasks/<작업 이름>/레이어.md`
- 앞 레이어의 구현 보고(마지막 것에 지금 코드 지도가 있다)
- 관련 설계와 남은 질문: 작업 파일·레이어 표에 연결된 같은 작업 폴더의 설계·이해 근거. 리뷰 레이어는 실제 리뷰 보고도 읽는다. 기존 `handoffs/`·`designs/`·`decisions.md` 등은 당시 근거로 연결한다. 옛 ‘걸린 결정’은 확정 ADR와 미정 권고를 구분하고 기존 보고서 이름은 바꾸지 않는다.

## 흐름 한눈에

| 단계 | 누가 | 하는 일 | 사용자 |
|---|---|---|---|
| 1 | 메인 | 기존 결정·전제를 확인하고 명세·이번 구성·실패 흐름·검증 계획과 시나리오를 함께 설명 | **멈춘다.** 기존 확인 자리에서 정한다 |
| 2 | 메인 | 행동 테스트와 필요한 최소 확인 도구·데이터를 준비하고 현재 결과를 본다. 합의한 구성을 구현 요청서에 연결한다 | |
| 3 | 구현 에이전트 | 메인의 테스트를 바꾸지 않고 통과시킨다 | 기다리는 동안 다른 이야기를 해도 된다 |
| 4 | 메인 | 동작·실제 결과와 이번 변경의 책임·상태·실패 처리 일치를 확인한다 | 중요한 차이나 새로 정한 사용자 동작이 있으면 **멈춘다** |
| 5 | 메인 | 커밋, 올리기, 레이어 표 | |
| 6 | 메인 | 바뀐 것과 확인할 것을 알린다 | **멈춘다.** 확인 환경에서 확인한다 |

## 1. 명세·이번 구성·검증 계획을 함께 확인한다

맨 앞에 셋을 먼저 보인다. 사용자는 레이어 목록을 기억하지 않는다.

- **이전 모습**: 앞 레이어까지 했을 때 사용자에게 보이는 것
- **이번 내용**: 이번 레이어에서 하는 것
- **끝나면 모습**: 이번 레이어까지 하면 보이는 것

그다음 명세:

- **사용자 흐름**: 사용자가 하는 일의 순서와 이번 지원 범위. 이번 레이어 동안만 임시로 그렇게 되는 것도 적는다.
- **실패할 때 보이는 것**: 무엇이 보이고 무엇을 할 수 있나. 프로젝트의 에러 규칙이 있으면 따른다.

**이번 구성을 필요한 만큼 함께 본다.** 상태·연결이 있는 기능에서는 다음을 설명하고 브라우저 설명 스킬로 질문에 맞는 그림을 골라 기존 자료에 보여 준다. 해당 없는 항목은 짧게 넘어가며 단순 수정에 빈 설계 문서를 만들지 않는다.

- **책임:** 어떤 부분이 어떤 일을 맡으며 기존 구조와 어디서 연결되는가?
- **데이터·상태:** 무엇이 한 건인가? 누가 상태를 소유·변경하고 언제까지 유지하는가? 동시에 실행되는 작업은 무엇을 공유하고 분리하는가?
- **처리 흐름:** 시작부터 결과까지 데이터와 요청이 어떻게 이동하는가? 외부 입력을 어디서 검사·변환하고 실패를 누가 처리·전달하는가?
- **범위와 조건:** 이번에 바꾸는 것·보존할 것과 아직 모르는 것은 무엇인가? 확정 설계와 충돌하는 중요한 선택은 기존 Understand·Design 연결을 따른다.

새 상태나 중간 계층을 더한다면 어떤 실제 복잡함을 줄이는지 확인한다. 같은 모양의 코드라는 이유만으로 책임과 규칙이 다른 것을 합치지 않는다. 범위 밖 정리를 새로 벌이지 않는다.

**어떤 결과로 확인할지도 구현 전에 정한다.** 자동화 여부와 실제 환경을 구분한다. 각 중요한 시나리오에 실행할 entry point·환경·입력·기대 결과·확인할 증거·담당을 필요한 만큼 연결한다. 실제 저장이 약속이면 다시 읽은 값, 외부 요청이 약속이면 전송 내용·횟수처럼 그 약속을 직접 확인한다. 단위·흐름 테스트와 직접 사용 확인은 함께 쓸 수 있다.

그다음 테스트 시나리오 표. 기준:

- **세 경로**: happy path(정상 경로), 잘못된 입력, 외부 실패(외부 호출의 오류·시간 초과). 해당 없는 경로는 없다고 한 줄.
- **조용히 틀리는 곳 먼저**: 실패가 성공처럼 보이는 곳, 늦게 온 결과가 엉뚱한 데 붙는 곳.
- **약속을 보고 구현은 보지 않는다.** 시나리오는 사용자가 겪는 것으로 쓴다.
- **어떻게 보나**: 단위·흐름 등 검사 범위와 실제/대체 환경, 자동/직접 수행, 기대 결과·증거·담당을 구분한다. 자동화할 수 없거나 이번 작업에서 적합하지 않은 확인은 이유와 누가 어떻게 직접 볼지 적는다. 실제 앱을 구동하는 자동 검사도 가능하며 자동 테스트와 실제 확인을 서로 반대말로 쓰지 않는다.
- 기존 동작을 보존하는 회귀 테스트(이미 되던 동작이 계속 되는지 확인하는 테스트)가 통과한다는 줄을 늘 넣는다.
- 답의 품질 같은 평가 영역은 뺀다.

**시나리오를 펼친 뒤 승인된 레이어 범위와 다시 대조한다.** 새 사용자 결과나 처음 약속하지 않은 큰 자료 이전·외부 의존·실행 방식 변경이 드러나면 테스트·구현 전에 나눌 안을 위의 기존 확인 자리에서 함께 보인다. 작업 자체가 여러 목적을 묶었다면 [기능 명세](../hippo-mode/SKILL.md#기능-명세를-잡는다)로 돌아가 범위를 확인한다. 내부 선택만으로 승인 단계를 늘리지 않는다. 정상·실패·중복은 현재 약속을 지키는 조건으로 함께 검증한다.

사용자 확인으로 완료 기준이 바뀌면 메인이 다음 위임·실행 전에 작업 파일의 현재 명세·채택 결정·적용할 상세 문서와 이유를 맞추고, 레이어 표 머리의 최신 기준 연결도 갱신한다. 해당 레이어의 명세·테스트·구현 요청서와 마지막 Review가 같은 기준을 읽도록 맞춘다. 당시 핸드오프 문서는 덮어쓰지 않으며 보고와 작업 파일이 충돌하면 메인이 해소한다.

**명세 전에 ‘결정·남은 질문’을 읽는다.**

- 확정 결정은 적용 전제가 유지되면 그대로 쓴다. 과거 확정 결정에 새 보고 형식을 소급해서 강제하지 않는다.
- 이번 범위의 세부 방법·실패 장면·연결은 이 레이어에서 구체화한다. 구현 요청서에 주요 책임·상태 소유·외부 약속과 남은 질문을 연결한다.
- 요구·관련 코드·외부 약속·새 근거가 달라졌거나 중요한 선택이 새로 드러나면 [Design](../design/SKILL.md)의 필요한 과정으로 돌아간다. 근거가 부족한 사실은 Understand에서 확인한다. 바뀐 부분만 다루고 기존 조사 전체를 반복하지 않는다.
- 두 권고가 같아도 근거·전제·미확인을 대조한다. 옛 사실 보고를 새 중요한 설계의 독립 후보·적대 검토 완료로 세지 않는다. 역할과 모델은 공통 역할표를 따른다.
- 사용자 동작·제품 방향·되돌리기 비싼 선택과 이번 레이어에서 새로 드러난 설계 판단은 사용자와 정하고 작업 파일에 핵심과 상세 근거를 연결한다. 설계 판단은 basics의 「설계 판단은 선택지를 보고 사용자가 고른다」대로 선택지를 보여 준다. 책임·추상화·경계를 바꾸지 않는 세부(이미 정한 책임 안에서 어느 파일에 둘지, 함수와 인터페이스의 세부)마다 별도 승인 자리를 늘리지 않는다.

## 2. 테스트와 구현 요청서

**테스트는 메인이 사용자와 정한 시나리오를 기준으로 쓴다.** 기대값은 구현 결과가 아니라 요구에서 정한다. 각 검사가 다음 두 조건을 만족하는지 본다: 약속한 결과가 잘못되거나 필요한 효과가 빠지거나 중복되면 실패하는가? 관찰 가능한 결과가 같은 채 내부만 바뀌면 계속 통과하는가? 외부 호출·저장 효과도 약속에 포함되면 검사하며 내부 helper 호출 자체를 성공 기준으로 삼지 않는다.

기존 검사·실행 방법을 우선 재사용한다. 확인에 꼭 필요한 데이터·실행 절차가 없다면 기능보다 먼저 가장 작은 준비를 한다. 준비는 메인의 테스트·확인 책임과 일반 구현 위임 원칙을 따른다. 비단순한 확인을 반복 실행할 필요가 있으면 최소 스크립트나 기존 테스트로 남긴다. 매 레이어마다 새 검사 도구나 공통 프레임워크를 만들지는 않는다.

- 자동 테스트로 확인하기로 한 시나리오마다 테스트를 쓴다. 테스트는 entry point(화면, 요청, 명령)로 부르고, entry point 이름이 아직 없으면 시나리오에서 정한다.
- 새 동작의 테스트는 돌려서 **실패 여부를 직접 본다.** 이미 통과하면 기존 구현으로 요구가 충족되는지, 시나리오를 잘못 옮겼는지 가른다. 억지로 실패시키지 않는다. 기존 동작을 보존하는 회귀 테스트는 처음부터 통과하는 것이 맞다. 지금 있는 테스트가 확인하는 행동을 줄이지 않는다.
- 테스트가 내부 구조나 버전 기대값에 묶여 변경이 필요하면 메인이 이유를 판단하고 고친다. 행동 검증은 보존하며, 구현자가 임의로 테스트를 바꾸지 않는다.
- 자동화할 수 없거나 이번 작업에서 자동 테스트가 적합하지 않은 시나리오는 이유·담당·직접 확인 방법과 증거를 요청서에 둔다.
- 테스트는 프로젝트의 테스트 폴더에 둔다. 구현과 같이 커밋한다.

그다음 구현 요청서를 `data/story-map/<프로젝트>/tasks/<작업 이름>/구현-<번호>-<이름>-요청서.md`에 쓴다. 보고 경로도 같은 폴더의 호출별 다른 이름으로 지정해 성공한 보고를 덮어쓰지 않는다. 틀: `references/layer-request.md`. 틀의 굵은 줄은 빼지 않는다. 현재 작업·적용 자료와 해당 부분·담당 범위·자기 보고 경로, 이번 레이어의 입력, 사용자가 확인한 시나리오, 메인이 쓴 테스트의 경로, 새 동작·보존 테스트의 구분과 현재 결과(실패한 것은 출력 일부)를 채운다. 구현자는 자기 보고만 쓰고 작업 파일·개인 기준을 고치지 않는다.

## 3. 만든다

구현 에이전트가 한다. 메인의 테스트를 **바꾸지 않고** 통과시킨다. 시나리오가 틀렸거나 불가능해 보이면 테스트를 고치지 말고 보고서에 적고 멈춘다. 안쪽을 확인하는 단위 테스트는 더 써도 된다. 메인은 기다리는 동안 사용자와 다른 이야기를 해도 된다(이번 레이어와 부딪치지 않는 것).

### 구현 중 실패하거나 새로운 조건을 발견하면

증상을 재현하고 최초로 잘못된 상태·결정이 생긴 곳을 확인한다. 재시도·조건 추가로 원인을 덮지 않으며 정상적으로 생길 수 있는 상태라면 그 상태의 처리 책임을 바로잡는다. 같은 전제를 공유한 수정이 두 번 이상 같은 검사에서 실패하면 다음 수정 전에 전제를 문장으로 적고 직접 확인한다. 결과와 필요한 재실행 절차는 기존 구현 보고에 남긴다. 중요한 설계·사용자 동작이 바뀌면 해당 Understand·Design과 기존 사용자 확인 자리로 돌아간다.

재시도·중단·재시작이 이번 지원 범위라면 두 번 실행하거나 중간에 끊긴 뒤 다시 실행했을 때 데이터·외부 효과가 어떻게 되는지 시나리오와 확인에 포함한다. 모든 레이어에 모든 장애 실험을 요구하지 않는다.

## 4. 메인이 확인한다

- 이미 정한 내용의 작은 고침이 필요하면 `basics.md`의 직접 수정 예외를 적용할 수 있다. 조건을 모두 만족할 때만 `how-we-work.md`의 작은 수정 절차로 처리하고 결과를 다시 확인한다.
- 이번 변경의 차이와 핵심 연결을 직접 읽어 합의한 책임·상태 소유·공유 범위·외부 약속·실패 처리와 대조한다. 전체 저장소를 다시 조사하거나 별도 독립 리뷰를 매번 추가하지 않는다. 테스트 통과만으로 설계 일치를 주장하지 않는다.
- 프로젝트가 정한 자동 검사와 테스트를 **직접 다시** 돌린다. 메인의 테스트 파일과 기존 행동 검증이 임의로 줄어들지 않았는지 본다. 합의된 테스트 변경은 메인이 이유와 유지할 행동을 확인한다.
- 앞서 정한 화면·응답·재조회한 데이터·외부 효과의 실제 증거를 **직접 본다**. 빌드 통과·오래된 화면·구현자 보고로 대신하지 않는다. 결과가 이상하면 관찰 방법이 실제 대상을 보고 있는지도 확인한다. 확인하지 못한 환경과 남은 조건을 밝힌다. 필요한 증거만 남기며 비밀 값은 포함하지 않는다.
- 띄운 것(서버, 백그라운드 프로세스, 열어 둔 포트)이 남지 않았는지 **직접 본다**
- 보고서의 "정한 것" 중 **사용자에게 보이는 것은 올리기 전에 사용자에게 보인다.** 메인이 "맞는 판단"이라고 넘기지 않는다
- 에이전트가 짚은 위험은, 사용자가 겪는 것이 달라지지 않으면 메인이 정해 같은 에이전트에게 고치게 하고 한 줄로 알린다

## 5. 커밋, 올리기, 기록

- 프로젝트 코드 변경을 커밋한다. 메시지는 사람이 읽을 수 있게, 무엇을 왜.
- 레이어 표의 "검토 환경"에 올린다.
- 레이어 표의 그 레이어를 `올림, 사용자 확인 기다림`과 커밋으로 고친다.
- 메인은 확인 결과·미확인·근거와 남은 일을 작업 파일에 먼저 반영한 뒤 보드 상태를 맞춘다. 레이어를 끝냈다는 이유만으로 작업을 완료로 쓰지 않는다.
- 결정·시도·검증의 경과는 작업 로그에 남긴다. 프로젝트 로그의 결과 요약은 작업 기록 기준에 따라 남긴다.

## 6. 알린다

- **바뀐 것**: 사용자에게 보이는 것으로
- **확인한 것**: 시나리오별 실행 환경·결과와 메인이 본 실제 증거, 핵심 구성과 구현의 대조. 테스트 개수만으로 증명하지 않는다. 확인하지 못한 것과 한계도 구분한다.
- **에이전트가 정한 것 중 보이는 것**
- **확인해 주실 것**: 테스트로 못 본 것. 특히 이번 레이어의 가장 위험한 곳
- 열어 볼 주소나 돌려 볼 명령

사용자가 확인하면 레이어 표를 `끝남(사용자 확인: 무엇)`으로 고친다. **완료 정의에 있는 확인을 미루면** 레이어 표와 작업 로그에 미뤘다고 남겨, 작업을 닫을 때 다시 꺼낸다.

**여기서 스킬이 끝난다.**
