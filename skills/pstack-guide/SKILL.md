# pstack 길잡이

사용자가 하려는 일을 말하면, 맞는 pstack 스킬과 그 스킬에 넣을 프롬프트 예시를 한국어로 알려 준다. 스킬 목록을 물으면 아래 표를 보여 준다.

원본 안내서는 pstack을 설치한 위치의 `docs/guide/`에 있다. 표에 없는 상황은 거기와 각 스킬의 `SKILL.md`를 읽고 답한다.

## 무엇을 언제 쓰나

| 하려는 일 | 스킬 |
|---|---|
| 사소하지 않은 과제 전반. 맞는 절차서를 골라 다른 스킬을 알아서 부른다 | `/poteto-mode` |
| 어떤 부분이 어떻게 동작하는지 알고 싶다 | `/how` |
| 왜 이렇게 만들어졌는지 알고 싶다 | `/why` |
| 요약이 아니라 제대로 이해하고 싶다 | `/teach` |
| 오랜만에 돌아와 어디까지 했는지 따라잡고 싶다 | `/recall` |
| 답을 쉬운 말로 다시 듣고 싶다 | `/bro` |
| 코드를 쓰기 전에 타입과 모듈 모양을 정하고 싶다 | `/architect` |
| 같은 일을 여러 번 시도시켜 좋은 부분을 합치고 싶다 | `/arena` |
| 서로 독립인 조각을 나눠서 한꺼번에 확인하고 싶다 | `/swarm` |
| 변경을 다른 모델에게 깨뜨려 보게 하고 싶다 | `/interrogate` |
| 작은 변경이 무엇을 깨뜨릴 수 있는지 알고 싶다 | `/blast-radius` |
| 버그를 실패하는 테스트부터 써서 고치고 싶다 | `/tdd` |
| 앱을 직접 돌려 동작을 증명할 수단이 없다 | `/create-verification-skill` |
| 그 검증 수단이 앱과 어긋났다 | `/maintain-verification-skill` |
| 리뷰 전에 주석을 걷어 내고 싶다 | `/no-comments` |
| 글에서 AI 티를 빼고 싶다 | `/unslop` |
| 문서, PR 설명, 커밋 메시지를 기준에 맞춰 쓰고 싶다 | `/technical-writing` |
| 맞는 절차서가 없는 크거나 특이한 일이다 | `/figure-it-out` |
| 자리를 비우는 동안의 결정 기록이 필요하다 | `/show-me-your-work` |
| 긴 과제에서 배운 것을 스킬에 남기고 싶다 | `/reflect` |
| 내가 일하는 방식으로 나만의 모드 스킬을 만들고 싶다 | `/automate-me` |

`principle-*`는 직접 부르는 스킬이 아니다. `/poteto-mode`가 읽어서 적용하고, 사용자는 이름으로 방향을 틀 때 쓴다(예: "동작을 증명하기를 적용해라").

## 프롬프트에 넣을 것

원본 안내서의 요지다.

- 목표, 끝났는지 확인할 방법, 바뀌면 안 되는 것을 말한다.
- 스킬을 순서대로 나열하지 않는다. 순서는 `/poteto-mode`의 절차서가 잡는다.
- 주제를 바꿀 때는 "새 과제"라고 말한다. 조사만 원하면 "아직 코드는 바꾸지 마"를 붙인다.
