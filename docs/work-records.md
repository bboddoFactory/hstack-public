# 작업과 기록의 기준

새 기록은 `data/story-map/<프로젝트>/tasks/<작업 이름>/`에 둔다. 기존 기록은 옮기거나 다시 만들지 않고 실제 경로로 연결한다. 에픽은 예전 기록의 관리 단위이며 새 작업 위에 별도로 만들지 않는다. [용어집](terms.md)의 작업 정의를 따른다.

## 같은 작업으로 이어 간다

후보 하나가 시작 전 작업이다. 처음에는 이름·기대하는 결과나 질문·나온 이유 정도만 적는다. 시작하며 목적·사용자 동작과 조건·현재 범위·완료 기준을 구체화한다. 보고서나 빈 목차를 미리 모두 만들지 않는다. 설명 제목이 바뀌거나 시작했다고 작업 폴더·파일을 복제하지 않는다.

같은 목적의 조사·설계·구현·검토는 같은 작업을 갱신하며 이어 간다. 조사 후 수정까지 합의하면 목적·범위·완료 기준을 먼저 맞추고 실행한다. 독립적으로 확인할 다른 결과가 생기면 작업을 나누는 기준으로 본다. 보드의 열이나 기술 단계에 맞추려고 나누지 않는다. 짧은 일반 질문마다 새 카드와 프로젝트 기록을 강제하지 않는다.

## 보드와 작업 파일의 책임

| 원본 | 관리하는 것 |
|---|---|
| `board.json` | 카드의 상태·주된 사용자 행동·짧은 표시 이름·작업 파일 경로 |
| `tasks/<작업 이름>/작업.md` | 현재 목적·범위·사용자 동작과 조건·완료 기준·채택 설계와 짧은 이유·확인 결과·미확인과 남은 일·현재 적용할 상세 문서와 근거 연결 |
| `tasks/<작업 이름>/log.md` | 그 작업의 결정과 이유·변경 경과·시도와 실패·사용자 지적·미결 논의·재개 지점 |
| 같은 작업 폴더의 요청서·보고서·자료 | 이해·설계·구현·검증의 자세한 내용과 근거 |
| 프로젝트의 `log.md` | 작업 결과의 요약과 상세 링크, 프로젝트 전체의 중요한 결정 |
| `product.md` | 프로젝트가 공유하는 제품 목적·원칙·현재 지원 범위와 중요한 알려진 제한 |
| `project-guide.md` | 다음 작업에도 적용할 확정 기준·적용 조건·이유와 근거 |

상태값은 보드에서만 관리한다. 작업 파일의 진행 설명은 확인 결과와 남은 일이며 별도 상태 필드를 반복하지 않는다. 보드에는 명세·완료 기준·채택 설계의 독립 사본을 두지 않는다. 메인은 결과와 근거를 작업 파일에 먼저 남긴 뒤 보드 상태를 맞춘다. 재개 중 둘이 어긋나면 불일치를 밝히고 실제 결과·합의로 정정한다. 편한 쪽을 골라 완료라고 말하지 않는다.

작업 파일과 작업 로그는 메인이 계속 관리한다. 메인이 위임할 때 자기 보고서의 경로를 지정하고 하위 에이전트가 그 보고서를 쓴다. 메인은 보고의 근거·이견·미확인을 대조해 핵심과 링크를 반영한다. 보고 원문을 작업 파일이나 로그에 전부 합치거나 보고자의 제안을 자동 채택하지 않는다. 하위 에이전트는 공통 문서와 다른 작업의 기록을 임의로 고치지 않는다.

## 현재 기준을 읽고 전달한다

프로젝트의 목적·관련 팀 지침·개인 기준과 프로젝트 로그의 최근 요약을 확인한 뒤, 보드에서 작업을 찾아 `작업.md`의 현재 합의와 남은 일, 같은 폴더의 `log.md` 끝부분을 읽는다. 작업 파일이 지정한 **현재 적용할 상세 문서와 해당 부분**을 이어 읽는다. 작업 로그에서 현재 판단·미결 논의가 시작된 부분을 더 읽을 필요가 있으면 범위를 넓힌다. 이전 보고·상세 실행 자료는 관련 부분만 더 읽는다. 프로젝트 요약만으로 진행 중 작업의 논의와 재개 지점을 추측하지 않는다. 모든 보고를 현재 지침으로 보거나 단순히 가장 최근 파일을 우선하지 않는다.

작업 파일의 요약에서 생략됐다고 채택한 상세 조건이 폐기된 것은 아니다. 핵심과 상세가 충돌하거나 적용 여부가 모호하면 메인이 해소한다. 하위 에이전트는 임의로 선택하지 않고 알린다. 현재 작업 경로·이번 담당 범위·적용할 자료·자기 보고 경로를 위임 요청에 함께 준다.

목적·범위·완료 기준 등 중요한 합의가 바뀌면 다음 위임·실행 전에 반영하고 이미 수행 중인 관련 에이전트에게도 변경 내용과 적용 시점을 전달한다. 일반 진행은 단계 마무리에 결과·미확인·남은 일을 맞춘다. 중단·인계 때도 어디까지 했고 무엇부터 이어갈지 적는다. 바뀐 내용이 없으면 다시 쓰지 않는다.

`작업.md`는 현재 본문을 최신으로 갱신한다. 지금 선택을 이해하는 데 필요한 짧은 이유와 근거 연결은 남기되, 변경 경과와 이전 판단을 계속 아래에 쌓지 않는다. 모든 변경 전후를 수동 이력으로 복사하지 않는다.

## 작업 로그와 프로젝트 요약

작업 로그는 기록할 일이 생겼을 때부터 만든다. 결정과 그 이유, 실제로 한 일, 시도·실패, 사용자의 지적, 미결 논의와 다음에 이어갈 지점을 그때그때 덧붙인다. 대화 전문이나 보고서 원문을 복사하지 않는다. 무엇에 관한 기록인지와 확인·합의의 범위를 그 항목만 읽어도 알 수 있게 쓰고, 자세한 근거는 같은 작업의 보고서를 연결한다.

- 모양은 `- [YYYY-MM-DD HH:mm] 내용. 이유와 근거. (사용자)`다. 한국 시간의 기록 시각을 쓰고 사용자가 정한 항목에만 `(사용자)`를 붙인다. 과거 판단의 실제 시각을 추정하거나 초·별도 순번을 만들지 않는다.
- 로그는 덧붙이며 옛 항목을 지우거나 고치지 않는다. 잘못 적은 내용은 새 항목에서 바로잡는다. 현재 합의는 작업 파일에도 맞춘다.
- 작업을 멈추거나 인계할 때는 어디까지 했고 무엇부터 이어갈지 적는다. 현재 결과·남은 일은 작업 파일에도 반영하되 경과 전체를 복제하지 않는다.

작업을 완료하거나 취소할 때는 프로젝트의 `log.md`에 **목록 항목 하나**로 결과·확인 범위·중요한 제한과 작업 파일·작업 로그 링크를 남긴다. 필요하면 한 항목 안에서 여러 줄을 쓴다. 조사 완료·수정 완료·취소를 구분하며, 진행 중 시도와 대화 내용을 프로젝트 로그에 매번 반복하지 않는다. 프로젝트 전체의 목표·공통 기준에 관한 중요한 결정은 작업 종료를 기다리지 않고 그때 요약할 수 있다. 형식은 작업 로그와 같은 기록 시각을 쓰되 상세 경과는 작업 로그로 연결한다.

작업 로그가 없던 기존 작업은 현재 작업 파일·프로젝트 로그·기존 상세 자료에서 이어 간다. 새 로그를 시작하면 이전 기록의 위치를 연결하고 이후 기록부터 새 역할을 적용한다. 기존 프로젝트 로그와 작업 파일의 누적 이력은 일괄 이동·삭제하지 않는다. 읽지 않은 파일을 읽었다고 보고하지 않는다.

## 프로젝트 공통 문서와 변경 보호

`product.md`와 `project-guide.md`는 프로젝트당 공통 원본 하나를 유지하며 코드 워크트리마다 복제하지 않는다. 제품 문서는 목표·현재 지원 범위·제한의 해당 설명을 갱신하고, 가이드는 다음 작업에도 적용하기로 확정한 기준을 갱신한다. 작업별 관찰·가설·선택과 자세한 이유는 작업 기록에 둔다. 단계별 가이드 갱신 검토는 [프로젝트 기준 관리](project-guidance.md)를 따른다.

한 워크트리에서만 확인한 결과를 프로젝트 전체의 지원 사실이나 공통 규칙으로 자동 반영하지 않는다. 공통 문서의 설명에 필요한 적용 범위·코드 상태·환경과 확인 근거를 밝혀 현재 사실과 계획을 구분한다. 공통의 현재가 어느 브랜치·배포 상태를 뜻하는지 작업에 필요하면 확인하며, 모든 프로젝트에 특정 기준을 일괄 강제하지 않는다.

다른 작업이나 세션의 변경을 덮어쓰거나 섞지 않는다. 공통 파일을 함께 수정 중이면 이번 작업에 해당하는 부분만 바꾸고 기존 변경을 보존한다.

## 상태와 배치

| 상태 | 뜻 |
|---|---|
| 후보 (`todo`) | 아직 시작하지 않은 작업. 결과·범위의 초안을 구체화할 수 있다 |
| 진행 중 (`doing`) | 시작했으며 합의한 결과나 확인이 남아 있다. 대기·실패한 시도는 이유와 다음 확인을 작업 파일에 적는다 |
| 완료 (`done`) | 당시 합의한 결과와 확인 범위를 충족했다. 조사 완료를 제품 구현·수정 완료로 바꾸지 않는다 |
| 취소 (`cancelled`) | 더 하지 않기로 정했다. 이유·미해결 결과·필요한 데이터와 코드의 영향을 보존한다. 성공 완료와 구분한다 |

완료 후 원래 기준을 충족하지 못했다는 사실이 드러나면 같은 작업의 완료 판단을 정정한다. 당시 결과는 맞았지만 나중의 변경·새 조건에서 다른 문제가 생겼다면 새 작업을 기존 작업에 연결할 수 있다. 어느 경우인지 모르면 먼저 확인한다.

가로 열은 작업을 찾는 사용자 행동이며 작업의 경계가 아니다. 주된 행동 한 곳에 카드 하나를 두고 다른 관련 행동은 작업 범위에 적는다. 주된 행동를 정하기 어려운 조사·내부 변경은 같은 보드의 `공통` 열에 둔다. 여러 열에 독립 카드·상태를 복제하지 않는다. 분류가 달라져도 작업 파일 경로가 같으면 같은 작업이다.

완료 행은 작업의 결과 이력이다. 현재 기능의 정확한 목록이나 지금도 모든 조건에서 정상이라는 보장이 아니다. 기능 추가·제거·중요한 지원 조건이나 알려진 제한이 달라지면 기존 제품 문서의 해당 설명만 맞춘다. 별도의 기능 원본이나 모든 작업을 다시 요약하는 목록을 만들지 않는다.

## 단계별 기록과 기존 자료

새 이해·설계·레이어 표·구현·리뷰·설명 자료는 해당 작업 폴더에 이름을 달리해 둔다. 예: `이해-요청서.md`, `이해-보고-1.md`, `설계-정리.md`, `레이어.md`, `구현-보고.md`, `리뷰-1.md`, `설계.html`. 실제 필요한 파일만 만든다. 반복 호출은 이미 성공한 보고를 덮어쓰지 않고 서로 다른 경로를 지정한다. 처음부터 단계별 하위 폴더를 만들지 않는다.

이해나 설계에서 확인·선택한 결과는 작업 파일의 현재 명세·핵심 결정과 적용 문서 연결에 반영한다. 구현이 필요하면 Prepare·Layer를 필요한 범위에서 쓰고 마지막 통합 검토는 Review로 한다. 다만 [공통 작은 수정 기준과 절차](../how-we-work.md#일을-시작할-때-묻는-것)를 끝까지 만족한 작업은 그 절차의 실제 결과 확인과 기록으로 마무리할 수 있다. 원인 조사로 끝나는 작업에 구현·리뷰 전체를 강제하지 않는다. 레이어 표는 작업 안의 작은 구현 순서이며 별도 관리 단위나 작업 상태가 아니다.

기존 `rows/verbs/cells` 보드와 `handoffs/understandings/designs/builds/reviews`의 기록은 당시 뜻으로 읽는다. 새 작업 보드 형식은 [보드 형식](../skills/story-map/references/board-format.md)에 있다. 기존 프로젝트를 새 형식으로 이전하는 일은 원본 변경·새 기록 적용과 구분해 `/hstack:migrate`에서 범위를 확인한다. 진행 중 기록을 자동으로 옮기거나 과거 보고를 고치지 않는다.
