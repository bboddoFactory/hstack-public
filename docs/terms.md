# 용어집

hstack이 쓰는 말과 뜻이다. 새 말을 들이거나 이름을 바꾸기 전에 이 표에서 겹치는 말이 있는지 먼저 본다. 실패 예: "줄"을 "슬라이스"로 바꾸려다 레이어의 vertical slice와 겹쳤다. 말을 바꾸면 이 표와 문서 전체를 같이 고치고, 진행 중인 프로젝트에는 `/hstack:migrate`로 적용한다.

## 무엇을 만드나

| 말 | 뜻 | 일반 용어(출처) | 옛 이름 · 피할 말 |
|---|---|---|---|
| 프로젝트 | 제품이나 저장소 하나. 기록은 `data/story-map/<프로젝트>/` | | 제품의 일부(기능, 패키지, 하위 폴더)를 프로젝트로 삼지 않는다 |
| **작업** | **사용자의 행동 흐름을 통해 하나의 독립적으로 확인 가능한 결과를 얻도록 묶은 단위.** 같은 목적과 맥락의 조사·설계·구현·검토는 작업을 갱신하며 이어 간다. 독립적인 다른 사용자 결과가 추가되면 작업을 나누는 기준으로 본다. 기존 에픽의 실행·기록 역할을 통합한 기본 관리 단위다 | Hstack에서 합의한 정의 | 클릭·화면·함수·진행 단계 하나를 곧바로 작업 하나로 세지 않는다. 에픽을 별도 상위 계층으로 요구하지 않는다 |
| 영역 | 여러 부분으로 된 제품(모노레포 등)에서 지금 손대는 부분. 작업 이름 앞에 붙인다(예: `web-장바구니-쿠폰적용`) | | |
| 제품 문서 | `product.md`. 목표·원칙·하지 않는 것과 확인한 현재 지원 범위·중요한 제한. 모든 작업은 이 위에서 정한다 | | |
| 히포 모드, Hippo mode | 요청을 작업으로 정리하고 현재 기록·스토리맵 보드와 필요한 단계별 스킬로 연결하는 입구. 이미 작업과 목적이 분명하면 해당 단계에서 바로 이어 갈 수 있다 | Pstack poteto-mode에서 배운 배경을 담아 Hstack에 맞게 정한 이름 | 옛 스킬 이름: story-map. 스토리맵 보드 자체와 구분한다 |
| 스토리 맵, 맵 | Hstack에서는 사용자 행동별로 작업을 보는 보드. 가로에 행동, 세로에 후보·진행 중·완료·취소를 두고 카드 하나가 작업 하나를 가리킨다. 실제 실행 절차는 각 스킬이 맡는다 | 사용자 행동을 펼치는 배치는 스토리 맵(Jeff Patton, *User Story Mapping*)을 참고했고 작업 상태 보드는 Hstack에 맞게 바꾼 것 | 원저자 기법 전체를 재현하거나 완료 행을 현재 제품 기능 목록으로 보지 않는다 |
| 사용자 활동 | 사용자가 하는 일. 맵의 가로 | 활동, 백본(Patton) | 옛 보드 형식의 이름: 동사(`verbs`) |
| 칸, 카드 | 사용자 행동과 상태에 따라 표시한 작업 하나. 같은 작업 파일을 가리키며 후보를 시작해도 별도 에픽·작업으로 복제하지 않는다 | 기존 칸의 뜻은 옛 스토리 카드(Patton)에서 따옴 | 새 작업의 식별 기준은 작업 파일 경로다 |
| 약속 | 특정 동사 하나가 아니라 제품이 사용자에게 지속해서 지키는 성질. 제품 문서와 관련 작업의 조건에서 유지한다 | 비기능 요구사항 | 옛 보드에는 약속 열이 있다. 새 공통 열을 약속과 같은 뜻으로 쓰지 않는다 |
| 후보 | 아직 시작하지 않은 작업의 상태. 결과·질문·이유 정도의 짧은 기록에서 구체화하며 같은 작업으로 이어 간다 | `todo` | 완성된 명세나 새 에픽 승격을 먼저 요구하지 않는다 |
| 후보 수단 | 대화·실험에서 나온 "어떻게"(에이전트로, 특정 SDK로 등). Design에서 같은 높이의 대안(같은 결과를 내는 다른 수단, 예: 에이전트 ↔ 고정 스크립트)과 비교되기 전에는 확정 전제로 쓰지 않는다 | | 작업 상태 「후보」와 다른 말이다 |
| **에픽** | **작업으로 통합하기 전의 관리 단위.** 그것만 다 되면 사용자가 처음부터 끝까지 한 번 써 볼 수 있는 묶음으로 목적과 완료 정의를 가졌다. 기존 기록의 의미를 읽기 위해 남기며 새 작업에 별도 에픽을 만들지 않는다 | 기존 Hstack에서는 릴리스 슬라이스(Patton), 스크럼의 증분(Increment)에 가깝게 사용 | 옛 이름: **줄, 1차·2차·n차**. 기존 에픽을 조사나 내부 단계 하나와 기계적으로 일대일 치환하지 않는다 |
| 완료 기준, 완료 정의 | 현재 합의한 작업의 목적·범위를 충족했는지 확인할 조건과 절차. 원인 조사 완료와 실제 수정 완료를 구분한다 | 기존 Hstack에서는 Definition of Done(스크럼)을 참고 | 예전 ‘완료 정의’ 기록도 당시 합의한 범위로 읽는다 |
| 현황판, 보드 | `board.json`과 그 화면. 작업의 상태·주된 행동·표시 이름·작업 파일 연결의 원본이다 | 새 형식 `task-board` | 작업 파일의 명세·완료 기준·결과를 다시 복사하지 않는다 |
| 핸드오프 문서 | 기존 에픽을 Prepare로 넘겼을 당시의 합의 기록. `handoffs/<에픽>.md`를 실제 경로로 보존해 읽는다 | 핸드오프(handoff) | 옛 이름: 넘기는 글. 새 작업은 현재 작업 파일과 그 파일이 지정한 상세 기준을 전달하며 별도 핸드오프 문서를 새로 만들지 않는다 |

새 기록은 `data/story-map/<프로젝트>/tasks/<작업 이름>/작업.md`를 중심으로 요청서·보고서·관련 자료를 같은 작업 폴더에 둔다. 실제 혼란이 생기기 전에는 단계별 하위 폴더를 미리 만들지 않는다.

상태·명세·보고 책임과 현재 기준 읽기는 [작업 기록 기준](work-records.md)을 따른다. 기존 에픽 보드와 단계별 기록은 당시 의미로 보존해 읽으며 새 작업 위의 별도 단위를 뜻하지 않는다.

## 어떻게 만드나

| 말 | 뜻 | 일반 용어(출처) | 옛 이름 · 피할 말 |
|---|---|---|---|
| 레이어 | 구현이 필요한 작업 안을 사용자가 확인할 수 있게 입구부터 끝까지 세로로 얇게 자른 것. 끝나면 보이거나 할 수 있는 변화가 하나 생긴다. 같은 흐름의 지원 범위·정확도·사용자 제어를 키우는 중간 증분도 포함한다. 조사로 끝나는 작업에 구현 레이어를 강제하지 않는다 | 수직 조각(vertical slice. Alistair Cockburn, "Elephant Carpaccio") | 서버·DB처럼 기술로 가로로 자른 층이 아니다 |
| 워킹 스켈레톤 레이어 | 맨 앞 레이어. 새로 필요한 기반이나 가장 모르는 것을 가장 얇게 끝까지 잇는다 | walking skeleton(Cockburn) | 옛 이름: 기반 레이어 |
| 정리 레이어 | 보이는 것은 그대로 두고 구조만 고치는 레이어. 지난 작업의 구조 빚이나 리뷰의 안 보이는 고침 | 준비 리팩토링(preparatory refactoring, Martin Fowler) | |
| 리뷰 레이어 | 리뷰에서 고치기로 한 것을 묶은 레이어(`리뷰-1`…) | | |
| 구현 준비, Prepare | 필요한 Understand↔Design을 연결하고 유효한 근거·확정 결정·남은 질문을 얇은 레이어 표로 정리한다. 구현은 시작하지 않는다 | | 옛 입구: Plan |
| 결정·남은 질문 | 레이어 표의 칸. 지켜야 할 확정 결정·적용 전제와 아직 정하지 않은 질문·시점을 구분한다. 그 답에 기대는 데이터·약속·구현을 만들기 전에 정한다 | | 옛 표의 ‘걸린 결정’은 ADR·권고의 실제 내용으로 읽고 일괄 변환하지 않는다 |
| 되돌리기 비싼 결정 | 틀렸을 때 쌓인 것을 옮기거나 남을 고쳐야 하는 결정 | Type 1 결정(아마존), 되돌릴 수 없는 문 | |
| 확인 환경 | 사용자가 레이어를 확인하는 곳(폰 브라우저, 터미널 등) | | 옛 이름: 확인하는 자리 |
| 검토 환경 | 확인 환경에서 열거나 돌릴 수 있는 곳(미리보기 주소, 명령과 브랜치) | 스테이징 | 옛 이름: 레이어를 올리는 곳. 운영이 아니다 |
| 배포 | 구현 작업의 검증된 결과를 프로젝트의 실제 배포 약속에 따라 운영에 반영하는 것 | 릴리스 단위 배포 | 옛 이름: 내보내기. 조사 작업의 완료가 배포를 뜻하지 않는다. 레이어마다 자동 배포하지 않는다 |
| 시제품 | 방향을 모를 때 만들어 보고 버리는 것. 코드는 가져오지 않고 결정만 남긴다 | 버리는 시제품(throwaway prototype, Fred Brooks) | |

## 누가 하나

| 말 | 뜻 | 옛 이름 · 피할 말 |
|---|---|---|
| 메인 | 사용자와 관련 코드·실행 결과를 확인하고 구조와 판단 이유를 이해한다. 테스트·설명 자료를 작성하고 일반 구현은 위임한다. 직접 작은 수정을 하는 조건은 basics를 따른다 | |
| 구현자 | 레이어를 구현하고 시제품을 만드는 에이전트. 모델은 `docs/agent-calls.md`의 역할표 | 구현 에이전트(같은 뜻) |
| 독립 의견 | 같은 질문과 요청서를 서로 모르게 받은 새 세션들의 보고. 난도별 모델·강도·대체는 docs/agent-calls.md의 역할표를 따른다 | 독립 검토(같은 뜻) |
| 항목별 리뷰 | 코드에서 출발해 동작, 구조, 테스트, 보안·성능·운영 등을 보는 리뷰 | |
| 적대적 리뷰 | 사용자가 하는 일에서 출발해 틀린 결과를 보게 되는 경우를 찾는 리뷰 | 옛 이름: 부수기 |

## 기록

| 말 | 뜻 |
|---|---|
| 작업 로그 | `tasks/<작업 이름>/log.md`. 결정 이유·진행 경과·시도와 실패·사용자 지적·미결 논의·재개 지점을 기록 시각과 함께 덧붙인다. 현재 합의는 작업 파일에서 읽는다 |
| 프로젝트 로그 | 프로젝트의 `log.md`. 작업 결과·확인 범위·제한과 상세 링크, 프로젝트 전체의 중요한 결정을 요약한다. 기존 대화 로그의 옛 항목은 보존한다 |
| 대화 로그 | 예전 프로젝트 `log.md`에 결정·지적·미결 논의를 함께 쌓던 이름. 옛 기록은 보존하며 새 기록의 작업 로그와 프로젝트 요약은 작업 기록 기준에 따라 구분한다 |
| 돌아보기 | 필요할 때 현재 세션의 실제 요청·응답·실행을 Hstack 지침과 비교해 일하는 방식을 개선하는 일(`/hstack:retro`). 확인한 근거로 제안하고 승인한 변경만 반영한다 |
| 규칙 적용 | hstack 규칙이 바뀐 뒤 진행 중인 프로젝트의 기록에 적용하는 일(`/hstack:migrate`). `docs/migrations.md`의 항목을 읽는다 |
| `hstack-version` | 프로젝트 폴더의 한 줄 파일. 그 프로젝트 기록에 반영한 마지막 hstack 버전. 없으면 "0.5.0 이전" |
