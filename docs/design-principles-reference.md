# 설계 상황별 원칙 참고

설계할 때 해당하는 절만 골라 읽는다. 문서 전체를 매번 읽는 용도가 아니다.

아래는 Pstack 원칙을 Hstack의 설계 질문으로 정리한 참고 자료다. 원칙의 뜻·꺼낼 상황·hstack 조정의 원본은 [basics의 「pstack 원칙(들)」](../basics.md#pstack-원칙들) 표이고, 이 문서는 설계 단계에서 던질 질문과 예시만 둔다. 둘이 어긋나면 표를 따르고 이 문서를 고친다. 원문을 그대로 실행하는 절차나 업계 공통 표준으로 취급하지 않는다. 기존 제품의 목표·확인한 구조·외부 약속과 함께 판단한다.

## 기존 구조에 새 요구를 추가할 때

**참고 원칙:** 근본부터 다시 생각하기(Redesign From First Principles).

기존 구조는 과거의 요구에 맞춰 만들어졌을 수 있다. 새 요구를 기존 구조에 붙이는 것만 검토하면 책임과 상태 수명이 맞지 않는 부분을 놓칠 수 있다.

- 이 요구를 처음부터 알았다면 어떤 책임·상태·흐름을 두었을까?
- 기존 구조는 그 요구를 어디까지 이미 만족하며, 어떤 전제가 달라졌는가?
- 유지·확장·변경 중 무엇이 필요한가? 이전 비용과 되돌리는 비용까지 고려했는가?

예: 화면을 떠나도 업로드가 계속돼야 한다면 화면의 수명과 업로드 작업의 수명을 구분한다. 이미 화면 밖에서 작업을 관리하는 곳이 있는지 확인하고 재사용 가능성과 새로 관리할 때의 비용을 비교한다.

기존 구조가 있다는 이유로 유지하거나, 원칙 이름을 이유로 전체를 다시 만들지 않는다. 요구를 만족하는 가장 작은 유용한 변경을 찾고 점진적으로 옮기는 방법을 검토한다.

출처: [Pstack 원문](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-redesign-from-first-principles/SKILL.md).

## 상태·데이터·동시 작업을 다룰 때

**참고 원칙:** 기반부터 생각하기(Foundational Thinking), 대상을 데이터로 표현하기(Model the Domain).

처리 순서만 정하면 무엇을 같은 대상으로 볼지, 누가 상태를 바꿀지, 어떤 상태 조합을 허용할지가 여러 곳에 흩어질 수 있다. 먼저 데이터의 단위와 실제 공유 대상을 살핀다.

- 무엇이 한 건이며 어떤 ID와 관계로 구분되는가?
- 누가 상태를 소유하고 누가 바꾸며 언제 만들고 끝내는가?
- 동시에 실행되는 작업이나 늦은 결과가 같은 상태를 바꾸면 어떤 일이 생기는가?
- 허용할 수 없는 상태 조합은 무엇이며 데이터 형식이나 변경 통로에서 막을 수 있는가?

예: 업로드 두 건의 진행률과 취소 상태는 작업 ID로 구분할 수 있다. 공유 작업 관리자 하나를 쓰더라도 각 작업의 데이터와 늦은 응답을 구분해야 한다. 모든 진행률을 하나의 ‘현재 업로드’ 상태에 넣었을 때 서로 덮어쓸 수 있는지 확인한다.

상태가 있다는 이유만으로 상태 머신·전역 저장소·새 관리자를 추가하지 않는다. 현재 구조가 명확하고 국소적이면 유지할 수 있다. 동시 작업도 실제로 공유·변경하는 대상을 확인한 뒤 격리·조율이 필요한지 판단한다.

출처: [Foundational Thinking](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-foundational-thinking/SKILL.md), [Model the Domain](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-model-the-domain/SKILL.md).

## 관리 클래스나 중간 계층을 추가할 때

**참고 원칙:** 이해 부담 줄이기(Minimize Reader Load), 추가 전에 덜어내기(Subtract Before You Add).

역할을 나눠도 호출을 그대로 전달하거나 여러 곳에서 같은 상태를 기억해야 한다면 이해할 일이 더 늘 수 있다. 추가할 부분이 다른 곳의 어떤 복잡함을 줄이는지 설명한다.

- 이 부분은 어떤 정책·표현·상태를 책임지고, 호출자가 무엇을 몰라도 되게 하는가?
- 같은 메서드와 인자를 다음 부분에 전달하기만 하는가, 필요한 변환이나 책임이 있는가?
- 기존의 중복·사용하지 않는 경로를 줄이면 새 부분 없이 해결할 수 있는가?
- 구조를 따라가야 하는 단계와 동시에 기억할 상태가 함께 줄어드는가?

예: 요청을 똑같은 인자로 전달하기만 하는 업로드 관리자를 추가하기보다 기존 담당자가 직접 처리할 수 있다. 반대로 작업별 취소·재시도·수명을 한곳에서 관리해 각 화면의 조율을 줄인다면 별도 관리자를 둘 이유가 생긴다.

파일·계층 수만으로 나쁘다고 판단하지 않는다. 이름이 ‘관리자’라는 이유만으로 없애거나, 이번 범위 밖의 오래된 코드까지 정리하지 않는다. 쓰이지 않는지와 기존 호출자의 약속을 확인하고 필요한 범위에서 단순화한다.

출처: [Minimize Reader Load](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-minimize-reader-load/SKILL.md), [Subtract Before You Add](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-subtract-before-you-add/SKILL.md).

## 외부 입력·통신·오류 처리를 연결할 때

**참고 원칙:** 경계의 책임 정하기(Boundary Discipline).

서로 다른 형식과 신뢰 범위를 넘는 곳에서 검사·변환·오류 처리의 책임을 분명히 한다. 같은 검사를 여러 곳에 반복하거나 내부 처리마다 외부 응답의 모양을 알게 하지 않는다.

- 입력이 실제로 어떤 시스템의 경계를 넘으며 어느 보장을 믿을 수 있는가?
- 어디서 형식을 검사·변환하고, 내부에는 어떤 데이터와 오류를 전달하는가?
- 통신 실패·잘못된 응답·시간 초과를 누가 해석하고 사용자에게 무엇을 보여 주는가?
- 내부 코드가 타입과 변경 통로로 실제 보장받는 것은 무엇인가?

예: 서버 응답을 받는 부분에서 외부 형식을 검사해 내부 업로드 결과로 변환하면 화면마다 응답 구조를 해석하지 않아도 된다. 브라우저와 업무 서버가 서로 다른 경계라면 브라우저가 검사했다는 이유만으로 서버 검사를 생략하지 않는다.

기존 보장을 확인하지 않고 내부 검사를 삭제하지 않는다. 모든 오류를 같은 것으로 숨기거나, 하나의 거대한 오류 관리자를 만들라는 뜻도 아니다. 사용자에게 보이는 실패 동작과 진단에 필요한 원인을 구분한다.

출처: [Pstack 원문](https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/skills/principle-boundary-discipline/SKILL.md). 원문의 내부 신뢰 전제는 현재 시스템에서 실제로 보장되는 범위를 확인해 적용한다.
