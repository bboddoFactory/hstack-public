# 프로젝트별 개인 작업 기준

프로젝트에서 다음 작업에도 필요한 기준을 Hstack에 보관하고 이어받는 절차다. 제품 목적은 product.md, 현재 할 일은 현황판, 현재 합의는 작업 파일, 상세 설계와 결정 경과는 해당 작업의 보고와 로그에 둔다. 역할과 읽기의 공통 기준은 [작업 기록 기준](work-records.md)을 따른다.

## 무엇을 어디에 남기나

현재 안내는 `data/story-map/<프로젝트>/project-guide.md`에 둔다. 확인된 기준이 생길 때 메인이 만들고 빈 목차나 가상의 규칙으로 채우지 않는다. 기존 설계·결정·팀 문서는 옮기지 않고 해당 부분을 연결한다. 개인 기준이나 Hstack 링크를 프로젝트의 AGENTS.md·CLAUDE.md·안내 파일에 추가하지 않는다.

다음 작업의 판단이나 실행을 바꾸는 내용만 남긴다.

| 내용 | 남길 수 있는 기준 |
|---|---|
| 용어와 데이터 | 한 건을 구분하는 단위, 헷갈릴 수 있는 용어의 뜻 |
| 책임과 상태 | 상태 소유자·변경 권한·수명·공유 범위 |
| 구현과 실패 처리 | 반복해서 지킬 입력 검사·변환·오류 전달·기록 방법, 관련 팀 규칙의 위치 |
| 실행과 검증 | 작업 경로·환경·실행 명령, 행동 테스트와 실제 앱 확인 방법, 확인의 한계 |

각 항목은 **어떤 조건에서 무엇을 지킬지, 이유와 확인 근거가 무엇인지** 알 수 있게 쓴다. 적용 대상·예외와 확인 날짜나 코드 상태는 필요한 만큼 적는다. 긴 설계는 경로와 해당 절로 연결하며 같은 규칙과 공통 Hstack 지침을 복제하지 않는다. 번호·별도 관리표·고정 목차를 강제하지 않는다. 변할 수 있는 명령·경로는 필요할 때 다시 확인하고 비밀 값 자체는 쓰지 않는다.

관찰한 동작은 이해 기록에, 제안은 해당 논의·보고에, 앞으로 지킬 것으로 확정한 기준만 현재 안내에 둔다. 일회성 선택·미선택 후보·구현자의 편의·추측한 이유를 확정 규칙으로 올리지 않는다. 기존 코드가 그렇다는 사실만으로 계속 따라야 하는 것은 아니다.

## 시작할 때 읽고 위임할 때 전달한다

1. 메인은 제품 문서·프로젝트 요약·현황판과 현재 작업 파일·작업 로그로 프로젝트와 실제 코드 경로를 식별하고 현재 합의와 재개 지점을 읽는다. 새 세션이나 문맥 압축 뒤에도 같은 시작 절차를 따른다. 기존 기록에 작업 로그가 없으면 실제 위치의 근거로 이어 간다.
2. 안내가 있으면 항목과 적용 조건을 확인하고 이번 질문·변경에 관련된 기준과 상세 근거를 읽는다. 기존 팀 지침도 읽되 모든 이력과 참고 문서를 매번 펼치지는 않는다. 안내가 없으면 부재를 밝히고 기존 문서·현재 코드에서 사실을 확인한다. 부재만으로 작업을 막거나 빈 파일을 만들지 않는다.
3. 적용 기준과 중요한 충돌·미확인을 시작 브리핑에 짧게 포함한다. 기준과 코드가 다르면 코드가 잘못됐는지 문서가 낡았는지 확인한다. 팀 지침과 충돌하면 알리고 확인하며 개인 기록으로 팀 지침을 덮어쓰지 않는다.
4. 조사자·설계자·검토자·구현자의 요청서에 **안내의 전체 경로, 읽을 항목과 적용 범위, 관련 팀 지침 경로**를 적는다. 없으면 부재와 대신 읽을 근거를 적는다. 유지할 조건과 대안으로 바꿀 수 있는 조건을 구분한다. 공통 문맥이 자동 상속됐다고 가정하지 않는다.
5. 하위 에이전트는 지정 기준을 읽고 적용한 항목·충돌·미확인과 갱신 제안(없으면 없음)을 기존 보고서에 짧게 남긴다. 메인은 변경·실행 결과의 핵심을 기준과 대조한다. 경로 전달이나 읽었다는 말만으로 준수를 확인했다고 보고하지 않는다.

자료에 접근할 수 없으면 빠진 항목과 영향을 보고한다. 중요한 기준을 임의로 만들어 그 기준에 기대는 설계·구현을 진행하지 않는다. 접근이 제한된 자료를 외부로 복사해 접근 문제를 해결하지 않는다.

요청 뒤 기준이 바뀌면 메인은 관련 에이전트에게 바뀐 항목과 적용 시점을 전달하고 기존 결과도 새 기준과 대조한다. 보고에는 참조한 날짜·코드 상태나 변경 시점을 필요한 만큼 남기고 전체 기준을 복제하지 않는다.

## 매 단계에서 갱신 여부를 확인한다

**갱신 검토는 필수이며 규칙 추가는 필수가 아니다.** 검토를 생략한 채 단계를 마무리했다고 보고하지 않는다. 각 단계 마무리에 새 지속 기준, 낡거나 충돌한 기준, 지우거나 범위를 좁힐 기준이 있는지 확인한다. 잘못된 기준을 발견하면 마무리까지 기다리지 않고 알린다. 매 답변마다 별도 절차나 승인 자리를 만들지는 않는다.

| 단계 | 메인이 확인할 것 |
|---|---|
| Hippo mode | 요청의 목적·제품·용어·사용자 동작의 합의가 기준의 뜻이나 범위를 바꾸는가 |
| Understand | 사실과 기준이 일치하는가. 관찰·추론을 규칙으로 승격하지 않았는가 |
| Design | 선택한 책임·상태·데이터·실패 처리 중 다음 작업도 지킬 약속이 있는가 |
| Prepare | 기준과 레이어 순서·확정 결정이 맞는가. 계획을 현재 동작하는 사실로 쓰지 않았는가 |
| Layer | 구현·실행·검증 결과가 기준과 맞는가. 구현자의 제안을 채택·수정·제외할 근거가 있는가 |
| Review | 레이어들의 결과·현재 코드·검증 방식·안내에 누락·충돌·폐기할 기준이 있는가 |
| Prototype·기술 실험 | 계속 사용할 근거가 있는가. 버릴 코드의 선택을 영구 규칙으로 옮기지 않았는가 |
| Retro·Migrate | 승인한 변경이 프로젝트 기준에 영향을 주는가. 공통 규칙과 중복·충돌하지 않는가 |

메인이 안내를 편집한다. 하위 에이전트는 근거와 제안만 보고하며 독자적으로 안내를 고치지 않는다. 중요한 새 동작·구조·정책은 기존 설계·Layer 논의에서 사용자와 정한 뒤 기록한다. 이미 합의한 내용이나 확인한 명령·경로의 수정까지 별도 승인을 요구하지 않는다. 미정 내용은 해당 논의에 질문으로 남긴다.

안내는 프로젝트당 공통 원본 하나로 유지하고 현재 적용할 내용으로 갱신한다. 변경 경과와 이전 판단은 해당 작업의 로그·설계·결정에 남긴다. 한 워크트리에서 확인한 사실이나 일회성 선택을 프로젝트 전체의 규칙으로 자동 반영하지 않고, 여러 작업에 적용하기로 확정한 기준만 조건과 근거를 밝혀 적는다. 이전 중에는 현재 상태·계획·적용 조건을 구분한다. 기준을 낮추거나 제품 코드를 범위 밖으로 고쳐 문서와 같게 보이도록 하지 않는다.

검토 결과는 **기존 단계 결과 기록과 사용자 보고에 한 줄씩** 남긴다. 예: “프로젝트 기준 확인: 오류 전달 기준 갱신. 근거: …” 또는 “프로젝트 기준 확인: 갱신할 내용 없음.” 확인하지 못했으면 이유·영향·남은 확인을 적고 갱신 불필요로 처리하지 않는다. 제안만 남긴 것은 적용 완료로 쓰지 않는다.

브리핑처럼 읽기만 하는 작업에서는 관련 기준의 상태와 발견한 충돌만 알리고 파일은 고치지 않는다. 단계 안의 도구 호출이나 단순 질의응답마다 보고를 반복하지 않는다. 버그·작은 수정·스킬 없는 프로젝트 작업도 시작과 마무리에 같은 확인을 적용하되 중간 단계를 새로 만들지 않는다.
