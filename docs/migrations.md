# 규칙 적용 목록

hstack 버전이 오를 때 **프로젝트 기록에 영향을 주는 변경**을 버전별로 적는다. `/hstack:migrate`가 각 프로젝트의 `hstack-version`보다 높은 항목만 읽는다. 처리 순서는 `/hstack:migrate`(낮은 버전부터)를 따른다. `hstack-version`이 없는 프로젝트는 "0.5.0 이전"으로 보고 모든 항목을 읽는다.

**쓰는 법** (버전을 올릴 때, 길잡이의 "고칠 때 순서"):

- 새 항목은 맨 위에 둔다. 제목은 `## <버전> (날짜)`.
- 기록에 영향이 없는 버전도 `기록에 영향 없음` 한 줄로 항목을 둔다. 점검 스크립트(`check.sh`)가 현재 버전의 항목이 없으면 경고한다.
- 변경마다 **적용이 필요한지 알아보는 법**을 쓴다. 이미 적용된 프로젝트에 다시 돌려도 해가 없게 하려는 것이다(시작 버전을 몰라도 된다).
- 변경마다 **할 일**과 **그대로 둘 것**을 쓴다. 대화 로그의 옛 줄과, 연결이 걸린 옛 이름(폴더, 파일, 현황판의 에픽 이름)은 어떤 항목에서도 고치지 않는다.

---

## 0.15.0 (2026-11-13)

기록에 영향 없음. data를 뺀 공개본(hstack-public)을 누구나 받아 쓰는 공용 문서로 정리했다. 공용 문서의 예시는 가상 프로젝트 sample-shop으로 바꾸고, 공용 문서에서 작업 기록을 Git에 커밋하라는 의무를 뺐다(migrate는 Git 조작 대신 변경안을 확인받는다). 규칙 문서에 특정 사람·프로젝트의 실제 내용을 쓰지 않는 규칙과 출시 전 검토의 개인 내용 점검을 더했다. basics·Understand·Design에 이름 있는 패턴·자료구조·알고리즘을 꺼내는 줄을, 기반 영역에 사용자에게 실패를 보여 주는 방식과 그 시점을 더했다. 기존 작업·보드·로그를 옮기거나 바꿀 필요는 없다.

## 0.14.0 (2026-11-12)

명세의 「후보 수단」, Design의 전제 꺼내기, 설계안·후보 템플릿, 로컬 앱 통신 레이어의 Sonnet 배정, 설계 적대 검토자 Astra+Opus, 개발 용어를 그대로 쓰는 기준을 더한다. CLI로 부른 조사자·검토자도 지정 보고서에 직접 쓴다(호출자가 본문을 저장하는 경로를 없앴다).

### 후보 수단

- 알아보는 법: 진행 중(`doing`)이고 아직 Design 전인 작업의 `작업.md` 명세 문장에 수단("에이전트가", "MCP로", 특정 SDK)이 결과와 한 문장으로 묶여 있다.
- 할 일: 일괄로 고치지 않는다. 그 작업이 Design으로 갈 때 메인이 수단을 「후보 수단」 줄로 떼어 사용자에게 확인받는다.
- 그대로 둘 것: Design을 거쳐 비교가 끝난 결정, 완료·취소된 작업, 기존 로그.

### 개발 용어

- 알아보는 법: 프로젝트의 `DESIGN.md`에 `## 부품` 절이 있다.
- 할 일: 없다. 새 DESIGN.md부터 `## 컴포넌트`를 쓴다. 기존 절 이름은 그 프로젝트에서 고칠 일이 있을 때 함께 바꾼다.
- 그대로 둘 것: 기존 DESIGN.md·작업 로그·레이어 표의 옛 말.

## 0.12.1 (2026-11-06)

기록에 영향 없음. 비유 대신 전문 용어와 짧은 뜻을 쓰도록 "쉬운 뜻/쉬운 말"을 "짧은 뜻"으로 바꾸고, hstack이 지어 쓴 이름을 업계 용어로 바꿨다(바닥→기반, 넘기는 글→핸드오프 문서, 확인하는 자리→확인 환경, 레이어를 올리는 곳→검토 환경, 내보내기→배포 등). 옛 레이어 표·로그·핸드오프 문서의 옛 이름은 고치지 않고 `docs/terms.md`의 옛 이름 칸으로 읽는다. 새 레이어 표부터 새 이름을 쓴다.

## 0.12.0 (2026-11-06)

**pstack 원칙(들)을 basics에 상시 두고 판단을 바꾼 원칙을 말하게 하며, Claude·Codex 모두 상기형 훅이 붙는다. Hippo mode에 기능 명세 확인 단계가 생기고, 설계 판단은 선택지를 보고 사용자가 고른다. 문서 사본을 걷어 냈다.**

### 기능 명세 확인

- 알아보는 법: 진행 중(`doing`)인 작업의 `작업.md`에 `명세 확인:` 줄이 없다.
- 할 일: 일괄로 채우지 않는다. 그 작업이 다음에 설계·구현으로 갈 때 메인이 명세가 확인되지 않았음을 먼저 말하고, 사용자가 확인하면 `명세 확인: <날짜>, <확인한 범위>`를 적는다.
- 그대로 둘 것: 완료·취소된 작업, 기존 작업 로그.

### 요청서의 원칙(들) 문단

- 알아보는 법: 진행 중인 작업 폴더에 이미 쓴 요청서에 **원칙(들):** 문단이 없다.
- 할 일: 다음 위임부터 새 요청서 틀을 쓴다. 이미 보낸 요청서와 받은 보고는 고치지 않는다.
- 그대로 둘 것: 기존 요청서·보고서 원문.

## 0.11.0 (2026-11-05)

기록에 영향 없음. 브라우저 설명 스킬(`browser-explain`)과 흐름도·시퀀스·상태 전이도 템플릿을 등록하고 공통 지침·Understand·Design·Prepare·Layer·Review에 연결했다. 다음 그림부터 질문에 맞는 종류와 선택 이유를 먼저 설명하고, 브라우저에는 그림과 핵심 해설을, 채팅에는 상세 해석과 판단을 둔다. 기존 HTML·폴더·과거 로그를 일괄 고치거나 옮기지 않는다. 공통 본문과 도구별 설치본은 각 PC에서 갱신하고 이미 열린 세션의 자동 적용은 가정하지 않는다.

## 0.10.0 (2026-11-03)

**화면 디자인 설명서(`ui-design`)가 생기고, `design-principles.md`가 없어진다. 앱별 `DESIGN.md`는 hstack 기록 폴더에 둔다.**

### DESIGN.md의 위치

- 알아보는 법: 개인 프로젝트 저장소 안에 `DESIGN.md`가 있고 `data/story-map/<프로젝트>/DESIGN.md`는 없다. 예: `apps/sample-shop`. 코드가 그 파일을 직접 읽는지 먼저 본다.
- 할 일: 사용자 확인 뒤 내용을 글자 그대로 `data/story-map/<프로젝트>/DESIGN.md`로 옮기고 저장소의 파일은 지운다. 저장소 안에서 그 파일을 가리키던 README·문서 목록·주석은 "시각 규칙은 개인 기록에 있다"는 한 줄로 바꾸거나 줄을 뺀다(hstack 경로는 적지 않는다). 그 앱의 진행 중인 브랜치·작업 사본에 더 새 DESIGN.md가 있으면 그것이 합쳐진 뒤 옮긴다(예: `shop-theme` 브랜치에 더 새 판이 있다). 저장소 변경은 커밋한다.
- 그대로 둘 것: 팀 저장소의 디자인 문서(그것이 우선이며 hstack에 만들지 않는다), 코드가 직접 읽는 시각 규칙 파일, hstack 저장소 루트의 보드 화면 `DESIGN.md`, 과거 로그·요청서에 적힌 옛 경로.

### design-principles.md의 내용

- 알아보는 법: 진행 중인 작업 파일이나 요청서가 `design-principles.md`를 읽을 것으로 가리킨다.
- 할 일: 다음 위임부터 `skills/ui-design/SKILL.md`(또는 그 `references/`의 해당 자료)를 가리킨다. 옛 여섯 철칙 중 시안·작은 UX·상태 문구·두 폭 확인·DESIGN.md 원본은 설명서에 들어갔고, 그림으로 이해하기는 basics의 브라우저 설명 자료 규칙이 맡는다.
- 그대로 둘 것: 이미 끝난 요청서·보고서·로그의 옛 경로.

## 0.9.0 (2026-11-02)

**Hippo mode·Understand·Design·Prepare, 작업 중심 기록과 보드, Layer·Review·Brief·Retro·Migrate 개편을 함께 출시한다.** 0.8.0에서 보류한 원본 개편과 마지막 원칙·정합성 검토의 네 보완을 포함한다.

### 입구·준비 단계와 현재 결정

- 알아보는 법: 새 요청이나 진행 중 작업에서 옛 `/hstack:story-map`·`/hstack:plan` 호출, 에픽 승격이나 새 넘기는 글을 요구한다. 또는 이해·설계의 확정 결정과 아직 정하지 않은 권고를 구분하지 않는다.
- 할 일: 새 요청의 입구는 Hippo mode, 필요한 사실 확인은 Understand, 구조 선택은 Design, 구현 순서 준비는 Prepare를 쓴다. 현재 작업과 목적이 분명하면 필요한 단계에서 이어 간다. 이미 확인한 근거·결정은 전제가 유지되면 재사용하고, 레이어에서 구체화할 질문만 남긴다. 짧은 일반 질문에 전체 흐름을 강제하지 않는다.
- 그대로 둘 것: 옛 스킬 이름이 든 과거 기록, 당시 넘기는 글·설계·레이어 표와 이미 선택한 결정. 예전 권고를 새 확정 결정으로 바꾸거나 모든 설계 판단을 다시 하지 않는다.

### 작업·보드·로그의 원본 분담

- 알아보는 법: 새 작업을 별도 에픽으로 복제하거나 상세 경과를 프로젝트 로그에 계속 쌓고, 같은 명세·상태를 여러 곳에서 독립 관리한다.
- 할 일: 새 기록부터 `docs/work-records.md`를 적용한다. 같은 목적의 조사·설계·구현·검토는 같은 작업으로 이어 가고 독립적으로 확인할 사용자 결과로 경계를 정한다. `tasks/<작업 이름>/작업.md`는 현재 합의·명세·결정·근거·결과, 같은 폴더의 `log.md`는 상세 경과를 맡는다. 프로젝트 로그는 결과 요약과 연결을 남기며 보드가 상태·위치·작업 파일 연결의 원본이다. 제품 문서·개인 기준은 프로젝트당 공통 원본을 유지한다. 기존 보드의 형식 전환이 필요하면 범위와 바꿀 내용을 먼저 확인한다.
- 그대로 둘 것: 기존 에픽 보드·카드·폴더·파일 경로와 누적 이력·보고 원문. 새 형식을 이유로 일괄 이동·삭제·재분할하지 않는다. 완료 행을 현재 제품 기능 전체의 보장으로 읽지 않는다.

### 프로젝트 기준과 단계별 확인

- 알아보는 법: 확정한 개인 기준이 흩어져 다음 작업이나 위임에 전달되지 않거나, 현재 기준과 실행 결과의 불일치를 마무리에 확인하지 않는다.
- 할 일: 다음 작업에도 지킬 것으로 확인된 기준부터 Hstack의 `project-guide.md`에 조건·이유·근거와 함께 둔다. 관련 팀 지침과 함께 시작·위임 때 필요한 부분을 읽고 각 단계 마무리에 갱신 필요를 확인해 기존 결과 기록에 남긴다. Layer는 최신 명세·구성·검증 계획과 행동 테스트·직접 확인을 연결하고, Review는 두 독립 통합 검토 뒤 필요한 수정만 리뷰 레이어로 잇는다. 작은 수정·조사 종료의 기존 예외와 실제 확인 책임은 유지한다.
- 그대로 둘 것: 팀의 프로젝트 지침과 코드 저장소의 기존 문서, 이미 완료한 검증과 당시 한계. 개인 기준의 복사본이나 Hstack 링크를 프로젝트 지시 파일에 추가하지 않는다. 과거 작업을 일괄 재검토하지 않는다.

### 호출·시안·수치 실험과 보조 스킬

- 알아보는 법: 새 위임에서 오래된 역할표·일괄 실행 금지를 사용하거나, 같은 작업의 시안을 고정 파일명으로 다시 쓰거나, 수치 비교의 조건·실행 근거 없이 결론을 낸다. Brief·Retro·Migrate의 범위를 자동으로 프로젝트 전체나 여러 세션으로 넓힌다.
- 할 일: 새 호출부터 `docs/agent-calls.md`의 역할·강도·대체와 실제 모델 확인 기준을 쓴다. 리뷰의 승인된 시험과 고정 금지를 구분하고 시안 요청·결과는 호출별 경로로 보존한다. 수치로 선택하는 실험에만 실행 전 판단 기준과 반복·실패·캐시·원인 근거 및 미확인을 남긴다. Brief는 지정한 대상, Retro는 필요할 때 현재 세션의 실제 협업, Migrate는 지정 범위나 현재 대화에서 확인한 프로젝트를 다룬다. Hstack 변경마다 가이드의 갱신 필요도 확인한다.
- 그대로 둘 것: 이미 성공한 보고와 과거 원칙 감사의 판정·실행 증거. 모델 배정은 프로젝트 기록을 다시 쓰는 이유가 아니다. 이 항목으로 자동 회고·예약·모델 설치·결제 변경을 실행하지 않는다.

## 0.7.0 (2026-10-25)

**페어 개발의 판단 근거, 작은 에픽·점진적인 레이어, 명세 뒤 범위 대조와 테스트 판정을 보완한다.**

- 알아보는 법: 진행 중인 에픽이나 레이어가 있다. 다음 단계에서 목적·이번 변화·현재 지원 범위와 보존 조건을 새 기준으로 본다. 기존 기록을 일괄 재검토하는 절차는 추가하지 않는다.
- 할 일: 다음 단계부터 새 기준을 쓴다. 기존 프로젝트 계획을 지금 고치지 않아도 이 버전의 기록 적용은 완료할 수 있다. `hstack-version`과 적용 로그는 `/hstack:migrate`의 기존 절차로 갱신한다. 명세를 펼치다가 실제 큰 범위가 드러나면 그 프로젝트의 기존 확인 자리에서 범위 변경을 사용자에게 확인한다. 그전에는 재검토 필요로 남긴다.
- 그대로 둘 것: 기존 에픽·레이어 표·넘기는 글·결정·로그와 연결된 폴더·파일 이름. 새 규칙만으로 자동 분할·이름 변경·옛 로그 수정·옛 결정 재승인을 하지 않는다. 정확성·보존 조건을 빼서 작업을 작게 만들지 않는다.

## 0.6.0 (2026-10-23)

**프로젝트 폴더에 `hstack-version` 파일이 생긴다.**

- 알아보는 법: 프로젝트 폴더(`data/story-map/<프로젝트>/`)에 `hstack-version`이 없다.
- 할 일: 이 항목까지 반영한 버전을 한 줄로 적는다(예: `0.6.0`). 새 프로젝트 기록을 만들 때도 그때의 hstack 버전을 적는다(`basics.md`).
- 그대로 둘 것: 없음.

## 0.5.0 (2026-10-23)

**에픽, 프로젝트 범위, 비싼 결정의 자리, 리뷰 레이어, 구현자와 독립 의견의 모델.**

### 말: "줄", "1차·2차" → 에픽
- 알아보는 법: 현황판 `board.json`의 `rows[].name`이 `1차`, `2차`처럼 번호이거나, 문서와 로그가 "줄"이라고 부른다.
- 할 일: 새 에픽부터 목적에서 따온 이름(예: `기록-화면`)을 쓴다. 손대는 영역이 나뉘는 제품이면 영역을 앞에 붙인다(예: `web-장바구니-쿠폰적용`). 로그에 "옛 기록의 줄·n차는 에픽과 같은 뜻" 한 줄.
- 그대로 둘 것: 옛 이름의 에픽(`1차`), `handoffs/1차.md`, `designs/1차/` 등 옛 폴더와 파일. 현황판의 이름으로 이어져 있어 바꾸면 연결이 끊긴다.

### 프로젝트 범위: 프로젝트는 제품이나 저장소 하나
- 알아보는 법: 프로젝트 이름(`scripts/project-id.sh`가 낸 이름)이 제품의 일부(기능, 패키지, 하위 폴더)를 가리킨다. 예: 저장소 `sample-shop` 안의 웹 작업이 `sample-shop-web`로 잡힘.
- 할 일: 제품 이름을 사용자에게 확인한다. 폴더를 제품 이름으로 바꾸고, 지금 손대던 부분은 앞으로 에픽 이름 앞에 영역으로 붙인다. 같은 제품의 다른 폴더가 이미 있으면 합칠지 묻는다.
- 그대로 둘 것: 폴더 안의 파일 이름과 현황판의 에픽 이름. 제품 문서는 제품 전체가 아니라 이 저장소에서 맡는 범위만 적어도 된다.

### 비싼 결정: 플랜에서 정하지 않고 처음 걸리는 레이어에서 정한다
- 알아보는 법: 하는 중인 에픽의 레이어 표(`designs/<에픽>/레이어.md`)에 "걸린 결정" 칸이 없다.
- 할 일: 이미 `decisions-review/`로 정해 둔 에픽은 표를 그대로 두고 남은 레이어부터 새 레이어 스킬로 간다. 아직 정하지 않은 에픽이면 탐색 보고의 비싼 결정 후보를 처음 걸리는 레이어의 "걸린 결정"에 붙이는 것부터 한다.
- 그대로 둘 것: 옛 방식으로 이미 정한 결정(`decisions.md`, `decisions-review/`).

### 리뷰: 고칠 것을 리뷰 레이어로 묶어 하나씩
- 알아보는 법: 리뷰 단계에 있는 에픽이 있다.
- 할 일: 리뷰에서 고르기로 한 것을 리뷰 레이어로 묶어 레이어 표에 잇는다. 이미 한꺼번에 고친 에픽은 그대로 둔다.
- 그대로 둘 것: 이미 닫은 에픽의 리뷰 기록.

### 구현자와 독립 의견
- 알아보는 법: 기록이 아니라 호출 방식이라 프로젝트 기록에는 영향이 없다.
- 할 일: 없음. 새 호출은 `docs/agent-calls.md`.
